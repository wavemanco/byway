## Context

VOICE is the product's core promise: a person writes every reader-facing line (spec §3.2; protocol 01 VOICE step 7, "inserts the human copy exactly"; port rule 6, "no later block writes over voice"). The external review's F07, confirmed at P1 by the verification, showed that the runner did not keep it:

- A page's write-back went to `helper.voice.apply`, and the result was checked only for an unchanged tag skeleton and for each non-empty line appearing somewhere on the page. Deleted text left on the page, a repeated line replaced by other words, swapped lines and new copy between tags all passed. The fallback placement emptied inline links and emphasis. An out-of-range character reference threw a `RangeError`.
- The "unchanged" test squashed whitespace, so moves across lines, merges and a prose paragraph split were dropped silently, and the last block could not be emptied.
- Every other medium fell back to the model whenever its reader could not map an answer, and the options and on-screen readers dropped or shadowed lines the person typed.
- `keepsVoice` held later machine writes only to substring membership (`lostVoiceLines`), and skipped the check for an empty voice. Canonical C5 reaches this: a model that appended to or reordered the voice-over passed.
- The page tokenizer ended a tag at the first `>`, even inside a quoted attribute value.

The common root: the person's copy could be written by something other than an exact, total application of their edit, as long as the result passed a check weaker than the edit.

This record supersedes the whole "VOICE write-back" bullet of [ADR-0073](0073-runner-semantics-where-the-spec-was-open.md), including its keepsVoice sentence. ADR-0073 is not edited.

## Decision

**Each medium's copy deck is the contract, and no model writes the person's words.** The runner offers the deck, reads the answer with a total reader (every line lands in exactly one place, or the answer is refused with that line named), writes it back deterministically, and checks the written artifact exactly. On a web page the browser has the last word: the runner's own Chromium decides which lines are offered and must show the written page as the person's edit of the page before, or nothing is stored (the browser arbiter, below). VOICE makes no model call in any medium, so demo and paid runs behave the same and VOICE costs nothing. The `helper.voice.apply` templates and the `voice.apply` id stay, because the prompt ids are in the workflow bundle; they are no longer called.

**Decks.**
- Prose: the Markdown document. Code diffs: the "Why:" paragraph (empty is refused). Media: the voice-over script at the early VOICE; at the late VOICE, `Headline:`, `Tagline:` and one `Shot N:` per shot. Options: `### A` then `Title:`, `Pitch:` and `Rationale:` for each option.
- Labelled decks are read by one total reader: each label once, in the order shown, matched by position (so a storyboard whose shots repeat a number still reads); continuation lines belong to the label above; anything else is refused and named. A voice-over line at the late VOICE is refused.
- Non-web write-backs pass a round trip: the deck read back from the written artifact, laid out by one line-based `layoutOf`, equals the answer laid out the same way. `layoutOf` is never the reader. It normalises only layout (line endings, trailing spaces, every run of blank lines that ends at a label or at either end, however long, a value on the line after its label, label case and spacing) and keeps everything inside a value, blank lines between its lines included. The same `layoutOf` is the "unchanged" test, so a doubled space inside a caption is written. A failed round trip is refused quoting the first line that would differ.
- Web pages: one line ("unit") per run of visible text, in reading order. A run is text with no tag inside it but inline formatting (a, abbr, b, bdi, bdo, cite, code, data, dfn, em, i, kbd, mark, q, s, samp, small, span, strong, sub, sup, time, u, var, wbr). So a block is one line unless a `<br>`, a nested block or any other tag splits it, and that includes the tags of elements browsers show inline: font, label, ins, del, a button, an image, an svg or a form control. `<p>Hello <a href="/s"><svg></svg></a> world</p>` is offered as two lines, "Hello" and "world", and `<p>Hello <font color="red">world</font>!</p>` as three (the words stay exact). The VOICE prompt and the line-count refusal say "one line per block of text", which is the common case only: a block that such a tag splits is offered, and counted, as the several lines the person is shown. A block of links side by side (each an `<a>` with an href) gives one line per link. Head content is not offered except `<title>`; text that is not whitespace ends the head, as browsers end it, so text written in the head after the title is offered; it continues the body's first screen line, as browsers show it. The content of a hidden element that browsers show inline (a span, a font, a label or the like with the hidden attribute) is not offered, so the person's words never go into text a browser hides inside a line it shows: `<p>Sale<span hidden> ends</span> today</p>` is offered as "Sale today", and "Sale starts today" is written `<p>Sale<span hidden> ends</span> starts today</p>`. Only lines a browser shows are offered: a line the runner's Chromium does not show in one piece with exactly its words is not offered, and stays byte for byte (the browser arbiter, below). So a hidden block, a closed dialog, the body of a closed `<details>`, the text of an svg or math `<title>` (a tooltip), anything a stylesheet hides, and a line the reader reads where a browser shows nothing (such as the lines an svg `<title>` left open over a paragraph's end hides) are not offered, and the prompt adds "Text a browser does not show (hidden, or shown only as a tooltip) is not offered, and stays as it is." Round 6 offered hidden blocks, closed dialogs, closed `<details>` bodies and svg titles as lines.

**The page tokenizer** reads a page as browsers tokenize it where that decides what is copy, without building the tree: WHATWG tag ends (quotes delimit attribute values only; input ending inside a tag is opaque); comment forms; raw text for script, style, noscript, template, iframe, xmp, noembed, noframes and textarea (textarea's default value is not offered; `/>` on these is ignored in HTML content); a script's `<!--` escapes, so `</script>` inside an escaped `<script` string does not end it; plaintext opaque to the end; `<title>` as RCDATA, offered; inside `<svg>` or `<math>`, a CDATA section is opaque. The self-closing flag is WHATWG's: a `/` read right before `>` outside any value (so `href=/shop/` does not set it). The reader honours it where browsers do (void elements, `<svg>` and `<math>`, and everything inside them) and ignores it on other HTML elements, so `<a href=x/>` and `<span/>` open an element. It builds no tree, but it keeps the stack of open elements as browsers keep it where that decides where an element ends. End tags are matched by WHATWG's rules: a block's end tag closes it and everything open inside it unless a scope boundary (a table, a cell, a caption, an object, a marquee, a template or a list box) lies between; any heading's end tag closes the open heading; `</p>` with no p open makes an empty p and `</br>` is a `<br>`; a formatting end tag (a, b, em, font and the rest) closes its element, and when a block is open inside it, browsers' adoption agency closes the formatting and leaves the block open, as the reader does; any other end tag is ignored when a block or control is open inside its element. Start tags end what browsers end for them: a block ends an open p, an li an open li, a dd or dt an open dd or dt, a heading a heading that is the innermost element, and body content an unclosed head (so the body of a page that omits `</head>` is now offered; it was read as head content before). Browsers ignore a table part outside a table, an `<html>` start tag after any other tag or text, a `<body>` start tag once the body has begun (explicitly, or implicitly with text or a start tag that does not belong in the head), a `<head>` once the head or the body has begun, and a form inside a form; the reader opens no element for them, so none of them breaks a line. (Round 6 read a `<body>` after an implied body as a block break, so deleting a heading between head text and the body's text ran the two together: `…Welcome</head><body><h2>Sale</h2>Order today` showed "WelcomeOrder today". The emptied heading is now kept, and Chromium shows "Welcome" and "Order today" on lines of their own.) There is no reconstruction of formatting elements, except where a link ends, and no foster parenting: content written in a table outside any cell (in a table, a row group, a row or a column group; a row opened inside a cell ends the cell in browsers, and the reader keeps that row innermost) is read where it stands, while browsers move it before the table, so its lines can be offered in another order than a browser shows them. An element read there, or a `<br>`, is never removed, nor is anything holding one: `<div>late:<table><tr><span><section>Gone</section></span>After<td>Cell</td></tr></table></div>` with "Gone" deleted keeps the emptied span and section, which browsers show before the table, so "late:" and "After" stay on lines of their own. Foster parenting is not modelled beyond that: removing a block that stands between text and a table holding fostered content can run that text into the fostered content in a browser (`<div>Lead<p>Middle</p><table><tr><font>F</font><td>Cell</td>…` with "Middle" deleted shows "LeadF"); the reader and the in-code verifier do not see it, and the browser arbiter refuses it. Only the html `<title>` is the page's title: an svg or math `<title>` is an element like any other there (a self-closed one opens nothing, and the svg's end closes one left open), and its text, a tooltip, is not counted as text a browser shows; Chromium does not show it, so it is not offered. Two foreign-content misreads remain in the reader, and the arbiter turns each into a refusal or a line not offered: a MathML `<title>` whose content breaks out (a `<b>`, a `<span>`, a `<p>` inside it) is read as hidden though browsers show that content, and an svg `<title>` left open over an HTML end tag such as `</p>` is read as closed there, though browsers keep it open and show nothing after it. A start tag named image is read as `<img>`, as browsers read it. A link is an `<a>` with an href; an `<a>` without one is a placeholder (browsers show its words plain), so its words are plain in the deck, the prompt and the lock, also when the page leaves it open, as in `<h2><a name="top"/>Welcome</h2>`; its tags still end the links around it. A link is read where browsers end it, at the next `<a ...>` or `</a>` tag: a link the page leaves open (an unclosed `<a>`, `<a href=x/>`, or one a misnested closing tag pops) reaches into the following blocks, as browsers open it again there, and an `<a>` inside another ends the first. This was checked against Chromium (below). Where browsers may stop, skip or resume the link and byway cannot tell without building the tree, that link is "tangled", and every line from it to the page's end is offered (where a browser shows it) but cannot be changed: when its reach holds a table, a list box, an embedded object, a marquee, svg or math; when one of those, opened inside a link the page closes, is still open at its `</a>` (browsers ignore an `</a>` inside a cell, a caption, an object, a marquee or a list box the link holds, so the reader does not match it and reads that link as left open); and when eight or more blocks opened inside the link are open where it ends, because the adoption agency gives up after eight turns. Checked against Chromium, that count is exact for a link open in its block and one block early (tangled where Chromium still ends the link) for a link a block's start has popped from a `<p>`. The VOICE prompt names those lines, and a change to one is refused, naming it ("Line 4 cannot be changed in this step: a link on the page (to /x) is left open or holds another link, around a table, a list box, an svg or other markup where byway cannot tell which words a browser shows as that link's words, so byway cannot write this line exactly. Leave line 4 as it was offered."). An element is removed only when it is balanced: closed by its own end tag while it was the innermost open element, with nothing inside it closed out of order, closed implicitly by an end tag, or ignored, and its start tag ended nothing (browsers' implied end of an open p, li or heading). So no removal leaves an end tag browsers would ignore, takes the start of a block browsers end later, or lets an element its start tag ended run on. Nor is an element removed that holds one end of a left-open link's reach and not the other; an `<a>` written around another goes whole, from its start tag to its own closing tag. On the C1 demo page its tokens are identical to the old tokenizer's. Character references are decoded by parse-entities with browser rules (total; U+FFFD for references out of range). Whitespace means HTML whitespace; a no-break space is text. Changed text is written with `&`, `<` and `>` escaped; unchanged text keeps its bytes.

**Not offered on a page** (each stays byte for byte): attribute copy (alt, aria-label, title, placeholder, meta description), script-generated copy, CSS content, textarea default text, svg CDATA text, xmp and plaintext content, noscript content, `<pre>` content, the content of a hidden element browsers show inline, and every line Chromium does not show (the browser arbiter's offer rule, below). An emptied element is kept, not removed, when it holds a script, a style, a noscript, a template, other raw text or a comment, so those bytes stay too (round 6 removed them with it).

**One bracket notation on every page line.** Link words inside a line are shown in `[brackets]`; a literal bracket, or a backslash before one, is shown escaped with a backslash on every line. A line with links keeps one pair per link, in order; `[]` removes that link. A line that is exactly one link's words takes plain words or one pair around the whole line. A line with no link refuses an unescaped bracket and says how to escape it. Link words are the person's decision: the VOICE prompt names where every link goes ("line 2 "Terms of service" goes to /terms"; at most 40, addresses cut to 60 characters), so there is no relabel guard. This suffix is added by `openCheckpoint` from the work itself, once per checkpoint, re-asks included; it lives there until the next workflow change.

**Edit semantics.** The answer is a positional edit: one line per unit; an empty line deletes that unit's text, the last one included; blank lines past the end are nothing. A question opened by an older engine is aligned by words only (brackets and backslashes dropped). When a changed line no longer lines up with the current deck, it is refused on the first offer and read against the current deck on a re-ask. "First offer" means exactly: the answered checkpoint's starting text equals the text the step first offered; a missing checkpoint counts as a first offer. A changed page line holding a null character (U+0000) is refused, because browsers drop it from a page's text.

**Placement and verification.** Placement is deterministic: changed text goes into the line's text slots, aligned to the old words so formatting follows whole words or pieces (a documented, tested rule; formatting coverage is not verified). No word crosses a link's edge: a link part's words go only into its link, words outside brackets only outside every link (never into an image, svg or icon link that held no words), and a whole-link line's words all into its link. Words added before a line's first kept word, or after its last, go beside it: into the shallowest slot reachable from it across only opening (or closing) formatting, so an empty icon between stays where it was. The whitespace before a line's first word and after its last stays in the slot that held it, at the same end, wherever the new words go (the new words carry their own spaces), so the gap beside an empty icon, an image link, or an arrow at a link's end stays where it was, except where words are added at that edge of the line and the whitespace sits inside formatting the new words go outside of: then the whitespace parts the new words from the old ones, and the new words touch the icon (`<p><svg …></svg><b> Hello</b> world</p>` with "Big Hello world" is written `<svg …></svg>Big <b> Hello</b> world`; layout only, the words are exact). The one exception: a piece that would then show as a space where the person's line has none is dropped. That happens when the person glues text to a word whose edge space sits inside a link or formatting: a pretty-printed `<a href="/shop">\n    our shop\n  </a>` with "Visit [our shop]." is written `<a href="/shop">our shop</a>.`, and `[Order now]!` after `<a>Order now <i class="arrow"></i></a>` is written `Order now<i class="arrow"></i></a>!`, so the arrow loses its gap, because the deck cannot show the arrow. With a space typed after the link (`[Order now] today`) the gap stays. The edge whitespace also parts the line from text beside it on the same screen line (in the same block as browsers show it). Where new words went past the slot that held it (into a shallower slot beyond formatting), or a piece was dropped, and text a browser shows stands beside the line in its block, a space goes at the line's new edge, beside the new words: `<p><del>Was <b>$20 </b></del>Now $15</p>` with "Was $20 only" is written `<del>Was <b>$20 </b> only </del>Now $15`, and `<p><label>Email</label><a href="/help"> help</a> is here</p>` with "Get [help] is here" is written `<label>Email</label> Get <a href="/help"> help</a> is here` (round 3 to 5 wrote "Was $20 onlyNow $15" and "EmailGet help is here"). With nothing beside the line in its block, nothing is added (`<p>Read <a href="/x">more </a></p>` with "Read [more]." is written `Read <a href="/x">more</a>.`). Whitespace inside a line is not kept per slot. Each gap between words is the person's single space: where the old gap lay within one part of the line (outside links, or one link), it goes into the first slot of that gap; at a link's edge, it goes into the part the person typed it in. So in an edited line, where an empty icon in the middle of the line has a space on each side, the space after it is lost ("Hello <icon> world" becomes "Hello <icon>world"); a space on one side only stays on that side, and where the words on both sides of the icon are replaced, the new words can all go before it. The gap before an arrow at the end of a link in the middle of a line is lost whenever the line is edited, even when only words outside the link change: `Ready? <a>Order now <i class="arrow"></i></a> and save.` with "Set? [Order now] and save." becomes `Order now<i class="arrow"></i></a> and save.`. This is layout only; the words are exact. Removal is conservative: an emptied inline element or text block (p, h1–h6, li, blockquote, figcaption), balanced and outside svg and math, is removed unless it holds an embedded element, a script, a style, a noscript, a template, other raw text or a comment, carries a hook (id, for, name, role, data-*, or aria-* other than aria-label), or browsers move it, or an element in it, out of a table (above). No removal may join two runs of text, neither two runs of the deck nor two blocks as the reader reads browsers' blocks, or move where browsers end a link (see the page tokenizer above); where the reader misreads the blocks (a button's content edge, foster parenting, a MathML title breakout), the browser arbiter refuses what the reader let through. Blocks are read by the default stylesheet: text on either side of a block's start tag, of the end tag that closes a block, or of a `<br>` shows on separate lines; every other element shows inline (font, label, ins, del, an image, an svg, a button, a control, a custom element) or not at all (script; an element with the hidden attribute, a closed dialog or a datalist; and the text of an svg or math `<title>` while it is open), whose text and tags are not counted. So `<div><font>Intro<p>Spring sale</p></font>Order today</div>` with the middle line deleted keeps an empty `<p></p>`: removing it would show "IntroOrder today" on one line. Both are weighed by union-find over all removals together, and a deleted line takes the `<br>` run that ends it under the same rule. The whitespace placement put inside an element it then removes (a line's edge space, or a space between two words) is written where the element was, so `<p>Hello <span>world </span><i class="arrow"></i></p>` with "Hello" keeps the gap before the arrow. A deleted line's edge whitespace inside an element the edit removes is written where the element was too, when text a browser shows stands on both sides of the element in one block, as the page was, and only whitespace a browser showed (a hidden block's never showed, so it goes with the block; round 6 wrote it there, and its own verifier refused the write); elsewhere it would sit at a block's edge, where it shows nothing, and it goes with the element. So `<p>Price: <del>$20</del><span> now </span><ins>$15</ins></p>` with "now" deleted is written `<p>Price: <del>$20</del>  <ins>$15</ins></p>`, which shows "Price: $20 $15" (round 5 wrote "Price: $20$15"). A link or button that would be left without words a browser shows, or nameless, is refused, naming its hook, and saying so when it holds words a browser hides, so a line whose link carries a hook can be edited but not deleted. Hidden words (a hidden span) name nothing, and they are never dropped, so a control left with only hidden words is refused, not removed (round 6 counted them as its words and wrote a button that showed empty, with no name). An `<a>` without an href counts here only when a role, a tabindex or an `on…` handler makes it a control; a placeholder such as `<a name="faq">FAQ</a>` may be left empty. One that keeps an image or icon is named by its own aria-label, aria-labelledby or title, or by an image's non-empty alt or an element's own label inside it (an empty alt is decoration). Placement returns its removals as a witness. The verifier shares the reader, the removability rule, the `<br>`-run rule and the rule for a deleted line's whitespace where a removed element was with placement, and nothing else. It refuses a changed line in a tangled link's reach, then checks six invariants: (1) each witnessed removal is allowed, and the markup is the page before less exactly those removals, token for token; (2) and (3) unchanged text keeps its bytes and a deleted line keeps only its edge whitespace, run by run, and where an element was removed the written text is exactly what that shared rule leaves there; (4) each changed line reads exactly as written, both by its words (each slot's text less the edge whitespace it held) and as it shows (all of its text, edge whitespace included, with HTML whitespace collapsed, so no space shows where the person wrote none), and each link part reads exactly its bracketed words; every slot that held the line's edge whitespace still holds it at the same end, across all of the line's segments, unless that piece would have shown between two characters (then it must be gone); (5) no link or button whose shown words were in a changed line is left without words a browser shows, unless something names it (one that held no words, such as an image link sharing a run with a changed line, had no name for the edit to take); (6) read fresh, the written page's runs hold exactly the expected words, in order, and the same words in the same links with the same addresses, so a word that crossed a link's edge is refused however it got there; and its blocks, read as browsers show them (end tags browsers ignore break nothing) with HTML whitespace collapsed, are the page before with the person's lines in place, each changed or deleted line keeping the edge whitespace it had, so the page's own separators between lines stay. Two lines a browser showed apart, on lines of their own or as words on one line, that now run together, a space where none showed, and a line it now breaks are refused however that came about ("The page, read again, runs lines together that a browser showed apart: it shows "IntroOrder today" as one line."; "The page, read again, runs words together that a browser showed apart: it shows "Was $20 onlyNow $15"."). Round 5 compared blocks with all whitespace removed, so it saw lines on separate screen lines run together but not two lines on one screen line losing the space between them. It is independent of placement's alignment and its choices among removals, not of the reader: a page the reader misreads can pass it, which is why the browser has the last word.

**The browser arbiter.** The reader is a model of how browsers build and show a page, and placement and the in-code verifier both depend on it, so a misread there is a write the verifier cannot see (round 6's verifier found that about 440 of 1,500 generated pages read differently from Chromium). So every page VOICE asks the browser itself, and fails closed (page-arbiter.ts):
- What it reads with: the runner's own Chromium (`PageRenderer.shownText`), with JavaScript off (the deck excludes script-made copy), under the render's allowlist, request filter and deadline, reading only the page's first document (a later navigation, such as a meta refresh, gets No Content). It reads document.title and the body's innerText (display, visibility, the hidden attribute, whitespace collapsing and block breaks applied, and CSS text-transform undone so letters read as written), and the same text with the characters of each link marked with the link's address. It changes no sandbox setting. With JavaScript off a noscript element's content shows, so the arbiter reads it as the page's own text; it is never offered and stays byte for byte.
- Where each line shows: a copy of the page is marked at each deck line's first and last character (noncharacters put into the text beside a character, so no element and no collapsed whitespace changes), and Chromium reads the page and the copy. A line is placed where its two marks each show once, the start before the end, with exactly the line's words between them (each run of whitespace read as one space, a line break included). The copy must read as the page does once the marks are taken out; if it does not, or the page itself holds the marks' characters, no line is placed: every line is offered, the prompt says none can be changed, and a change to one is refused.
- What is offered (the offer rule): a line that is not placed is not offered, and stays byte for byte; placement and the in-code verifier read it as the page's own text. Lines are offered in the reader's order, and each is placed where Chromium shows it (content a browser moves out of a table is placed before the table).
- What the written page must show: Chromium's text of the page before, with each changed or deleted line's placed words replaced by the person's words (brackets taken out), and everything else, the separators between lines included, as the page had it. A gap between two of the person's words is one space, except inside a line Chromium showed broken over screen lines (by a style the deck does not read), where it may be a space or a line break. A changed line's link words must be the deck's as Chromium shows them (each bracketed part in one link, nothing else in a link); the person's bracketed words then belong to that link's address, and every other character keeps the link Chromium showed it in.
- The check, after placement and the in-code verifier pass and before anything is stored: Chromium's reading of the written page, with each run of whitespace one space or, when it holds a line break, one line break, and its ends trimmed, must equal that text exactly, every character it shows must be in the expected link (by address), and the title must read as expected. Any difference refuses the write: nothing is stored, the person's answer is kept, and the question is asked again with the reason, naming the changed line nearest the difference and quoting it as first offered: "byway could not put line 4 on this page exactly as you wrote it, because a browser would run words together that your lines keep apart: it would show "Pay $20Total". Change line 4 again, or leave it as it was offered." The other reasons say that a browser would show a space, a line break or text the lines do not have, would not show all of the lines, would put on one line what it showed on separate lines, or would show words outside, inside or in another link than the brackets put them. A changed line Chromium does not show where byway reads it, or whose link words Chromium shows otherwise, is refused the same way, ending "Leave line N as it was offered." A fault in byway's own arbiter code is asked again like any fault in the pure copy code; a page Chromium cannot load in time is a plain StepError, as a render is.
- With no page renderer configured, a page's VOICE fails plainly with a StepError, when it would ask and when it would write: byway never writes a page no browser checked.
- What it does not check: formatting and layout beyond the text (an icon's gap, which words are bold), attribute copy, what a script would change, and where a line break falls inside a line Chromium already showed broken. A control left with only hidden words shows the same text, so it is the in-code check (invariant 5) that refuses it.

Fuzzing with a proper generator (mulberry32) backs this, and is evidence, not proof. The round-7 runs, each a scratch harness outside the repository (C:/Users/arvik/AppData/Local/Temp/byway-fixes/scratch/runner-copy/r7/), on the final code, skip no page whatever the reader makes of it:

Of 27,000 edits, 4,287 changed nothing; placement refused 2,314 with its own reasons (a link or button that would be left empty or nameless, words with no place beside a link the page leaves open); the in-code verifier refused 1 of placement's own writes (a page whose MathML title breaks out); the arbiter refused 22; 20,376 were stored. An independent oracle checked every stored edit: its own Chromium read (JavaScript on, its own character-by-character link reading) and its own placement of the changed lines (a search for occurrences of each changed line's old characters, in any order, such that the person's characters, in the links the old ones showed in, turn the page's characters before into its characters after, everything else equal). None had a character or a link that differs, a gap shown otherwise than the person's lines and the page's separators make it, or a title otherwise; one had a line read again as one line per link after a deletion (the regrouping under Consequences). 16 needed the oracle to place a line out of deck order (content a browser moves out of a table).
- The arbiter's 22 refusals there, by reason: 9 "would show on one line what it showed on separate lines", 7 "shows its link words differently from how they were offered", 5 "would run words together", 1 "would show … there". Each is on a page with one of the reader's known misreads: content in a table outside any cell (15 of them), a button (10), a link wrapped around a table (4), an svg `<title>` left open (3), text in the head (3), a MathML title breakout (2) (a page can have several). Round 6's evidence skipped the pages the reader misreads; its verifier, aligning them, found 17 accepted edits that ran lines together there.
- Chromium, links (oracle-r7-links.mts: the same pipeline and oracle over the round-5 open-link generator: links left open, self-closed, nested and misnested, an `</a>` inside a cell, a caption, an object, a marquee or a list box, deep nesting, name-only anchors), 2 × 1,500 pages: of 9,000 edits, 4,362 were stored, none with a character or link that differs, a gap shown otherwise or a title otherwise; the oracle could not read 1 (an object's fallback text); 3 had a line regrouped after a deletion; the arbiter refused none (the generator leaves tangled lines unchanged; the reader refuses a change to one).
- The verifiers' hand cases of rounds 4 to 6 (their case files, 319 pages, probe-cases-r7.mts), through the real VOICE activity with the runner's Chromium: 224 stored, each confirmed by the independent oracle, and 1 more stored that the oracle cannot read (MathML's automatic italic, which the arbiter undoes as text-transform); 6 refused by the arbiter (the button edge twice, foster parenting three times, the MathML title breakout); 39 refused by the reader, placement or the verifier with their own reasons, many because the case was written against a deck that now offers fewer lines; 6 wrote nothing; 43 only read the deck. The round-6 verifier's activity probes (probe-activity-r7.mts) give the same: every stored page shows the person's lines, the head-text page keeps its emptied heading, and the MathML, foster and button pages are refused by the arbiter.
- The adoption agency's depth (aaa-depth.mts) reads as in rounds 5 and 6: a link open in its block stays open in Chromium from eight blocks on, and the reader flags it tangled from eight; a link a block popped from a `<p>` stays open from nine, and the reader flags it from eight.

Reading and verifying are linear in the page (amortized: the open elements are looked up by name and kind, and no run of text copies them), and so is placement except where it matches a changed block's old and new words: by a table quadratic in that block's words for a line of up to about a thousand words, and past that by the common first and last words plus a Myers edit script whose cost grows with the words changed, capped at 2,000 changed words (past the cap the changed middle is one span and its formatting is not kept). A 24,010-tag page, a 20,000-path svg, a 12,000-word block with a word changed near each end, one block holding 20,000 unclosed `<span>`, `<b>` or `<a>` elements (round 4 ran out of memory there), and 20,000 nested spans emptied each take well under a second alone; the tests bound them at five seconds so a loaded machine does not fail them. The arbiter's marking, placing and comparing are linear too; its cost is Chromium's reads (see Consequences).

**keepsVoice is an exact lock.** The locked deck is computed before the model call.
- A storyboard's voice-over is written back from the work before the write whenever a voice exists, and the step finishes with a note: "The voice-over is locked, so it was kept exactly as it was; this step's change to it was undone." An obedient write is byte-identical and gets no note. If the undone change was the step's only change, a following A/B compare is skipped as "nothing to compare".
- Its on-screen copy is locked exactly when the late VOICE's own reader reads the voice as this storyboard's complete on-screen deck (whatever the values and their layout) and the voice is not the voice-over itself. Then any change to it is refused. A VO script has no `Headline:` line, so it stays unlocked; a VO script that happens to be the whole labelled deck is the voice-over, so it stays unlocked too.
- Options, prose, code diffs and pages are held by exact deck equality; pages also by each link part's address, by position. A page's lock reads its whole deck, so the lines VOICE did not offer (a browser does not show them) are held unchanged too. Visibility (the hidden attribute, inline styles, classes) is not checked, and neither are the spacing and line breaks between a page's lines: a later write that runs two of the person's lines together on screen, by wrapping them in font or label instead of two paragraphs or by dropping the space between two labels, passes the lock, though every line's words are kept. An empty voice is checked.
- With no work before the write, the written artifact must hold exactly the voice. For a page this is practically unsatisfiable (the whole deck would have to equal the handed-in deck); such recipes should place the deck with a VOICE step.
- In canonical C5 every keepsVoice writer runs in the script phase, with the VO script as its voice, so the write-back is the live path. The on-screen lock is reached only by composed recipes with a writer after the late VOICE.

**Typed boundaries (ENG-6).** Every problem with a VOICE answer, including a fault inside the pure copy code, is a question asked again (`AnswerRejected`), quoting how the offered lines or fields it names first read (at most five, 80 characters each), because after a re-ask the web editor's starting text is the person's previous answer. Sending the offered copy back always succeeds. An answer to a writing question with a broken character (half of a surrogate pair, which no store can hold) is asked again in every medium, naming the line, before anything is stored ("Line 3 has a broken character (half of a surrogate pair, not valid Unicode), so it cannot be stored: type that character again, or take it out."); round 6 let the store refuse it, a plain error retried and failing the same way each time. A fault reading the deck in `openCheckpoint` (the page arbiter's own code included), or in a keepsVoice check, is a plain, non-retryable `StepError`, so a paid call is never repeated. Store errors are retried as before, and so are Chromium's reads, as renders are. The claim log runs on prose only; on any other medium the step offers and writes the copy deck.

**Bundling.** parse-entities switches to DOM decoding under the "browser" export condition, so the copy modules (copy.ts, page-copy.ts, page-arbiter.ts, html-tokens.ts) must never be bundled for a browser or the workflow sandbox. Everything here is activity code; the workflow bundle hash is unchanged.

**Parked, not fixed: VOICE-RETRY.** In C5 a failed launch gate re-enters D2 from the ports D2 started with (`RetryStage`), so the copy the person wrote at the first late VOICE is not in the second pass, and the second late VOICE offers model copy without saying so. Its root is the workflow's stage re-entry, not a weak check; fixing it changes the workflow bundle, and ADR-0078 then ends open runs. The owner's options: carry the person's on-screen answer across the retry in the interpreter, or, as an activity-only interim, have `openCheckpoint` name the earlier answer when the current deck differs. A C5 test records today's behaviour.

## Alternatives considered

- **Structured segment ids and a per-segment editor (the review's repair).** Exact by id and fully explicit, but it changes checkpoint and resolution formats, store rows, the CLI and API answer format and the web UI, touches workflow types (ending every open run), and still needs every exactness rule above.
- **Exact checks, with the model still placing page copy.** Smaller, but link coverage stays the model's unverifiable choice, every web VOICE edit costs a call, and in demo mode an edit to a line with inline markup could never succeed.
- **Deterministic placement with heuristics instead of brackets.** No notation, but a heuristic (or a model) decides which words a link covers, or the person is forced to keep words they wanted to change.

## Consequences

**Positive**

- The person's words are written exactly as stated, in every medium, and a later machine write cannot change the locked deck unnoticed. The lock covers the words and, on a page, each link's address; it does not cover visibility, formatting, attribute copy, or the spacing and line breaks between a page's lines (see keepsVoice above).
- On a page, the browser checks every write before it is stored: Chromium must show the written page as the person's edit of what it showed before, so a misread in byway's page reader becomes a question asked again, naming the line, never a silent mis-write.
- No model in VOICE: demo and paid runs agree, and VOICE is free.
- Canonical C5's voice-over is now written back, with a note, instead of passing appended or reordered text.

**Negative**

- Page decks carry a small notation: link words in brackets, literal brackets escaped. The C1 demo deck has none.
- Free-form answers that the model used to map are now asked again, with the exact problem.
- Pages whose attributes hold a quoted `>`, or that contain svg CDATA, iframe, xmp, noembed, noframes, plaintext or literal brackets, are read differently; a question opened before the upgrade may be asked again once.
- A paragraph whose link carries a hook cannot be deleted in VOICE (it can be edited).
- A block of more than about a thousand words rewritten in more than 2,000 words loses the formatting in its changed middle (the words are still written exactly).
- Because the reader builds no tree, it reads a link the page leaves open or nests where browsers end it only outside tables, list boxes, embedded objects, marquees, svg and math, and only under fewer than eight blocks opened inside it. Where that does not hold (see the page tokenizer above), every line from that link to the page's end is offered (where a browser shows it) but cannot be changed in VOICE, and the lock does not cover which of those lines' words are link words (the words themselves are locked).
- The deck splits a line at any tag outside inline formatting, so a block with font, label, ins, del, a button, an image or an svg in it is offered as several lines that a browser shows as one. A removal can regroup lines within one block as browsers show it: a line left with only links side by side is read again as one line per link, and links side by side that a removal joins to the formatting around them are read again as one line, so the lock holds them as the written page reads. The words and links stay exact, and no removal runs two blocks together as the reader reads blocks. The reader reads blocks by the default stylesheet and the hidden attribute; the arbiter reads them as the page's own stylesheets make them, so a line a stylesheet hides is not offered, and a write that shows otherwise than the reader expected is refused. Content in a table outside any cell is offered in the reader's order, though browsers show it before the table.
- Every page VOICE needs the page renderer, and reads the page in Chromium: twice when the question is asked (the page and its marked copy) and three times when an answer that changes it is written (those two, then the written page), each under the render's deadline. Without a renderer a page's VOICE fails plainly. A page whose styles come from the allowlisted hosts is read as they load.
- Where the reader misreads a page, the arbiter refuses edits the person cannot fix by rewording, and the line must be left as it was. Whitespace at the start or end of a button's content does not show in browsers (a button is an inline block), and the reader counts it, so deleting the first or last line inside a button can take the gap that parted its neighbours: `<p>Pay <button type="button"><b>$20</b> <label>now</label></button>Total</p>` with "now" deleted would show "Pay $20Total", and is refused. So are a deletion that runs text into content a browser moves out of a table, and one beside a MathML `<title>` whose content breaks out. Round 6 wrote these. The round-7 runs above count such refusals.
- Lines a browser does not show are not offered, so they cannot be changed in VOICE, even where a script or a reader would show them later: a hidden block, a closed dialog, a closed `<details>` body, an svg or math `<title>`, svg text outside a text element, anything a stylesheet hides. Chromium drops a newline right after `<wbr>` (the CSS segment-break rules) where the deck reads a space, so the line `<p>Hello<wbr>\nworld</p>` ("Hello world" in the deck, "Helloworld" in a browser) is not placed, and not offered.
- A line a style breaks over screen lines (a `display: block` span in a heading) is one line in the deck; the arbiter checks its words and that each gap the person wrote is a gap, not whether a gap is a space or the line break, so where the break falls in such a line is not checked.
- The arbiter reads with JavaScript off, so a noscript element's content shows to it (it is never offered, and stays byte for byte), and CSS text-transform is undone, so a person's capitals are compared as typed.
- An `<a>` without an href is not a link: its words are plain and the lock does not hold them as link words, though a page whose CSS and script make one look and act like a link shows it as one.
- An emptied element browsers end elsewhere than its own end tag (misnested, left open, or one whose start tag ends another, such as a `<p>` inside an open `<p>`) is kept, empty, as is a block whose removal would run two lines together on screen; the page keeps an empty element where a person might have expected it gone.
- On a page with a link left open, that link is never removed, nor is anything holding one end of its reach and not the other. So emptying such a link is refused, and deleting the line that holds its start tag can leave an empty block. Words between two links with no place outside both are refused; a space there is written. So are words after a link the page leaves open at the end of a line, with their own reason ("words cannot be added after the link "there" on this line: the page leaves that link open, so a browser makes the words after it, up to the next link, part of it").
- In an edited line, where an empty icon in the middle of the line has a space on each side, the space after it is lost ("Hello <icon> world" becomes "Hello <icon>world"). So is the gap before an arrow at the end of a link in the middle of the line, even when only words outside the link change. Text glued to a link whose edge space sat before an arrow drops that gap too ("[Order now]!"). At a line's edge, words added outside the formatting that holds the edge space touch an icon beside them (placement above). This is layout only; the words are exact. The verifier checks edge whitespace slot by slot only where no removal merged slots; where one did, the line's words and the line as it shows are still checked.
- An old composed-recipe late answer that left out a field leaves that run's on-screen copy unlocked.
- A new runner dependency: parse-entities 4.0.2 (already in the lockfile).
