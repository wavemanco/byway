## Context

VOICE is the product's core promise: a person writes every reader-facing line (spec §3.2; protocol 01 VOICE step 7, "inserts the human copy exactly"; port rule 6, "no later block writes over voice"). The external review's F07, confirmed at P1 by the verification, showed that the runner did not keep it:

- A page's write-back went to `helper.voice.apply`, and the result was checked only for an unchanged tag skeleton and for each non-empty line appearing somewhere on the page. Deleted text left on the page, a repeated line replaced by other words, swapped lines and new copy between tags all passed. The fallback placement emptied inline links and emphasis. An out-of-range character reference threw a `RangeError`.
- The "unchanged" test squashed whitespace, so moves across lines, merges and a prose paragraph split were dropped silently, and the last block could not be emptied.
- Every other medium fell back to the model whenever its reader could not map an answer, and the options and on-screen readers dropped or shadowed lines the person typed.
- `keepsVoice` held later machine writes only to substring membership (`lostVoiceLines`), and skipped the check for an empty voice. Canonical C5 reaches this: a model that appended to or reordered the voice-over passed.
- The page tokenizer ended a tag at the first `>`, even inside a quoted attribute value.

The common root: the person's copy could be written by something other than an exact, total application of their edit, as long as the result passed a check weaker than the edit.

This record supersedes the whole "VOICE write-back" bullet of [ADR-0073](0073-runner-semantics-where-the-spec-was-open.md), including its keepsVoice sentence. ADR-0073 is not edited. [ADR-0098](0098-recipe-limits-disclosure-and-held-voice.md), merged into this branch in round 12, decides which of the person's words a keepsVoice writer is held to (every held VOICE answer and the latest words); this record decides how it is held (the exact lock below, in place of the line-membership check the two shared before this branch). ADR-0098 is not edited.

## Decision

**Each medium's copy deck is the contract, and no model writes the person's words.** The runner offers the deck, reads the answer with a total reader (every line lands in exactly one place, or the answer is refused with that line named), writes it back deterministically, and checks the written artifact exactly. On a web page the browser has the last word: the runner's own Chromium, reading the page as a visitor sees it (its scripts running, scrolled through, each character judged by its box), decides which lines are offered and must show the written page as the person's edit of the page before, or nothing is stored (the browser arbiter, below). VOICE makes no model call in any medium, so demo and paid runs behave the same and VOICE costs nothing. The `helper.voice.apply` templates and the `voice.apply` id stay, because the prompt ids are in the workflow bundle; they are no longer called.

**Decks.**
- Prose: the Markdown document. Code diffs: the "Why:" paragraph (empty is refused). Media: the voice-over script at the early VOICE; at the late VOICE, `Headline:`, `Tagline:` and one `Shot N:` per shot. Options: `### A` then `Title:`, `Pitch:` and `Rationale:` for each option.
- Labelled decks are read by one total reader: each label once, in the order shown, matched by position (so a storyboard whose shots repeat a number still reads); continuation lines belong to the label above; anything else is refused and named. A voice-over line at the late VOICE is refused.
- Non-web write-backs pass a round trip: the deck read back from the written artifact, laid out by one line-based `layoutOf`, equals the answer laid out the same way. `layoutOf` is never the reader. It normalises only layout (line endings, trailing spaces, every run of blank lines that ends at a label or at either end, however long, a value on the line after its label, label case and spacing) and keeps everything inside a value, blank lines between its lines included. The same `layoutOf` is the "unchanged" test, so a doubled space inside a caption is written. A failed round trip is refused quoting the first line that would differ.
- Web pages: one line ("unit") per run of visible text, in reading order. A run is text with no tag inside it but inline formatting (a, abbr, b, bdi, bdo, cite, code, data, dfn, em, i, kbd, mark, q, s, samp, small, span, strong, sub, sup, time, u, var, wbr). So a block is one line unless a `<br>`, a nested block or any other tag splits it, and that includes the tags of elements browsers show inline: font, label, ins, del, a button, an image, an svg or a form control. `<p>Hello <a href="/s"><svg></svg></a> world</p>` is offered as two lines, "Hello" and "world", and `<p>Hello <font color="red">world</font>!</p>` as three (the words stay exact). The VOICE prompt and the line-count refusal say "one line per block of text", which is the common case only: a block that such a tag splits is offered, and counted, as the several lines the person is shown. A block of links side by side (each an `<a>` with an href) gives one line per link. Head content is not offered except `<title>`; text that is not whitespace ends the head, as browsers end it, so text written in the head after the title is offered; it continues the body's first screen line, as browsers show it. The content of a hidden element that browsers show inline (a span, a font, a label or the like with the hidden attribute) is not offered, so the person's words never go into text a browser hides inside a line it shows: `<p>Sale<span hidden> ends</span> today</p>` is offered as "Sale today", and "Sale starts today" is written `<p>Sale<span hidden> ends</span> starts today</p>`. A canvas is read the same way: its content is the fallback only a browser without scripting shows (a visitor sees the canvas), so it is not offered, as noscript content is not (round 8 offered it). Only lines a visitor sees are offered (the browser arbiter's offer rule, below): a line the runner's Chromium, reading the page as a visitor sees it, does not show in one piece with exactly its characters is not offered, and stays byte for byte. So a hidden block, a closed dialog, the body of a closed `<details>`, the text of an svg or math `<title>` (a tooltip), text a stylesheet does not lay out (`display: none`, `visibility: hidden`, a block shown only at another screen size), and a line the reader reads where a browser shows nothing (such as the lines an svg `<title>` left open over a paragraph's end hides) are not offered; nor is a line whose words a browser shows run together where the line has a space (flex or grid items with no gap between them, also where one of them keeps moving, as a price that pulses beside "From", judged where both stand at the read's last instant and at every point of an endless animation's cycle, below; round 11 offered that line; also flex items set top to bottom in a vertical writing mode or in a label a transform turns, judged along the line their text runs along, below; a negative `word-spacing` that brings two words within a tenth of the font size, as `-0.22em` does, 0.47 px apart at 16 px, which a visitor reads as one word; `Hello<wbr>` before a newline) or in another order (a float, a reversed flex row, `order`, `<bdo>`; a right-to-left page is read in its visitor's order, so its native numbers, a phone number's groups, a Latin name and left-to-right boxes in a right-to-left row are offered: round 11 read Arabic-Indic digits as right-to-left letters and left out 6 of the 23 lines of the round-11 verifier's Arabic café page), or with other words between its ends (a script rewrote part of it, as a counter that counts up from the "0" in the source). Nor is a line holding any text a visitor does not see though the line's other words show: text a style hides from sight (a screen-reader-only class; opacity, filter opacity(), a clear text fill or a colour almost clear that leave it less than 0.05 of ink; font size 0; a character whose middle a box or a clip-path cuts off, such as a sliver of a row a box of fixed height cuts; cut off by an ellipsis or a line clamp; moved off the page; as the arbiter defines it below), or a part a style does not lay out. Its words are not all seen, so the person's words never go into such text. `<p>Rated 4.5<span class="sr-only"> out of 5</span> stars</p>`, a Bootstrap button `Send message <span class="visually-hidden">to Saltbox</span>` and a card link `Read more<span class="visually-hidden"> about quiet interfaces</span>` are not offered, and stay byte for byte, also where the screen-reader-only class comes from a stylesheet a script makes, as Tailwind's browser build makes it (round 8 offered them and wrote "Rated 5 by every single baker" as `<p>Rated <span class="sr-only">5</span> by every single baker</p>`, whose "5" no sighted visitor sees; round 9 read the page with JavaScript off, so the script-made stylesheet never applied, and wrote it again). A line a visitor sees in one piece is offered even where the page's own boxes part characters the source runs together: `<blockquote>“Worth every penny.”<cite style="display:block">— Maya R.</cite></blockquote>` is offered as "“Worth every penny.”— Maya R." (round 9 left it out), tag chips that are inline blocks with padding as "Tags: Newtech", a menu's dish and price that are flex items as "Cacio e pepe£13", and a paragraph whose first letter is a floated drop cap as its words. A line a script reveals as the visitor scrolls (a section that waits at opacity 0, or moved aside by a transform, for an IntersectionObserver or a scroll listener) is read revealed, so it is offered (round 9 left out 44 of the 62 lines of such a page; round 10 still left out the sections AOS slides or turns into view), and so are a carousel's slides and a ticker's text, where the read's instants show them. A script that splits a heading into letters, an element each, no longer keeps the page's lines from being placed (round 10 placed no line of such a page); the heading itself is offered where its letters read as its line (a no-break space the script puts between its words is a character, so such a heading is named as showing other words). The prompt names every line it does not offer, quoting it, with why ("These lines of the page are not offered, because a browser does not show them as one line here, and stay as they are: part of it is hidden (from sight, for screen readers, or not shown at all) or cut off: "Rated 4.5 out of 5 stars"; …"; the reasons are listed under the arbiter, below). Round 9 named none ("Text a browser does not show as one line here (hidden, out of sight, a tooltip, or laid out differently) is not offered, and stays as it is."). Round 6 offered hidden blocks, closed dialogs, closed `<details>` bodies and svg titles as lines.

**The page tokenizer** reads a page as browsers tokenize it where that decides what is copy, without building the tree: WHATWG tag ends (quotes delimit attribute values only; input ending inside a tag is opaque); comment forms; raw text for script, style, noscript, template, iframe, xmp, noembed, noframes and textarea (textarea's default value is not offered; `/>` on these is ignored in HTML content); a script's `<!--` escapes, so `</script>` inside an escaped `<script` string does not end it; plaintext opaque to the end; `<title>` as RCDATA, offered; inside `<svg>` or `<math>`, a CDATA section is opaque. The self-closing flag is WHATWG's: a `/` read right before `>` outside any value (so `href=/shop/` does not set it). The reader honours it where browsers do (void elements, `<svg>` and `<math>`, and everything inside them) and ignores it on other HTML elements, so `<a href=x/>` and `<span/>` open an element. It builds no tree, but it keeps the stack of open elements as browsers keep it where that decides where an element ends. End tags are matched by WHATWG's rules: a block's end tag closes it and everything open inside it unless a scope boundary (a table, a cell, a caption, an object, a marquee, a template or a list box) lies between; any heading's end tag closes the open heading; `</p>` with no p open makes an empty p and `</br>` is a `<br>`; a formatting end tag (a, b, em, font and the rest) closes its element, and when a block is open inside it, browsers' adoption agency closes the formatting and leaves the block open, as the reader does; any other end tag is ignored when a block or control is open inside its element. Start tags end what browsers end for them: a block ends an open p, an li an open li, a dd or dt an open dd or dt, a heading a heading that is the innermost element, and body content an unclosed head (so the body of a page that omits `</head>` is now offered; it was read as head content before). Browsers ignore a table part outside a table, an `<html>` start tag after any other tag or text, a `<body>` start tag once the body has begun (explicitly, or implicitly with text or a start tag that does not belong in the head), a `<head>` once the head or the body has begun, and a form inside a form; the reader opens no element for them, so none of them breaks a line. (Round 6 read a `<body>` after an implied body as a block break, so deleting a heading between head text and the body's text ran the two together: `…Welcome</head><body><h2>Sale</h2>Order today` showed "WelcomeOrder today". The emptied heading is now kept, and Chromium shows "Welcome" and "Order today" on lines of their own.) There is no reconstruction of formatting elements, except where a link ends, and no foster parenting: content written in a table outside any cell (in a table, a row group, a row or a column group; a row opened inside a cell ends the cell in browsers, and the reader keeps that row innermost) is read where it stands, while browsers move it before the table, so its lines can be offered in another order than a browser shows them. An element read there, or a `<br>`, is never removed, nor is anything holding one: `<div>late:<table><tr><span><section>Gone</section></span>After<td>Cell</td></tr></table></div>` with "Gone" deleted keeps the emptied span and section, which browsers show before the table, so "late:" and "After" stay on lines of their own. Foster parenting is not modelled beyond that: removing a block that stands between text and a table holding fostered content can run that text into the fostered content in a browser (`<div>Lead<p>Middle</p><table><tr><font>F</font><td>Cell</td>…` with "Middle" deleted shows "LeadF"); the reader and the in-code verifier do not see it, and the browser arbiter refuses it. Only the html `<title>` is the page's title: an svg or math `<title>` is an element like any other there (a self-closed one opens nothing, and the svg's end closes one left open), and its text, a tooltip, is not counted as text a browser shows; Chromium does not show it, so it is not offered. Two foreign-content misreads remain in the reader, and the arbiter turns each into a refusal or a line not offered: a MathML `<title>` whose content breaks out (a `<b>`, a `<span>`, a `<p>` inside it) is read as hidden though browsers show that content, and an svg `<title>` left open over an HTML end tag such as `</p>` is read as closed there, though browsers keep it open and show nothing after it. A start tag named image is read as `<img>`, as browsers read it. A link is an `<a>` with an href; an `<a>` without one is a placeholder (browsers show its words plain), so its words are plain in the deck, the prompt and the lock, also when the page leaves it open, as in `<h2><a name="top"/>Welcome</h2>`; its tags still end the links around it. A link is read where browsers end it, at the next `<a ...>` or `</a>` tag: a link the page leaves open (an unclosed `<a>`, `<a href=x/>`, or one a misnested closing tag pops) reaches into the following blocks, as browsers open it again there, and an `<a>` inside another ends the first. This was checked against Chromium (below). Where browsers may stop, skip or resume the link and byway cannot tell without building the tree, that link is "tangled", and every line from it to the page's end is offered (where a browser shows it) but cannot be changed: when its reach holds a table, a list box, an embedded object, a marquee, svg or math; when one of those, opened inside a link the page closes, is still open at its `</a>` (browsers ignore an `</a>` inside a cell, a caption, an object, a marquee or a list box the link holds, so the reader does not match it and reads that link as left open); and when eight or more blocks opened inside the link are open where it ends, because the adoption agency gives up after eight turns. Checked against Chromium, that count is exact for a link open in its block and one block early (tangled where Chromium still ends the link) for a link a block's start has popped from a `<p>`. The VOICE prompt names those lines, and a change to one is refused, naming it ("Line 4 cannot be changed in this step: a link on the page (to /x) is left open or holds another link, around a table, a list box, an svg or other markup where byway cannot tell which words a browser shows as that link's words, so byway cannot write this line exactly. Leave line 4 as it was offered."). An element is removed only when it is balanced: closed by its own end tag while it was the innermost open element, with nothing inside it closed out of order, closed implicitly by an end tag, or ignored, and its start tag ended nothing (browsers' implied end of an open p, li or heading). So no removal leaves an end tag browsers would ignore, takes the start of a block browsers end later, or lets an element its start tag ended run on. Nor is an element removed that holds one end of a left-open link's reach and not the other; an `<a>` written around another goes whole, from its start tag to its own closing tag. On the C1 demo page its tokens are identical to the old tokenizer's. Character references are decoded by parse-entities with browser rules (total; U+FFFD for references out of range). Whitespace means HTML whitespace; a no-break space is text. Changed text is written with `&`, `<` and `>` escaped; unchanged text keeps its bytes.

**Not offered on a page** (each stays byte for byte): attribute copy (alt, aria-label, title, placeholder, meta description), script-generated copy, CSS content, textarea default text, svg CDATA text, xmp and plaintext content, noscript content, a canvas's fallback, `<pre>` content, the content of a hidden element browsers show inline, and every line a visitor does not see in one piece with exactly its characters, so every line holding text a visitor does not see (the browser arbiter's offer rule, below; the prompt names each). An emptied element is kept, not removed, when it holds a script, a style, a noscript, a template, other raw text or a comment, so those bytes stay too (round 6 removed them with it).

**One bracket notation on every page line.** Link words inside a line are shown in `[brackets]`; a literal bracket, or a backslash before one, is shown escaped with a backslash on every line. A line with links keeps one pair per link, in order; `[]` removes that link. A line that is exactly one link's words takes plain words or one pair around the whole line. A line with no link refuses an unescaped bracket and says how to escape it. Link words are the person's decision: the VOICE prompt names where every link goes ("line 2 "Terms of service" goes to /terms"; at most 40, addresses cut to 60 characters), so there is no relabel guard. This suffix is added by `openCheckpoint` from the work itself, once per checkpoint, re-asks included; it lives there until the next workflow change.

**Edit semantics.** The answer is a positional edit: one line per unit; an empty line deletes that unit's text, the last one included; blank lines past the end are nothing. A changed line is read with its whitespace collapsed, and a space the person types at either of its edges (with its brackets taken out, so also the space beside a link removed with `[]` at the line's start or end) is kept as a space at that edge (placement, below). So is a no-break space (or another space that is not HTML whitespace) the line had at an edge and the person took out: an editor shows it as any space, and round 11 glued such a line to the text beside it ("here:now!", "NameIntro"). A line whose words and links are as offered is unchanged, whatever spaces it has at its edges. A question opened by an older engine is aligned by words only (brackets and backslashes dropped). When a changed line no longer lines up with the current deck, it is refused on the first offer and read against the current deck on a re-ask. "First offer" means exactly: the answered checkpoint's starting text equals the text the step first offered; a missing checkpoint counts as a first offer. A changed page line holding a null character (U+0000) is refused, because browsers drop it from a page's text.

**Placement and verification.** Placement is deterministic: changed text goes into the line's text slots, aligned to the old words so formatting follows whole words or pieces (a documented, tested rule; formatting coverage is not verified). No word crosses a link's edge: a link part's words go only into its link, words outside brackets only outside every link (never into an image, svg or icon link that held no words), and a whole-link line's words all into its link. Words added before a line's first kept word, or after its last, go beside it: into the shallowest slot reachable from it across only opening (or closing) formatting, so an empty icon between stays where it was. Text glued to that word (no space between it and the word: punctuation, a suffix) goes into the word's own slot instead, so it stays in the word's box: a menu's price that a flex row shows apart from its dish (`<span>£13</span>` with "£13!" is written `<span>£13!</span>`), a tag chip, a price written `$9/loaf`; it is never put into a link the brackets keep it out of (`Read [more].` keeps the stop outside the link). Round 11 put it in the shallowest slot, outside the word's element, where a flex row or an inline block shows it apart, and the arbiter refused every such answer (31 of about 311 such edits on the round-11 verifier's realistic pages), which no rewording could avoid. The whitespace before a line's first word and after its last stays in the slot that held it, at the same end, wherever the new words go (the new words carry their own spaces), so the gap beside an empty icon, an image link, or an arrow at a link's end stays where it was, except where words are added at that edge of the line and the whitespace sits inside formatting the new words go outside of: then the whitespace parts the new words from the old ones, and the new words touch the icon (`<p><svg …></svg><b> Hello</b> world</p>` with "Big Hello world" is written `<svg …></svg>Big <b> Hello</b> world`; layout only, the words are exact). The one exception: a piece that would then show as a space where the person's line has none is dropped. That happens when the person glues text to a word whose edge space sits inside a link or formatting: a pretty-printed `<a href="/shop">\n    our shop\n  </a>` with "Visit [our shop]." is written `<a href="/shop">our shop</a>.`, and `[Order now]!` after `<a>Order now <i class="arrow"></i></a>` is written `Order now<i class="arrow"></i></a>!`, so the arrow loses its gap, because the deck cannot show the arrow; where the arrow takes up width (an inline block, an icon), a browser shows the stop apart from the link's words, beyond the arrow, and the arbiter refuses the write, saying a browser would part words that your lines run together at the edge of a box on the same row, and quoting "Ready? Order now / !" (the round-12 verifier found this record calling such a write stored). With a space typed after the link (`[Order now] today`) the gap stays. The edge whitespace also parts the line from text beside it on the same screen line (in the same block as browsers show it). Where new words went past the slot that held it (into a shallower slot beyond formatting), or a piece was dropped, and text a browser shows stands beside the line in its block, a space goes at the line's new edge, beside the new words: `<p><del>Was <b>$20 </b></del>Now $15</p>` with "Was $20 only" is written `<del>Was <b>$20 </b> only </del>Now $15`, and `<p><label>Email</label><a href="/help"> help</a> is here</p>` with "Get [help] is here" is written `<label>Email</label> Get <a href="/help"> help</a> is here` (round 3 to 5 wrote "Was $20 onlyNow $15" and "EmailGet help is here"). With nothing beside the line in its block, nothing is added (`<p>Read <a href="/x">more </a></p>` with "Read [more]." is written `Read <a href="/x">more</a>.`). A space the person typed at a changed line's edge goes there by the same rule, where the line's own edge whitespace is not still at that edge: `<p><b>Hello</b><font>world</font></p>` with " there" is written `<font> there</font>`, and `<p><b>Sale,</b><font><a href="/d">$20</a> menu</font></p>` with "[] menu" is written `<b>Sale,</b><font> menu</font>` (round 7 dropped these spaces, so the words ran together: "Hellothere", "Sale,menu"). Whitespace already beside the line is not weighed, so where some stands there a space more is written, which shows as one (the reader cannot always tell whether whitespace shows, as at a button's edge). At the edge of a button's content a space never shows (a button lays its content out on its own), so a typed space at the start or end of a line that starts or ends a button's content is not written there; where the button touches the text beside it with no whitespace between, the edit is refused, naming the line ("Line 2: a space at the end of this line would be inside a button, where browsers do not show it, so it cannot part the line from the text after the button; leave the space out."), so the space is never dropped unsaid. A gap between two words that stand, one for one, where two words stood side by side in the line before keeps the page's own whitespace bytes there where they lay in one run of text. The words stand one for one where the person kept them (matched as placement aligns words), and where a run of changed words between two kept ones (or a line's edge) is as long as the run it replaced, word for word in order. So a `white-space: pre`, `pre-wrap` or `pre-line` style keeps an address's, opening hours' or poem's line breaks where a word changed in place of another, beside the break or not: `<address style="white-space:pre-line">Crumb &amp; Co.\n12 Baker Street\nLondon NW1 6XE</address>` with "NW2", "14", "Road" or "Leeds" is written with both breaks, and opening hours with "7pm", "Saturday" and "5pm" with theirs (round 9 wrote each gap as one space and put the address on one line; round 11 kept the bytes only between two words the person kept, so it refused "14", "Leeds" and "7pm" and stored "Road" with the address on one row). So does a gap between two characters the person kept side by side, with whitespace between them before as now, matched by an edit script of the line's characters, as the arbiter matches them and holds such a pair to the separator it had: two words glued beside a kept break (`$29\nFrom\nCall late` with "$29From Call late" keeps the break before "Call", an address's "BakerStreet" the break after it) or a word split beside one (round 12's first fix wrote one space there, shown on one row, and the arbiter refused it as "on one line what it showed on separate lines"). Placement keeps them only where the in-code verifier, matching the line's words by its own edit script, sees the same words standing there (below); where it matches a repeated word otherwise, every gap of that line is the person's single space (`open\nopen Sign today` with "today! open Sign today" is written on one row; round 12's first fix kept the break after "today!", and the verifier, reading the kept "open" as the first one, refused the write as "Line 2 must read exactly …", which no rewording explained). Every other gap between words (beside a word the person added, or where they deleted one, or whitespace that spans formatting) is the person's single space: where the old gap lay within one part of the line (outside links, or one link), it goes into the first slot of that gap; at a link's edge, it goes into the part the person typed it in. So in an edited line, where an empty icon in the middle of the line has a space on each side, the space after it is lost ("Hello <icon> world" becomes "Hello <icon>world"); a space on one side only stays on that side, and where the words on both sides of the icon are replaced, the new words can all go before it. The gap before an arrow at the end of a link in the middle of a line is lost whenever the line is edited, even when only words outside the link change: `Ready? <a>Order now <i class="arrow"></i></a> and save.` with "Set? [Order now] and save." becomes `Order now<i class="arrow"></i></a> and save.`. This is layout only; the words are exact. Removal is conservative: an emptied inline element or text block (p, h1–h6, li, blockquote, figcaption), balanced and outside svg and math, is removed unless it holds an embedded element, a script, a style, a noscript, a template, other raw text or a comment, or a table's tag (a table, a cell, a row or another part, start or end tag), carries a hook (id, for, name, role, data-*, or aria-* other than aria-label), or browsers move it, or an element in it, out of a table (above). (Round 7 removed an emptied `<sub>` holding a `<td>`, which ends the cell around it in browsers, so the written page had a cell fewer; the arbiter refused it. The empty `<sub>` is now kept and the deletion written.) No removal may join two runs of text, neither two runs of the deck nor two blocks as the reader reads browsers' blocks, or move where browsers end a link (see the page tokenizer above); where the reader misreads the blocks (foster parenting, a MathML title breakout), the browser arbiter refuses what the reader let through. Blocks are read by the default stylesheet: text on either side of a block's start tag, of the end tag that closes a block, or of a `<br>` shows on separate lines; every other element shows inline (font, label, ins, del, an image, an svg, a button, a control, a custom element) or not at all (script; an element with the hidden attribute, a closed dialog or a datalist; and the text of an svg or math `<title>` while it is open), whose text and tags are not counted. So `<div><font>Intro<p>Spring sale</p></font>Order today</div>` with the middle line deleted keeps an empty `<p></p>`: removing it would show "IntroOrder today" on one line. Both are weighed by union-find over all removals together, and a deleted line takes the `<br>` run that ends it under the same rule. The whitespace placement put inside an element it then removes (a line's edge space, or a space between two words) is written where the element was, so `<p>Hello <span>world </span><i class="arrow"></i></p>` with "Hello" keeps the gap before the arrow. A deleted line's edge whitespace inside an element the edit removes is written where the element was too, when text a browser shows stands on both sides of the element in one block, as the page was, and only whitespace a browser showed (a hidden block's never showed, so it goes with the block; round 6 wrote it there, and its own verifier refused the write); elsewhere it would sit at a block's edge, where it shows nothing, and it goes with the element. So `<p>Price: <del>$20</del><span> now </span><ins>$15</ins></p>` with "now" deleted is written `<p>Price: <del>$20</del>  <ins>$15</ins></p>`, which shows "Price: $20 $15" (round 5 wrote "Price: $20$15"). A link or button that would be left without words a browser shows, or nameless, is refused, naming its hook, and saying so when it holds words a browser hides, so a line whose link carries a hook can be edited but not deleted. Hidden words (a hidden span) name nothing, and they are never dropped, so a control left with only hidden words is refused, not removed (round 6 counted them as its words and wrote a button that showed empty, with no name). "Words a browser shows" here are the reader's, which reads no stylesheet: words a style hides from sight (a screen-reader-only span) count, and they name the control for a screen reader, so a control whose seen words are a line of their own and whose other words are hidden from sight can be left showing no words: `<button type="submit"><font>Send</font><span class="visually-hidden">your order</span></button>` with "Send" deleted is written with the empty `<font></font>` and the hidden span kept, a button a sighted visitor sees empty and a screen reader names "your order". The arbiter lets it through, since the page then shows exactly the person's lines. An `<a>` without an href counts here only when a role, a tabindex or an `on…` handler makes it a control; a placeholder such as `<a name="faq">FAQ</a>` may be left empty. One that keeps an image or icon is named by its own aria-label, aria-labelledby or title, or by an image's non-empty alt or an element's own label inside it (an empty alt is decoration). Placement returns its removals as a witness. The verifier shares the reader, the removability rule, the `<br>`-run rule and the rule for a deleted line's whitespace where a removed element was with placement, and nothing else. It refuses a changed line in a tangled link's reach, then checks six invariants: (1) each witnessed removal is allowed, and the markup is the page before less exactly those removals, token for token; (2) and (3) unchanged text keeps its bytes and a deleted line keeps only its edge whitespace, run by run, and where an element was removed the written text is exactly what that shared rule leaves there; (4) each changed line reads exactly as written, both by its words (each slot's text less the edge whitespace it held; a gap other than one space only where the line before had those bytes between the same two characters, or between the two words that stand, one for one, where these two do, matched by the verifier's own edit script of the line's words, Myers's, not placement's table) and as it shows (all of its text, edge whitespace included, with HTML whitespace collapsed, so no space shows where the person wrote none), and each link part reads exactly its bracketed words; every slot that held the line's edge whitespace still holds it at the same end, across all of the line's segments, unless that piece would have shown between two characters (then it must be gone); (5) no link or button whose shown words were in a changed line is left without words a browser shows, unless something names it (one that held no words, such as an image link sharing a run with a changed line, had no name for the edit to take); (6) read fresh, the written page's runs hold exactly the expected words, in order, and the same words in the same links with the same addresses, so a word that crossed a link's edge is refused however it got there; and its blocks, read as browsers show them (end tags browsers ignore break nothing) with HTML whitespace collapsed, are the page before with the person's lines in place, each changed or deleted line keeping the edge whitespace it had, so the page's own separators between lines stay, and a changed line with a space where the person typed one at its edge. Two lines a browser showed apart, on lines of their own or as words on one line, that now run together, a space where none showed, and a line it now breaks are refused however that came about ("The page, read again, runs lines together that a browser showed apart: it shows "IntroOrder today" as one line."; "The page, read again, runs words together that a browser showed apart: it shows "Was $20 onlyNow $15"."). Round 5 compared blocks with all whitespace removed, so it saw lines on separate screen lines run together but not two lines on one screen line losing the space between them. It is independent of placement's alignment (it matches words by its own edit script, and shares with placement only the rule that a changed run as long as the run it replaced stands for it word for word) and of its choices among removals, not of the reader: a page the reader misreads can pass it, which is why the browser has the last word.

**The browser arbiter.** The reader is a model of how browsers build and show a page, and placement and the in-code verifier both depend on it, so a misread there is a write the verifier cannot see (round 6's verifier found that about 440 of 1,500 generated pages read differently from Chromium). So every page VOICE asks the browser itself, reading the page as a visitor sees it, and fails closed (page-arbiter.ts; the read is pages.ts `shownText`):
- Which read decides what. The deck (which lines a page has, their words and their links) is the page reader's static read of the markup, which runs no script: script-made copy, noscript content and a canvas's fallback are never deck lines. Everything about what a visitor sees is the visitor read's, below: whether each character is shown, hidden from sight or not laid out; how each pair of neighbouring shown characters sits; which link each shown character is in; the title. No read runs with JavaScript off. (Rounds 7 to 9 read the page with JavaScript off and judged gaps by innerText, which is not what a visitor sees: innerText puts a line break at a flex, grid or float item's edge where a visitor sees glued words, so round 9 stored "Sign intoday"; a stylesheet a script makes, as Tailwind's browser build makes it, never applied, so screen-reader-only text read as shown and took the person's words; and sections waiting at opacity 0 for a scroll-reveal script read as hidden, so most lines of such a page were not offered.)
- What it reads with: the runner's own Chromium, the one the renderer starts by its one stated launch (ADR-0084: no secrets in its environment, its OS sandbox as `RENDERER_OS_SANDBOX` says, which this record does not change), with JavaScript on, as the critic's renders load a page: under the render's allowlist (held on every redirect hop, with the byte cap per response), request filter and deadline, on the wide screen (1440 × 900, reduced motion), reading only the page's first document. A read never judges a page without a file it loads: every file the page fetches from an admitted host (a stylesheet, a script such as Tailwind's browser build, a font, an image) is counted while it is on its way and waited for before the read looks at the page (once it has loaded, before each sample, before the end), and the first that does not arrive whole (the connection failed or took too long, its body was cut off at the byte cap, the host answered with a server error or a 408 or 429, it redirects where byway does not load from or more often than byway follows) stops the read. The page is then read once more, in a fresh context; if a file fails again, the read is a plain StepError saying which ("The page's text could not be read as a visitor sees it: it loads https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4, which could not be fetched (the connection failed), also when byway read the page again, and a page read without a file it loads is not the page a visitor sees."). A file that is not there (a 404) is what a visitor's browser gets too, so the page is read without it. (Round 12 answered a failed fetch with a 404 and read on, so under load a Tailwind page was read unstyled at the write and its answer refused as read with another number of lines; a read that missed the stylesheet at both steps would have judged an unstyled page.) A later navigation the request filter sees (a meta refresh to an address, a script setting `location`) gets No Content; a move within the document (to a fragment, `history.pushState`) keeps it (round 8 called a refresh to `#top` navigating away and failed the step); a document that takes its place without a request the filter sees (a meta refresh to about:blank or about:srcdoc) is a plain StepError ("The page navigates away as it loads (a meta refresh, for example), so the text it shows could not be read."; round 7 let the read throw a raw error, which was retried): the read's functions live in the first document, installed only where a script run before the page's own found the page's address. A question's two reads share one deadline of 40 s, because openCheckpoint runs under the workflow's `quick` proxy (one minute to close, no heartbeat): a page Chromium cannot read in that time is a StepError, not a timed-out activity Temporal retries (round 7 gave each read 30 s). A write's reads each have the render's 30 s; finishHumanStep heartbeats under the 15-minute `model` proxy. A page that does not load in time, a script that loops, and a renderer that fails while it reads (a Playwright protocol error, a page that crashes) are a plain StepError that is not retried, as a render's are ("The page's text could not be read: the page renderer failed while reading it (Target crashed)."; round 8 let a raw Playwright error be retried). A page nesting thousands of inline elements left open, which crashed the JavaScript-off read of round 9, is read in one call (5,000 and 20,000 are tested).
- How it reads (the visitor read). The page's scripts run under a stopped clock set to one instant (noon UTC on 1 January 2026) that only the read moves, the same way on every read, with `Math.random` seeded, animation frames run on that clock twenty times a second, and every IntersectionObserver told at once that each element it watches is in view (a visitor scrolls to every part of the page): a page reads the same each time, so a clock, a countdown, a counter, a slideshow and a random pick read the same before and after a write. Once the page has loaded, the line marks of a marked copy (below) are taken out of its text, its web fonts and images are loaded (lazy ones too), and the clock runs 1.5 s. The page is then scrolled from the top in steps of 720 px (longer on a page taller than 21,600 px, so there are at most 30), to its end, and back to the top, where the clock runs on in the same steps: at each step a scroll event is dispatched, the clock runs 0.2 s and the page is sampled, so every page is sampled at the same 33 instants, 1.5 s to 7.9 s after it loaded, however long it is. A sample takes every animation and transition to its end and holds an endless one at the next of eight points of its cycle (round 10 stopped it). Then, if the document changed since the last sample (a script's change, which a mutation observer sees) or an animation runs, it measures each text node a style shows (visible, with an ink of at least 0.05: the alpha of its fill colour, or of a stroke, times its opacity counting `filter: opacity()`; an svg text's by its fill and fill-opacity, or its stroke), unless the node was measured with its present text where it is now (its box and what clips it); else it measures nothing (a page with 20,000 text nodes measured again at each sample ran past the read's deadline), so text a fixed header holds keeps the place it was first measured at. A node keeps the measurement where most of its characters are seen, then one taken while it was on the screen, then the later one. So a section a script reveals as the visitor scrolls is read revealed, whether it waited at opacity 0 or moved aside by a transform (AOS's slides and flips; round 10 measured such a section where it first stood, off the page or turned, and did not offer six of the seventeen body lines of the round-10 verifier's AOS page), and so are a carousel's slides that move or fade, and a ticker, wherever the read's instants show them, even when the script hides them again on the way back. Whether a node is laid out at all is read at the end, so a slide a script hides by switching its display is read as not shown at all unless it shows at the read's last instant. A node whose text a script changed after its last measurement is measured at the end, and so is a node shown at the end that moved since its measurement (an endless pulse, a tween that settled at a later sample, a slide moved on), so that how its characters sit beside their neighbours is judged where it stands then (below). The last sample holds every endless animation at the first of its eight points (the start of its cycle, the 0% keyframe of one that runs forwards; every page is sampled 33 times, so on every page); then each endless animation (a CSS or Web Animations one) is held at each of the other seven points in turn, and each node shown at the read's last instant that such an animation can move (one inside an element it animates by its transform, opacity or another property that moves only that element's own boxes; every such node where one animates a property that moves other boxes, as a width or a margin) is measured again wherever it stands at that point (round 12 judged such a node at the first point only, below). A motion a script draws itself (a GSAP timeline that repeats, a setInterval) is not such an animation: it is seen at the read's last instant only. Playwright's own animation frames made a GSAP page's read take 8 to 12 s; at twenty frames a second it takes about 0.5 s (Consequences).

A run of characters with no glyph (a no-break or other space that is not HTML whitespace, a zero-width or format character) takes the separator of the visible characters on either side of it wherever those stand glued: a visitor sees them glued, whatever the run's own boxes say (round 11 measured the separators to such a character only, so a no-break space standing elsewhere could keep two glued neighbours apart in the read: the round-11 verifier's generator stored "dcCall"). A wrap changes none of these, so a longer line that makes the text after it reflow changes no separator, except where a word is broken over rows. The read also notes which of its line breaks stand between two characters on one row (apart across a box's edge on the same row, as a flex item's or a table cell's), only to say so when a write is refused, and marks where text hidden from sight stands among the shown characters, lists that text run by run with its link, marks where text that is not laid out stands (only to say why a line is not offered), and lists the text a stylesheet adds (the strings of a `::before`'s or `::after`'s `content`) on each element that shows it with none of the page's own text, such as an empty element or an icon, where a style lets it show.

**keepsVoice is an exact lock.** The locked deck is computed before the model call.
- The person's words it holds are every VOICE answer held on the run's path and the latest words (ADR-0098's held voice, merged into this branch in round 12: held-voice.ts `keptVoice`), each passed on its own. The deck is held whenever any of them exists. A storyboard's on-screen copy is locked when one of them is its on-screen deck: joined into one text, as ADR-0098 passes them to the line-membership check this record replaces, the voice-over script held beside the on-screen answer would keep the joined text from reading as an on-screen deck and leave the on-screen words open. With no work before the write, the latest of them is what the work must hold.
- A storyboard's voice-over is written back from the work before the write whenever a voice exists, and the step finishes with a note: "The voice-over is locked, so it was kept exactly as it was; this step's change to it was undone." An obedient write is byte-identical and gets no note. If the undone change was the step's only change, a following A/B compare is skipped as "nothing to compare".
- Its on-screen copy is locked exactly when the late VOICE's own reader reads one of those answers as this storyboard's complete on-screen deck (whatever the values and their layout) and that answer is not the voice-over itself. Then any change to it is refused. A VO script has no `Headline:` line, so it stays unlocked; a VO script that happens to be the whole labelled deck is the voice-over, so it stays unlocked too.
- Options, prose, code diffs and pages are held by exact deck equality; pages also by each link part's address, by position. A page's lock reads its whole deck, so the lines VOICE did not offer (a browser does not show them) are held unchanged too. Visibility (the hidden attribute, inline styles, classes) is not checked, and neither are the spacing and line breaks between a page's lines: a later write that runs two of the person's lines together on screen, by wrapping them in font or label instead of two paragraphs or by dropping the space between two labels, passes the lock, though every line's words are kept. An empty voice is checked.
- With no work before the write, the written artifact must hold exactly the voice. For a page this is practically unsatisfiable (the whole deck would have to equal the handed-in deck); such recipes should place the deck with a VOICE step.
- In canonical C5 every keepsVoice writer runs in the script phase, with the VO script as its voice, so the write-back is the live path. The on-screen lock is reached only by composed recipes with a writer after the late VOICE.

**Typed boundaries (ENG-6).** Every problem with a VOICE answer, including a fault inside the pure copy code, is a question asked again (`AnswerRejected`), quoting how the offered lines or fields it names first read (at most five, 80 characters each), because after a re-ask the web editor's starting text is the person's previous answer. Sending the offered copy back always succeeds. An answer to a writing question with a broken character (half of a surrogate pair, which no store can hold) is asked again in every medium, naming the line, before anything is stored ("Line 3 has a broken character (half of a surrogate pair, not valid Unicode), so it cannot be stored: type that character again, or take it out."); round 6 let the store refuse it, a plain error retried and failing the same way each time. A fault reading the deck in `openCheckpoint` (the page arbiter's own code included), or in a keepsVoice check, is a plain, non-retryable `StepError`, so a paid call is never repeated. Store errors are retried as before. Chromium's reads fail as renders do: a page that does not load in time, a file it loads from an admitted host that does not arrive whole in two reads, or a renderer that fails while it reads, is a plain StepError, not retried (round 8 let a raw Playwright error be retried, as renders then were). The claim log runs on prose only; on any other medium the step offers and writes the copy deck.

**Bundling.** parse-entities switches to DOM decoding under the "browser" export condition, so the copy modules (copy.ts, page-copy.ts, page-arbiter.ts, html-tokens.ts) must never be bundled for a browser or the workflow sandbox. Everything here is activity code; the workflow bundle hash is unchanged.

**Parked, not fixed: VOICE-RETRY.** In C5 a failed launch gate re-enters D2 from the ports D2 started with (`RetryStage`), so the copy the person wrote at the first late VOICE is not in the second pass, and the second late VOICE offers model copy without saying so. Its root is the workflow's stage re-entry, not a weak check; fixing it changes the workflow bundle, and ADR-0078 then ends open runs. The owner's options: carry the person's on-screen answer across the retry in the interpreter, or, as an activity-only interim, have `openCheckpoint` name the earlier answer when the current deck differs. A C5 test records today's behaviour.

## Alternatives considered

- **Structured segment ids and a per-segment editor (the review's repair).** Exact by id and fully explicit, but it changes checkpoint and resolution formats, store rows, the CLI and API answer format and the web UI, touches workflow types (ending every open run), and still needs every exactness rule above.
- **Exact checks, with the model still placing page copy.** Smaller, but link coverage stays the model's unverifiable choice, every web VOICE edit costs a call, and in demo mode an edit to a line with inline markup could never succeed.
- **Deterministic placement with heuristics instead of brackets.** No notation, but a heuristic (or a model) decides which words a link covers, or the person is forced to keep words they wanted to change.

## Consequences

**Positive**

- The person's words are written exactly as stated, in every medium, and a later machine write cannot change the locked deck unnoticed. The lock covers the words and, on a page, each link's address; it does not cover visibility, formatting, attribute copy, or the spacing and line breaks between a page's lines (see keepsVoice above).
- On a page, the browser checks every write before it is stored: Chromium must show the written page, as a visitor sees it (the page's scripts running, scrolled through, each character judged by its box), as the person's edit of what it showed before, so a misread in byway's page reader becomes a question asked again, naming the line, never a silent mis-write. Wherever the read sees two neighbours side by side (both shown at its last instant, so an item that keeps moving too, and then at every point of an endless animation's cycle it holds; or shown, or laid out apart, at one of its samples), judged along the line their text runs along (vertical text and text a transform turns included), the person's words never run together where a visitor would see them glued (where the read cannot measure how two neighbours sit, in text turned in a way it cannot measure or beside a box's edge offset across their line, a space typed there is refused), and they never go where a style hides them from sight or a box cuts them off (a box a transform turns or scales, or CSS zoom scales, included; a line in a box turned in 3D, where it cuts cannot be told, is not offered); all of this in the ways the read detects, at its one screen size, with reduced motion and at its instants (see what it does not check), and only on a page read with every file it loads from an admitted host (else the read fails plainly).
- No model in VOICE: demo and paid runs agree, and VOICE is free.
- Canonical C5's voice-over is now written back, with a note, instead of passing appended or reordered text.

**Negative**

- Page decks carry a small notation: link words in brackets, literal brackets escaped. The C1 demo deck has none.
- Free-form answers that the model used to map are now asked again, with the exact problem.
- Pages whose attributes hold a quoted `>`, or that contain svg CDATA, iframe, xmp, noembed, noframes, plaintext or literal brackets, are read differently; a question opened before the upgrade may be asked again once.
- A paragraph whose link carries a hook cannot be deleted in VOICE (it can be edited). Nor can a line whose element is kept for its hook when emptied and then shows on its own the text a stylesheet adds to it (a checkmark `::before` on a list item that carries `data-aos`, `p:empty::before{content:"Coming soon"}` on a paragraph with an id): the arbiter refuses the deletion, naming that text, which the person never wrote (round 10 stored it).
- A block of more than about a thousand words rewritten in more than 2,000 words loses the formatting in its changed middle (the words are still written exactly).
- Because the reader builds no tree, it reads a link the page leaves open or nests where browsers end it only outside tables, list boxes, embedded objects, marquees, svg and math, and only under fewer than eight blocks opened inside it. Where that does not hold (see the page tokenizer above), every line from that link to the page's end is offered (where a browser shows it) but cannot be changed in VOICE, and the lock does not cover which of those lines' words are link words (the words themselves are locked).
- The deck splits a line at any tag outside inline formatting, so a block with font, label, ins, del, a button, an image or an svg in it is offered as several lines that a browser shows as one. A removal can regroup lines within one block as browsers show it: a line left with only links side by side is read again as one line per link, and links side by side that a removal joins to the formatting around them are read again as one line, so the lock holds them as the written page reads. The words and links stay exact, and no removal runs two blocks together as the reader reads blocks. The reader reads blocks by the default stylesheet and the hidden attribute; the arbiter reads the page as a visitor sees it, so a line a stylesheet does not lay out is not offered, and a write that shows otherwise than the reader expected is refused. Content in a table outside any cell is offered in the reader's order, though browsers show it before the table. The deck shows a line as its source runs it: where the page's own boxes part characters the source runs together (tag chips, a `display: block` cite), the person sees them glued in the deck, and they stay parted as the page had them.
- Every page VOICE needs the page renderer, and reads the page in Chromium: twice when the question is asked (the page and its marked copy, sharing one 40 s deadline) and three times when an answer that changes it is written (those two, then the written page), each under the render's deadline. Each read loads the page with its scripts, fonts, images and allowlisted resources (fetched afresh each time: a script stylesheet from a CDN, such as Tailwind's browser build, is about 260 KB), scrolls it through and runs its clock. The person is not shown the lines as now read, only the first difference.
- Where the reader misreads a page, the arbiter refuses edits the person cannot fix by rewording, and the line must be left as it was: a deletion that runs text into content a browser moves out of a table, and one beside a MathML `<title>` whose content breaks out (round 6 wrote these). A button, an inline block and a table cell are boxes of their own in the visitor read, so deleting the first or last line inside a button (`<p>Pay <button type="button"><b>$20</b> <label>now</label></button>Total</p>` with "now" deleted shows "Pay", "$20" and "Total" apart) or the last block line of an inline block beside the next one is written: rounds 8 and 9 refused these, reading innerText, which cannot tell a box's edge from no gap.
- Deleting a line beside a float can let the next line rise beside the float, so a visitor reads that line before the float, though it follows it in the page. The arbiter gives a deleted line's neighbours the stronger of its two separators (a break, here, over the other order) and refuses the write as words in another order (in round 13, 7 of the round-11 verifier's generator's 7,200 edits were refused as another order, none on the realistic pages; round 12's record said 6 where its own runs had 7); the line can be changed, not deleted.
- A space the person types at a changed line's edge is written there where text stands beside the line in its block, also beside whitespace already there (a space more, which shows as one). A line whose only change is a space at its edge is unchanged, so two lines a page shows glued stay glued unless one of them is changed. A no-break space at a changed line's edge that the person takes out counts as a typed space (edit semantics, above); where that edge is a flex item's, which drops a space there, the write is refused as running words together that the lines keep apart, though the person typed no space (`<p style="display:flex"><b>Price:&nbsp;</b><font>$20</font></p>` with "Cost:"; the round-12 verifier), and it is stored only with the no-break space typed back.
- Lines a visitor does not see are not offered, so they cannot be changed in VOICE: a hidden block, a closed dialog, a closed `<details>` body, an svg or math `<title>`, svg text outside a text element, text a stylesheet does not lay out, a canvas's fallback, an accordion's body, a dropdown, a hover overlay, a slide a carousel shows only after the read's last instant (7.9 s after the page loads). Nor can a line a visitor sees otherwise than in one piece with exactly its words: words a flex or grid row shows glued where the line has a space, or offset across their line and meeting there (a staggered heading of flex items), a float, a reversed row, `order` or `<bdo>` that shows them in another order (in vertical and turned text too, however far apart along the line, but for two pieces far apart of which one stands in a box positioned out of the flow that the other is not in: what the arbiter does not check), a line in a box turned in 3D that hides its overflow, a line part of which is not laid out, a line a script rewrote in part (a counter from "0", a typed-out phrase) or copies (a table of contents). Chromium drops a newline right after `<wbr>` (the CSS segment-break rules) where the deck reads a space, so the line `<p>Hello<wbr>\nworld</p>` ("Hello world" in the deck, "Helloworld" in a browser) is not placed, and not offered. The prompt names each line it leaves out, and why.
- A line that holds any text a visitor does not see is not offered, so it cannot be changed in VOICE, though its other words show: a rating with "out of 5" for screen readers, a Bootstrap button or a card's "Read more" link with a screen-reader-only suffix, a nav link with "(current)" for screen readers, `<h2>Our menu<span class="sr-only">, updated daily</span></h2>`, a line with a faint, filtered or clear-filled word, a line a box truncates with an ellipsis or cuts partway through a row. On pages built with such classes that can be many lines, and visible words go with them: on the round-7 verifier's custom page the footer line "[Privacy] · [Terms] · [Instagram]" is not offered, because its icon link's label "Instagram" is for screen readers only. Offering the seen words and keeping the hidden ones would need the reader to know which of its text a style hides (backlog); it is not done, because then the person's words and a screen reader's would no longer match. A section a script reveals as the visitor scrolls, at opacity 0 or moved aside by a transform, is read revealed, so its lines are offered (rounds 7 to 9 read it hidden; round 10 read a slid or turned one where it waited). Text hidden from sight in ways the read does not detect (see what the arbiter does not check: covered by another element, painted behind an ancestor's background, coloured as its background, turned away, clipped by a clip-path given by url() or path() or a mask, faint or small above the thresholds) is read as shown.
- Two characters the person kept side by side, with the same spacing as in the deck, keep the separator they had, so a line a style breaks over screen lines (a `display: block` span in a heading) keeps its break where the words around it were kept; where the person's new words meet, a typed space may show as a space or as a break across boxes, and a gap they did not type must show glued, except right beside a character they kept where the page itself parted the line (a box's edge or a margin with no space in the deck), which may stay parted as the page had it: so a menu's price keeps its own box whatever the dish now says, and a chip the person extends keeps its edge. A gap they did not type between new characters away from such an edge must still show glued. Where a row wraps is not checked.
- A gap between two words that stand, one for one, where two words stood, or between two characters the person kept side by side, keeps the page's own whitespace only where it lay in one run of text. Beside a word the person added, or where they deleted one, it is the person's single space, so a line break a white-space style kept there is gone: an address line with a word inserted before its break ("Crumb & Co. Bakery") or with "London" deleted shows the words around that gap on one row, which the person's line allows (a space). The arbiter holds a gap to the separator it had only between two characters the person kept side by side; elsewhere a typed space may show apart in the flow or across boxes. Placement matches the characters of each part of a line (outside links, or one link) on its own and the arbiter those of the whole line, so where a character repeated across a link's edge beside a kept break makes the two match it otherwise, the write is refused. So is a line whose repeated word beside a kept break the in-code verifier matches otherwise than placement: placement then writes every gap of the line as one space (above), the break the arbiter holds between two characters the person kept is gone, and the write is refused as showing on one line what the page showed on separate lines (`Fresh\nFresh bread Blue\nSign` with the first "Fresh" replaced; the round-12 verifier saw this 6 times in 600 generated pages, never on realistic hours or addresses). Where formatting or a link's edge splits whitespace that a white-space style keeps (`<span style="white-space:pre"> late <span style="white-space:pre">
  Spring?</span></span>`, which shows "late" and "Spring?" on two screen lines), placement writes the gap as one space, which a browser shows on one row, so an edit elsewhere in that line is refused ("would show on one line what it showed on separate lines").
- The read runs the page's scripts under a stopped clock at one instant, a seeded Math.random and an IntersectionObserver that reports every element it watches in view: a page reads the same in every check, as on one day; a page whose text depends on the real date shows its text for that instant, and a script that shows other words on another day is not seen to. A carousel that moves or fades its slides, and a ticker, are read wherever the read's 33 instants show them, so every slide shown by 7.9 s is offered; one that switches its slides' display shows the read only the slide showing at its last instant, and its other slides are named as not shown at all (the round-10 restaurant's testimonials); a slide shown only after 7.9 s is not offered. Deleting one of a carousel's slides can bring a later one into the read's window, and the write is refused as a line the person did not change showing otherwise. A page whose script rewrites other text from the lines (a reading-time estimate, a table of contents) cannot have those lines changed: the write is refused as other text changing ("other text on this page, not one of your lines, would change …"), quoting what it would show. Letters are read as written (CSS text-transform changes how a character looks, not the text), so a person's capitals are compared as typed. It reads one screen size, 1440 × 900: a line a stylesheet shows only at phone widths (a `d-md-none` block) is not offered, and the prompt names it as not shown at all (backlog: a phone-width read).
- An `<a>` without an href is not a link: its words are plain and the lock does not hold them as link words, though a page whose CSS and script make one look and act like a link shows it as one.
- An emptied element browsers end elsewhere than its own end tag (misnested, left open, or one whose start tag ends another, such as a `<p>` inside an open `<p>`) is kept, empty, as is a block whose removal would run two lines together on screen; the page keeps an empty element where a person might have expected it gone.
- On a page with a link left open, that link is never removed, nor is anything holding one end of its reach and not the other. So emptying such a link is refused, and deleting the line that holds its start tag can leave an empty block. Words between two links with no place outside both are refused; a space there is written. So are words after a link the page leaves open at the end of a line, with their own reason ("words cannot be added after the link "there" on this line: the page leaves that link open, so a browser makes the words after it, up to the next link, part of it").
- In an edited line, where an empty icon in the middle of the line has a space on each side, the space after it is lost ("Hello <icon> world" becomes "Hello <icon>world"). So is the gap before an arrow at the end of a link in the middle of the line, even when only words outside the link change. Text glued to a link whose edge space sat before an arrow drops that gap too ("[Order now]!"), and where the arrow takes up width the write is refused, since a visitor sees the stop beyond the arrow (placement above). At a line's edge, words added outside the formatting that holds the edge space touch an icon beside them (placement above). This is layout only; the words are exact. Text glued to a line's first or last kept word goes into that word's slot, so it takes that word's formatting too ("£13!" with the price in bold has a bold "!"). Where that word is a link's and the text is outside the brackets, it goes beside the link, into the shallowest slot after it, which can be outside the box that holds the link (a flex item): a visitor then sees it apart, and the write is refused (3 of the 1,527 answers on round 13's realistic pages that glued punctuation to a line's end, each a footer's last link: "[Dribbble]!", "[hello@northwind.studio]!", "[hei@nls26.no]!"; backlog). The verifier checks edge whitespace slot by slot only where no removal merged slots; where one did, the line's words and the line as it shows are still checked.
