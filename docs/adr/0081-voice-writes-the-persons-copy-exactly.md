## Context

VOICE is the product's core promise: a person writes every reader-facing line (spec §3.2; protocol 01 VOICE step 7, "inserts the human copy exactly"; port rule 6, "no later block writes over voice"). The external review's F07, confirmed at P1 by the verification, showed that the runner did not keep it:

- A page's write-back went to `helper.voice.apply`, and the result was checked only for an unchanged tag skeleton and for each non-empty line appearing somewhere on the page. Deleted text left on the page, a repeated line replaced by other words, swapped lines and new copy between tags all passed. The fallback placement emptied inline links and emphasis. An out-of-range character reference threw a `RangeError`.
- The "unchanged" test squashed whitespace, so moves across lines, merges and a prose paragraph split were dropped silently, and the last block could not be emptied.
- Every other medium fell back to the model whenever its reader could not map an answer, and the options and on-screen readers dropped or shadowed lines the person typed.
- `keepsVoice` held later machine writes only to substring membership (`lostVoiceLines`), and skipped the check for an empty voice. Canonical C5 reaches this: a model that appended to or reordered the voice-over passed.
- The page tokenizer ended a tag at the first `>`, even inside a quoted attribute value.

The common root: the person's copy could be written by something other than an exact, total application of their edit, as long as the result passed a check weaker than the edit.

This record supersedes the whole "VOICE write-back" bullet of [ADR-0073](0073-runner-semantics-where-the-spec-was-open.md), including its keepsVoice sentence. ADR-0073 is not edited.

## Decision

**Each medium's copy deck is the contract, and no model writes the person's words.** The runner offers the deck, reads the answer with a total reader (every line lands in exactly one place, or the answer is refused with that line named), writes it back deterministically, and checks the written artifact exactly. On a web page the browser has the last word: the runner's own Chromium, read as a sighted visitor sees the page, decides which lines are offered and must show the written page as the person's edit of the page before, or nothing is stored (the browser arbiter, below). VOICE makes no model call in any medium, so demo and paid runs behave the same and VOICE costs nothing. The `helper.voice.apply` templates and the `voice.apply` id stay, because the prompt ids are in the workflow bundle; they are no longer called.

**Decks.**
- Prose: the Markdown document. Code diffs: the "Why:" paragraph (empty is refused). Media: the voice-over script at the early VOICE; at the late VOICE, `Headline:`, `Tagline:` and one `Shot N:` per shot. Options: `### A` then `Title:`, `Pitch:` and `Rationale:` for each option.
- Labelled decks are read by one total reader: each label once, in the order shown, matched by position (so a storyboard whose shots repeat a number still reads); continuation lines belong to the label above; anything else is refused and named. A voice-over line at the late VOICE is refused.
- Non-web write-backs pass a round trip: the deck read back from the written artifact, laid out by one line-based `layoutOf`, equals the answer laid out the same way. `layoutOf` is never the reader. It normalises only layout (line endings, trailing spaces, every run of blank lines that ends at a label or at either end, however long, a value on the line after its label, label case and spacing) and keeps everything inside a value, blank lines between its lines included. The same `layoutOf` is the "unchanged" test, so a doubled space inside a caption is written. A failed round trip is refused quoting the first line that would differ.
- Web pages: one line ("unit") per run of visible text, in reading order. A run is text with no tag inside it but inline formatting (a, abbr, b, bdi, bdo, cite, code, data, dfn, em, i, kbd, mark, q, s, samp, small, span, strong, sub, sup, time, u, var, wbr). So a block is one line unless a `<br>`, a nested block or any other tag splits it, and that includes the tags of elements browsers show inline: font, label, ins, del, a button, an image, an svg or a form control. `<p>Hello <a href="/s"><svg></svg></a> world</p>` is offered as two lines, "Hello" and "world", and `<p>Hello <font color="red">world</font>!</p>` as three (the words stay exact). The VOICE prompt and the line-count refusal say "one line per block of text", which is the common case only: a block that such a tag splits is offered, and counted, as the several lines the person is shown. A block of links side by side (each an `<a>` with an href) gives one line per link. Head content is not offered except `<title>`; text that is not whitespace ends the head, as browsers end it, so text written in the head after the title is offered; it continues the body's first screen line, as browsers show it. The content of a hidden element that browsers show inline (a span, a font, a label or the like with the hidden attribute) is not offered, so the person's words never go into text a browser hides inside a line it shows: `<p>Sale<span hidden> ends</span> today</p>` is offered as "Sale today", and "Sale starts today" is written `<p>Sale<span hidden> ends</span> starts today</p>`. A canvas is read the same way: its content is the fallback only a browser without scripting shows (a visitor sees the canvas), so it is not offered, as noscript content is not (round 8 offered it). Only lines a browser shows are offered: a line the runner's Chromium does not show, as a sighted visitor sees it, in one piece with exactly its words is not offered, and stays byte for byte (the browser arbiter, below). So a hidden block, a closed dialog, the body of a closed `<details>`, the text of an svg or math `<title>` (a tooltip), text a stylesheet does not lay out (`display: none`, `visibility: hidden`), and a line the reader reads where a browser shows nothing (such as the lines an svg `<title>` left open over a paragraph's end hides) are not offered; nor is a line a browser shows, but not in one piece with exactly its words (the items of a flex row, a line with a `display: none` span inside it, `Hello<wbr>` before a newline). Nor is a line holding any text a style hides from sight though a browser lays it out (a screen-reader-only class, opacity 0, font size 0, a transparent colour, text clipped away or moved off the page, as the arbiter defines it below): its words are not all seen, so the person's words never go into such text. `<p>Rated 4.5<span class="sr-only"> out of 5</span> stars</p>`, a Bootstrap button `Send message <span class="visually-hidden">to Saltbox</span>` and a card link `Read more<span class="visually-hidden"> about quiet interfaces</span>` are not offered, and stay byte for byte (round 8 offered them, read such text as shown, and wrote "Rated 5 by every single baker" as `<p>Rated <span class="sr-only">5</span> by every single baker</p>`, whose "5" no sighted visitor sees). The prompt adds "Text a browser does not show as one line here (hidden, out of sight, a tooltip, or laid out differently) is not offered, and stays as it is." (round 8 said "hidden, a tooltip, or laid out differently"; round 7 said "hidden, or shown only as a tooltip", which called those visible lines hidden). Round 6 offered hidden blocks, closed dialogs, closed `<details>` bodies and svg titles as lines.

**The page tokenizer** reads a page as browsers tokenize it where that decides what is copy, without building the tree: WHATWG tag ends (quotes delimit attribute values only; input ending inside a tag is opaque); comment forms; raw text for script, style, noscript, template, iframe, xmp, noembed, noframes and textarea (textarea's default value is not offered; `/>` on these is ignored in HTML content); a script's `<!--` escapes, so `</script>` inside an escaped `<script` string does not end it; plaintext opaque to the end; `<title>` as RCDATA, offered; inside `<svg>` or `<math>`, a CDATA section is opaque. The self-closing flag is WHATWG's: a `/` read right before `>` outside any value (so `href=/shop/` does not set it). The reader honours it where browsers do (void elements, `<svg>` and `<math>`, and everything inside them) and ignores it on other HTML elements, so `<a href=x/>` and `<span/>` open an element. It builds no tree, but it keeps the stack of open elements as browsers keep it where that decides where an element ends. End tags are matched by WHATWG's rules: a block's end tag closes it and everything open inside it unless a scope boundary (a table, a cell, a caption, an object, a marquee, a template or a list box) lies between; any heading's end tag closes the open heading; `</p>` with no p open makes an empty p and `</br>` is a `<br>`; a formatting end tag (a, b, em, font and the rest) closes its element, and when a block is open inside it, browsers' adoption agency closes the formatting and leaves the block open, as the reader does; any other end tag is ignored when a block or control is open inside its element. Start tags end what browsers end for them: a block ends an open p, an li an open li, a dd or dt an open dd or dt, a heading a heading that is the innermost element, and body content an unclosed head (so the body of a page that omits `</head>` is now offered; it was read as head content before). Browsers ignore a table part outside a table, an `<html>` start tag after any other tag or text, a `<body>` start tag once the body has begun (explicitly, or implicitly with text or a start tag that does not belong in the head), a `<head>` once the head or the body has begun, and a form inside a form; the reader opens no element for them, so none of them breaks a line. (Round 6 read a `<body>` after an implied body as a block break, so deleting a heading between head text and the body's text ran the two together: `…Welcome</head><body><h2>Sale</h2>Order today` showed "WelcomeOrder today". The emptied heading is now kept, and Chromium shows "Welcome" and "Order today" on lines of their own.) There is no reconstruction of formatting elements, except where a link ends, and no foster parenting: content written in a table outside any cell (in a table, a row group, a row or a column group; a row opened inside a cell ends the cell in browsers, and the reader keeps that row innermost) is read where it stands, while browsers move it before the table, so its lines can be offered in another order than a browser shows them. An element read there, or a `<br>`, is never removed, nor is anything holding one: `<div>late:<table><tr><span><section>Gone</section></span>After<td>Cell</td></tr></table></div>` with "Gone" deleted keeps the emptied span and section, which browsers show before the table, so "late:" and "After" stay on lines of their own. Foster parenting is not modelled beyond that: removing a block that stands between text and a table holding fostered content can run that text into the fostered content in a browser (`<div>Lead<p>Middle</p><table><tr><font>F</font><td>Cell</td>…` with "Middle" deleted shows "LeadF"); the reader and the in-code verifier do not see it, and the browser arbiter refuses it. Only the html `<title>` is the page's title: an svg or math `<title>` is an element like any other there (a self-closed one opens nothing, and the svg's end closes one left open), and its text, a tooltip, is not counted as text a browser shows; Chromium does not show it, so it is not offered. Two foreign-content misreads remain in the reader, and the arbiter turns each into a refusal or a line not offered: a MathML `<title>` whose content breaks out (a `<b>`, a `<span>`, a `<p>` inside it) is read as hidden though browsers show that content, and an svg `<title>` left open over an HTML end tag such as `</p>` is read as closed there, though browsers keep it open and show nothing after it. A start tag named image is read as `<img>`, as browsers read it. A link is an `<a>` with an href; an `<a>` without one is a placeholder (browsers show its words plain), so its words are plain in the deck, the prompt and the lock, also when the page leaves it open, as in `<h2><a name="top"/>Welcome</h2>`; its tags still end the links around it. A link is read where browsers end it, at the next `<a ...>` or `</a>` tag: a link the page leaves open (an unclosed `<a>`, `<a href=x/>`, or one a misnested closing tag pops) reaches into the following blocks, as browsers open it again there, and an `<a>` inside another ends the first. This was checked against Chromium (below). Where browsers may stop, skip or resume the link and byway cannot tell without building the tree, that link is "tangled", and every line from it to the page's end is offered (where a browser shows it) but cannot be changed: when its reach holds a table, a list box, an embedded object, a marquee, svg or math; when one of those, opened inside a link the page closes, is still open at its `</a>` (browsers ignore an `</a>` inside a cell, a caption, an object, a marquee or a list box the link holds, so the reader does not match it and reads that link as left open); and when eight or more blocks opened inside the link are open where it ends, because the adoption agency gives up after eight turns. Checked against Chromium, that count is exact for a link open in its block and one block early (tangled where Chromium still ends the link) for a link a block's start has popped from a `<p>`. The VOICE prompt names those lines, and a change to one is refused, naming it ("Line 4 cannot be changed in this step: a link on the page (to /x) is left open or holds another link, around a table, a list box, an svg or other markup where byway cannot tell which words a browser shows as that link's words, so byway cannot write this line exactly. Leave line 4 as it was offered."). An element is removed only when it is balanced: closed by its own end tag while it was the innermost open element, with nothing inside it closed out of order, closed implicitly by an end tag, or ignored, and its start tag ended nothing (browsers' implied end of an open p, li or heading). So no removal leaves an end tag browsers would ignore, takes the start of a block browsers end later, or lets an element its start tag ended run on. Nor is an element removed that holds one end of a left-open link's reach and not the other; an `<a>` written around another goes whole, from its start tag to its own closing tag. On the C1 demo page its tokens are identical to the old tokenizer's. Character references are decoded by parse-entities with browser rules (total; U+FFFD for references out of range). Whitespace means HTML whitespace; a no-break space is text. Changed text is written with `&`, `<` and `>` escaped; unchanged text keeps its bytes.

**Not offered on a page** (each stays byte for byte): attribute copy (alt, aria-label, title, placeholder, meta description), script-generated copy, CSS content, textarea default text, svg CDATA text, xmp and plaintext content, noscript content, a canvas's fallback, `<pre>` content, the content of a hidden element browsers show inline, and every line Chromium does not show as a sighted visitor sees it, so every line holding text a style hides from sight (the browser arbiter's offer rule, below). An emptied element is kept, not removed, when it holds a script, a style, a noscript, a template, other raw text or a comment, so those bytes stay too (round 6 removed them with it).

**One bracket notation on every page line.** Link words inside a line are shown in `[brackets]`; a literal bracket, or a backslash before one, is shown escaped with a backslash on every line. A line with links keeps one pair per link, in order; `[]` removes that link. A line that is exactly one link's words takes plain words or one pair around the whole line. A line with no link refuses an unescaped bracket and says how to escape it. Link words are the person's decision: the VOICE prompt names where every link goes ("line 2 "Terms of service" goes to /terms"; at most 40, addresses cut to 60 characters), so there is no relabel guard. This suffix is added by `openCheckpoint` from the work itself, once per checkpoint, re-asks included; it lives there until the next workflow change.

**Edit semantics.** The answer is a positional edit: one line per unit; an empty line deletes that unit's text, the last one included; blank lines past the end are nothing. A changed line is read with its whitespace collapsed, and a space the person types at either of its edges (with its brackets taken out, so also the space beside a link removed with `[]` at the line's start or end) is kept as a space at that edge (placement, below). A line whose words and links are as offered is unchanged, whatever spaces it has at its edges. A question opened by an older engine is aligned by words only (brackets and backslashes dropped). When a changed line no longer lines up with the current deck, it is refused on the first offer and read against the current deck on a re-ask. "First offer" means exactly: the answered checkpoint's starting text equals the text the step first offered; a missing checkpoint counts as a first offer. A changed page line holding a null character (U+0000) is refused, because browsers drop it from a page's text.

**Placement and verification.** Placement is deterministic: changed text goes into the line's text slots, aligned to the old words so formatting follows whole words or pieces (a documented, tested rule; formatting coverage is not verified). No word crosses a link's edge: a link part's words go only into its link, words outside brackets only outside every link (never into an image, svg or icon link that held no words), and a whole-link line's words all into its link. Words added before a line's first kept word, or after its last, go beside it: into the shallowest slot reachable from it across only opening (or closing) formatting, so an empty icon between stays where it was. The whitespace before a line's first word and after its last stays in the slot that held it, at the same end, wherever the new words go (the new words carry their own spaces), so the gap beside an empty icon, an image link, or an arrow at a link's end stays where it was, except where words are added at that edge of the line and the whitespace sits inside formatting the new words go outside of: then the whitespace parts the new words from the old ones, and the new words touch the icon (`<p><svg …></svg><b> Hello</b> world</p>` with "Big Hello world" is written `<svg …></svg>Big <b> Hello</b> world`; layout only, the words are exact). The one exception: a piece that would then show as a space where the person's line has none is dropped. That happens when the person glues text to a word whose edge space sits inside a link or formatting: a pretty-printed `<a href="/shop">\n    our shop\n  </a>` with "Visit [our shop]." is written `<a href="/shop">our shop</a>.`, and `[Order now]!` after `<a>Order now <i class="arrow"></i></a>` is written `Order now<i class="arrow"></i></a>!`, so the arrow loses its gap, because the deck cannot show the arrow. With a space typed after the link (`[Order now] today`) the gap stays. The edge whitespace also parts the line from text beside it on the same screen line (in the same block as browsers show it). Where new words went past the slot that held it (into a shallower slot beyond formatting), or a piece was dropped, and text a browser shows stands beside the line in its block, a space goes at the line's new edge, beside the new words: `<p><del>Was <b>$20 </b></del>Now $15</p>` with "Was $20 only" is written `<del>Was <b>$20 </b> only </del>Now $15`, and `<p><label>Email</label><a href="/help"> help</a> is here</p>` with "Get [help] is here" is written `<label>Email</label> Get <a href="/help"> help</a> is here` (round 3 to 5 wrote "Was $20 onlyNow $15" and "EmailGet help is here"). With nothing beside the line in its block, nothing is added (`<p>Read <a href="/x">more </a></p>` with "Read [more]." is written `Read <a href="/x">more</a>.`). A space the person typed at a changed line's edge goes there by the same rule, where the line's own edge whitespace is not still at that edge: `<p><b>Hello</b><font>world</font></p>` with " there" is written `<font> there</font>`, and `<p><b>Sale,</b><font><a href="/d">$20</a> menu</font></p>` with "[] menu" is written `<b>Sale,</b><font> menu</font>` (round 7 dropped these spaces, so the words ran together: "Hellothere", "Sale,menu"). Whitespace already beside the line is not weighed, so where some stands there a space more is written, which shows as one (the reader cannot always tell whether whitespace shows, as at a button's edge). At the edge of a button's content a space never shows (a button lays its content out on its own), so a typed space at the start or end of a line that starts or ends a button's content is not written there; where the button touches the text beside it with no whitespace between, the edit is refused, naming the line ("Line 2: a space at the end of this line would be inside a button, where browsers do not show it, so it cannot part the line from the text after the button; leave the space out."), so the space is never dropped unsaid. Whitespace inside a line is not kept per slot. Each gap between words is the person's single space: where the old gap lay within one part of the line (outside links, or one link), it goes into the first slot of that gap; at a link's edge, it goes into the part the person typed it in. So in an edited line, where an empty icon in the middle of the line has a space on each side, the space after it is lost ("Hello <icon> world" becomes "Hello <icon>world"); a space on one side only stays on that side, and where the words on both sides of the icon are replaced, the new words can all go before it. The gap before an arrow at the end of a link in the middle of a line is lost whenever the line is edited, even when only words outside the link change: `Ready? <a>Order now <i class="arrow"></i></a> and save.` with "Set? [Order now] and save." becomes `Order now<i class="arrow"></i></a> and save.`. This is layout only; the words are exact. Removal is conservative: an emptied inline element or text block (p, h1–h6, li, blockquote, figcaption), balanced and outside svg and math, is removed unless it holds an embedded element, a script, a style, a noscript, a template, other raw text or a comment, or a table's tag (a table, a cell, a row or another part, start or end tag), carries a hook (id, for, name, role, data-*, or aria-* other than aria-label), or browsers move it, or an element in it, out of a table (above). (Round 7 removed an emptied `<sub>` holding a `<td>`, which ends the cell around it in browsers, so the written page had a cell fewer; the arbiter refused it. The empty `<sub>` is now kept and the deletion written.) No removal may join two runs of text, neither two runs of the deck nor two blocks as the reader reads browsers' blocks, or move where browsers end a link (see the page tokenizer above); where the reader misreads the blocks (a button's content edge, foster parenting, a MathML title breakout), the browser arbiter refuses what the reader let through. Blocks are read by the default stylesheet: text on either side of a block's start tag, of the end tag that closes a block, or of a `<br>` shows on separate lines; every other element shows inline (font, label, ins, del, an image, an svg, a button, a control, a custom element) or not at all (script; an element with the hidden attribute, a closed dialog or a datalist; and the text of an svg or math `<title>` while it is open), whose text and tags are not counted. So `<div><font>Intro<p>Spring sale</p></font>Order today</div>` with the middle line deleted keeps an empty `<p></p>`: removing it would show "IntroOrder today" on one line. Both are weighed by union-find over all removals together, and a deleted line takes the `<br>` run that ends it under the same rule. The whitespace placement put inside an element it then removes (a line's edge space, or a space between two words) is written where the element was, so `<p>Hello <span>world </span><i class="arrow"></i></p>` with "Hello" keeps the gap before the arrow. A deleted line's edge whitespace inside an element the edit removes is written where the element was too, when text a browser shows stands on both sides of the element in one block, as the page was, and only whitespace a browser showed (a hidden block's never showed, so it goes with the block; round 6 wrote it there, and its own verifier refused the write); elsewhere it would sit at a block's edge, where it shows nothing, and it goes with the element. So `<p>Price: <del>$20</del><span> now </span><ins>$15</ins></p>` with "now" deleted is written `<p>Price: <del>$20</del>  <ins>$15</ins></p>`, which shows "Price: $20 $15" (round 5 wrote "Price: $20$15"). A link or button that would be left without words a browser shows, or nameless, is refused, naming its hook, and saying so when it holds words a browser hides, so a line whose link carries a hook can be edited but not deleted. Hidden words (a hidden span) name nothing, and they are never dropped, so a control left with only hidden words is refused, not removed (round 6 counted them as its words and wrote a button that showed empty, with no name). "Words a browser shows" here are the reader's, which reads no stylesheet: words a style hides from sight (a screen-reader-only span) count, and they name the control for a screen reader, so a control whose seen words are a line of their own and whose other words are hidden from sight can be left showing no words: `<button type="submit"><font>Send</font><span class="visually-hidden">your order</span></button>` with "Send" deleted is written with the empty `<font></font>` and the hidden span kept, a button a sighted visitor sees empty and a screen reader names "your order". The arbiter lets it through, since the page then shows exactly the person's lines. An `<a>` without an href counts here only when a role, a tabindex or an `on…` handler makes it a control; a placeholder such as `<a name="faq">FAQ</a>` may be left empty. One that keeps an image or icon is named by its own aria-label, aria-labelledby or title, or by an image's non-empty alt or an element's own label inside it (an empty alt is decoration). Placement returns its removals as a witness. The verifier shares the reader, the removability rule, the `<br>`-run rule and the rule for a deleted line's whitespace where a removed element was with placement, and nothing else. It refuses a changed line in a tangled link's reach, then checks six invariants: (1) each witnessed removal is allowed, and the markup is the page before less exactly those removals, token for token; (2) and (3) unchanged text keeps its bytes and a deleted line keeps only its edge whitespace, run by run, and where an element was removed the written text is exactly what that shared rule leaves there; (4) each changed line reads exactly as written, both by its words (each slot's text less the edge whitespace it held) and as it shows (all of its text, edge whitespace included, with HTML whitespace collapsed, so no space shows where the person wrote none), and each link part reads exactly its bracketed words; every slot that held the line's edge whitespace still holds it at the same end, across all of the line's segments, unless that piece would have shown between two characters (then it must be gone); (5) no link or button whose shown words were in a changed line is left without words a browser shows, unless something names it (one that held no words, such as an image link sharing a run with a changed line, had no name for the edit to take); (6) read fresh, the written page's runs hold exactly the expected words, in order, and the same words in the same links with the same addresses, so a word that crossed a link's edge is refused however it got there; and its blocks, read as browsers show them (end tags browsers ignore break nothing) with HTML whitespace collapsed, are the page before with the person's lines in place, each changed or deleted line keeping the edge whitespace it had, so the page's own separators between lines stay, and a changed line with a space where the person typed one at its edge. Two lines a browser showed apart, on lines of their own or as words on one line, that now run together, a space where none showed, and a line it now breaks are refused however that came about ("The page, read again, runs lines together that a browser showed apart: it shows "IntroOrder today" as one line."; "The page, read again, runs words together that a browser showed apart: it shows "Was $20 onlyNow $15"."). Round 5 compared blocks with all whitespace removed, so it saw lines on separate screen lines run together but not two lines on one screen line losing the space between them. It is independent of placement's alignment and its choices among removals, not of the reader: a page the reader misreads can pass it, which is why the browser has the last word.

**The browser arbiter.** The reader is a model of how browsers build and show a page, and placement and the in-code verifier both depend on it, so a misread there is a write the verifier cannot see (round 6's verifier found that about 440 of 1,500 generated pages read differently from Chromium). So every page VOICE asks the browser itself, and fails closed (page-arbiter.ts):
- What it reads with: the runner's own Chromium (`PageRenderer.shownText`), the one the renderer starts by its one stated launch (ADR-0084: no secrets in its environment, its OS sandbox as `RENDERER_OS_SANDBOX` says, which this record does not change), with JavaScript off (the deck excludes script-made copy), under the render's allowlist (held on every redirect hop, with the byte cap per response), request filter and deadline, reading only the page's first document: a later navigation the request filter sees (a meta refresh to an address) gets No Content, a move to a fragment of the page (a meta refresh to `#top`) keeps the document and is read (round 8 called it navigating away and failed the step), and a navigation the filter does not see (a meta refresh to about:blank or about:srcdoc) is a plain StepError ("The page navigates away as it loads (a meta refresh, for example), so the text it shows could not be read."; round 7 let the read throw a raw error, which was retried). A question's two reads share one deadline of 40 s, because openCheckpoint runs under the workflow's `quick` proxy (one minute to close, no heartbeat): a page Chromium cannot read in that time is a StepError, not a timed-out activity Temporal retries (round 7 gave each read 30 s). A write's reads each have the render's 30 s; finishHumanStep heartbeats under the 15-minute `model` proxy. It reads what a sighted visitor sees, as the page settles: once the page has loaded, its web fonts are waited for and its animations and transitions taken to their end (an endless one, which cannot end, is stopped), so a fade-in is read as it ends, not at its first frame. It reads document.title and the body's innerText (display, visibility, the hidden attribute, whitespace collapsing and block breaks applied, and CSS text-transform undone so letters read as written) with every text node a style hides from sight taken out, and the same text with the characters of each link marked with the link's address; and it lists the text it took out, node by node, with each node's link. A text node is hidden from sight when Chromium lays it out but: it or an ancestor has opacity 0; its colour and fill are fully transparent, with no stroke, no shadow and no background clipped to the text (so gradient text shows); or none of its boxes, once clipped by every ancestor whose overflow is hidden or clip (an absolutely or fixed positioned element escapes those below its containing block), by an absolutely or fixed positioned ancestor's `clip` rect and by an ancestor's `clip-path: inset(…)`, keeps more than a pixel in each direction short of the page's top or start edge, beyond which no scrolling reaches. So a screen-reader-only class (Bootstrap's `visually-hidden`, Tailwind's `sr-only`), font size 0, a box of height 0 that clips what overflows it, and text moved off the page (`text-indent: -9999px`) are hidden from sight; a scroll box and overflow that spills are not. Text in a marquee is measured by the marquee's own box, through which it scrolls (measured where its scrolling had taken it, a page with a marquee read differently from its marked copy, so none of its lines could be changed; the round-9 runs found it). The noncharacters the arbiter marks a copy of the page with are taken out of the text while this is measured, so the marked copy is measured as the page is. An absolutely or fixed positioned element that then shows no text and holds no image or control is left out of the read too: it stands outside the text's flow, so it breaks no line (innerText puts such a box on a line of its own, so a screen-reader-only space between two words read as a line break, though they show glued). With JavaScript off, text a script would bring into sight (a section that waits at opacity 0 for a scroll animation's script) reads as hidden, so its lines are not offered. It changes no sandbox setting. With JavaScript off a noscript element's content and a canvas's fallback show, so the arbiter reads them as the page's own text; they are never offered and stay byte for byte.
- Where each line shows: a copy of the page is marked at each deck line's first and last character (noncharacters put into the text beside a character, so no element and no collapsed whitespace changes), and Chromium reads the page and the copy. A line is placed where its two marks each show once, the start before the end, with exactly the line's words between them (each run of whitespace read as one space, a line break included). The copy must read as the page does once the marks are taken out; if it does not, or the page itself holds the marks' characters, no line is placed: every line is offered, the prompt says none can be changed, and a change to one is refused.
- What is offered (the offer rule): a line that is not placed is not offered, and stays byte for byte; placement and the in-code verifier read it as the page's own text. A line holding text hidden from sight is never placed: a mark in that text is taken out with it, and words missing between two marks are not exactly the line's words. Lines are offered in the reader's order, and each is placed where Chromium shows it (content a browser moves out of a table is placed before the table).
- What the written page must show: Chromium's text of the page before, with each changed or deleted line's placed words replaced by the person's words (brackets taken out, and a space at an edge where the person typed one), and everything else, the separators between lines included, as the page had it. A gap between two of the person's words is one space, except inside a line Chromium showed broken over screen lines (by a style the deck does not read), where it may be a space or a line break. A rewritten line's link words must be the deck's as Chromium shows them (each bracketed part in one link, nothing else in a link); the person's bracketed words then belong to that link's address, and every other character keeps the link Chromium showed it in.
- The check, after placement and the in-code verifier pass and before anything is stored: Chromium's reading of the written page, with each run of whitespace one gap and its ends trimmed, must equal that text exactly, gap for gap. A gap is n table-cell boundaries when the run holds n tabs (innerText ends each cell but a row's last with a tab), else a line break when it holds one, else a space. The line breaks beside a cell boundary are not compared: they are a block's edge or a `<br>` at the end or start of a cell's content, which parts nothing from the cell beside it, or a row's end after an empty last cell (placement never moves a cell). So a deleted line at a cell's edge leaves the cell boundary as the separator: `<td>Name<br>Note</td><td>$9</td>` with "Note" deleted shows "Name" and "$9" in their own cells, as the page before did (round 7 read the tab as a space against the deleted line's line break, and refused every deletion of the first or last line of a two-line cell, saying a browser "would show on one line what it showed on separate lines"). A cell boundary against a space or a line break, or another number of them, is refused ("a browser would show in one table cell what it showed in separate cells", "in separate table cells what it showed in one", "another number of table cells here"). Every character Chromium shows on the written page must be in the expected link (by address), and the title must read as expected. The text the written page hides from sight must be the page's own, node by node, in the same links and order: no changed line holds any (the offer rule), so a difference there is the person's words put out of sight (as a write that put new words into an empty screen-reader-only span would), the page's text pushed out of sight (a longer line pushing the next out of a box that clips what overflows it) or brought into it, and its reason says so ("a style on this page would hide "Two" from sight there (a browser lays that text out, as for a screen reader, but does not show it)"; "a browser would show "Three", which a style on this page hid from sight before"). Any difference refuses the write: nothing is stored, the person's answer is kept, and the question is asked again with the reason, naming the changed line nearest the difference and quoting it as first offered: "byway could not put line 4 on this page exactly as you wrote it, because a browser would run words together that your lines keep apart: it would show "Pay $20Total". Change line 4 again, or leave it as it was offered." The other reasons say that a browser would show a space, a line break, a table cell's edge or text the lines do not have, would not show all of the lines, would put on one line what it showed on separate lines, or would show words outside, inside or in another link than the brackets put them. A changed line Chromium does not show where byway reads it, or one the person rewrote whose link words Chromium shows otherwise, is refused the same way, ending "Leave line N as it was offered." A deleted line has no words to give a link, so its link words are not checked (round 7 refused deleting such a line too); the written page's other text must still show in the links it showed in. A fault in byway's own arbiter code is asked again like any fault in the pure copy code; a page Chromium cannot load in time, and a renderer that fails while it reads (a Playwright protocol error), are a plain StepError that is not retried, as a render's are ("The page's text could not be read: the page renderer failed while reading it (Target crashed).").
- With no page renderer configured, a page's VOICE fails plainly with a StepError, when it would ask and when it would write: byway never writes a page no browser checked.
- What it does not check: formatting and layout beyond the text (an icon's gap, which words are bold), text hidden from sight in ways it does not detect (covered by another element, coloured as its background, clipped by another clip-path shape, a mask, a filter or containment, or clipped in part, as an ellipsis clips a long line: the person's words added to a line a box cuts short can be cut off), attribute copy, what a script would change, and where a line break falls inside a line Chromium already showed broken. **keepsVoice is an exact lock.** The locked deck is computed before the model call.
- A storyboard's voice-over is written back from the work before the write whenever a voice exists, and the step finishes with a note: "The voice-over is locked, so it was kept exactly as it was; this step's change to it was undone." An obedient write is byte-identical and gets no note. If the undone change was the step's only change, a following A/B compare is skipped as "nothing to compare".
- Its on-screen copy is locked exactly when the late VOICE's own reader reads the voice as this storyboard's complete on-screen deck (whatever the values and their layout) and the voice is not the voice-over itself. Then any change to it is refused. A VO script has no `Headline:` line, so it stays unlocked; a VO script that happens to be the whole labelled deck is the voice-over, so it stays unlocked too.
- Options, prose, code diffs and pages are held by exact deck equality; pages also by each link part's address, by position. A page's lock reads its whole deck, so the lines VOICE did not offer (a browser does not show them) are held unchanged too. Visibility (the hidden attribute, inline styles, classes) is not checked, and neither are the spacing and line breaks between a page's lines: a later write that runs two of the person's lines together on screen, by wrapping them in font or label instead of two paragraphs or by dropping the space between two labels, passes the lock, though every line's words are kept. An empty voice is checked.
- With no work before the write, the written artifact must hold exactly the voice. For a page this is practically unsatisfiable (the whole deck would have to equal the handed-in deck); such recipes should place the deck with a VOICE step.
- In canonical C5 every keepsVoice writer runs in the script phase, with the VO script as its voice, so the write-back is the live path. The on-screen lock is reached only by composed recipes with a writer after the late VOICE.

**Typed boundaries (ENG-6).** Every problem with a VOICE answer, including a fault inside the pure copy code, is a question asked again (`AnswerRejected`), quoting how the offered lines or fields it names first read (at most five, 80 characters each), because after a re-ask the web editor's starting text is the person's previous answer. Sending the offered copy back always succeeds. An answer to a writing question with a broken character (half of a surrogate pair, which no store can hold) is asked again in every medium, naming the line, before anything is stored ("Line 3 has a broken character (half of a surrogate pair, not valid Unicode), so it cannot be stored: type that character again, or take it out."); round 6 let the store refuse it, a plain error retried and failing the same way each time. A fault reading the deck in `openCheckpoint` (the page arbiter's own code included), or in a keepsVoice check, is a plain, non-retryable `StepError`, so a paid call is never repeated. Store errors are retried as before. Chromium's reads fail as renders do: a page that does not load in time, or a renderer that fails while it reads, is a plain StepError, not retried (round 8 let a raw Playwright error be retried, as renders then were). The claim log runs on prose only; on any other medium the step offers and writes the copy deck.

## Alternatives considered

- **Structured segment ids and a per-segment editor (the review's repair).** Exact by id and fully explicit, but it changes checkpoint and resolution formats, store rows, the CLI and API answer format and the web UI, touches workflow types (ending every open run), and still needs every exactness rule above.
- **Exact checks, with the model still placing page copy.** Smaller, but link coverage stays the model's unverifiable choice, every web VOICE edit costs a call, and in demo mode an edit to a line with inline markup could never succeed.
- **Deterministic placement with heuristics instead of brackets.** No notation, but a heuristic (or a model) decides which words a link covers, or the person is forced to keep words they wanted to change.

## Consequences

**Positive**

- The person's words are written exactly as stated, in every medium, and a later machine write cannot change the locked deck unnoticed. The lock covers the words and, on a page, each link's address; it does not cover visibility, formatting, attribute copy, or the spacing and line breaks between a page's lines (see keepsVoice above).
- On a page, the browser checks every write before it is stored: Chromium must show the written page, as a sighted visitor sees it, as the person's edit of what it showed before, so a misread in byway's page reader becomes a question asked again, naming the line, never a silent mis-write, and the person's words never go where a style hides them from sight (in the ways the arbiter detects).
- No model in VOICE: demo and paid runs agree, and VOICE is free.
- Canonical C5's voice-over is now written back, with a note, instead of passing appended or reordered text.

**Negative**

- Page decks carry a small notation: link words in brackets, literal brackets escaped. The C1 demo deck has none.
- Free-form answers that the model used to map are now asked again, with the exact problem.
- Pages whose attributes hold a quoted `>`, or that contain svg CDATA, iframe, xmp, noembed, noframes, plaintext or literal brackets, are read differently; a question opened before the upgrade may be asked again once.
- A paragraph whose link carries a hook cannot be deleted in VOICE (it can be edited).
- A block of more than about a thousand words rewritten in more than 2,000 words loses the formatting in its changed middle (the words are still written exactly).
- Because the reader builds no tree, it reads a link the page leaves open or nests where browsers end it only outside tables, list boxes, embedded objects, marquees, svg and math, and only under fewer than eight blocks opened inside it. Where that does not hold (see the page tokenizer above), every line from that link to the page's end is offered (where a browser shows it) but cannot be changed in VOICE, and the lock does not cover which of those lines' words are link words (the words themselves are locked).
- The deck splits a line at any tag outside inline formatting, so a block with font, label, ins, del, a button, an image or an svg in it is offered as several lines that a browser shows as one. A removal can regroup lines within one block as browsers show it: a line left with only links side by side is read again as one line per link, and links side by side that a removal joins to the formatting around them are read again as one line, so the lock holds them as the written page reads. The words and links stay exact, and no removal runs two blocks together as the reader reads blocks. The reader reads blocks by the default stylesheet and the hidden attribute; the arbiter reads them as the page's own stylesheets make them, so a line a stylesheet does not lay out (`display: none`, `visibility: hidden`) is not offered, and a write that shows otherwise than the reader expected is refused. Content in a table outside any cell is offered in the reader's order, though browsers show it before the table.
- Every page VOICE needs the page renderer, and reads the page in Chromium: twice when the question is asked (the page and its marked copy, sharing one 40 s deadline) and three times when an answer that changes it is written (those two, then the written page), each under the render's deadline, which includes waiting for the page's web fonts. A page that navigates away as it loads (a meta refresh to about:blank) cannot be read, so its VOICE fails plainly. Without a renderer a page's VOICE fails plainly. A page whose styles come from the allowlisted hosts is read as they load: when they load at the question and not at the write (or the other way), the page can be read with another number of lines, and an answer that kept the lines it was offered is refused as such ("This page is now read with 4 lines, where this question offered 3 (a browser shows it differently than when the question was asked, as when a stylesheet or font it loads comes back differently, or byway reads it differently), so byway cannot tell which lines you changed. … Answer again with 4 lines, one for each line the page has now."; round 8 told the person to merge a line they added or put back one they removed). The person is not shown the lines as now read, only the first difference.
- Where the reader misreads a page, the arbiter refuses edits the person cannot fix by rewording, and the line must be left as it was: a deletion that runs text into content a browser moves out of a table, and one beside a MathML `<title>` whose content breaks out (round 6 wrote these). A deletion at a button's content edge is refused too, though there the write is right in what a sighted visitor sees. Whitespace at the start or end of a button's content is not in innerText (a button is an inline block), and the reader counts it, so deleting the first or last line inside a button removes the space innerText read between its neighbours: `<p>Pay <button type="button"><b>$20</b> <label>now</label></button>Total</p>` with "now" deleted is read "Pay $20Total", and refused, quoting that. In a browser the button's own padding and border part "$20" from "Total" by the same 8 px that parted "now" from "Total" before the deletion (when innerText read "nowTotal" glued), so the person would see the lines they wrote; only a button styled with no padding, border or margin lets the words touch. innerText cannot tell a box's edge from no gap, so these are false refusals in what a visitor sees, like the inline-block ones below, and the refusal's quote is innerText's reading, not what a visitor sees. The round-9 evidence (above) counts them as wrong writes only in innerText's terms, which its oracle shares.
- The arbiter cannot tell an inline block's edge (`display: inline-block`) from a space. innerText shows a block inside an inline block on lines of its own, so deleting the first or last block line of an inline block that has text beside it is refused, though the written page shows the person's lines: `<div style="display:inline-block"><b>Pro</b><p>For teams</p></div> <div style="display:inline-block">$29</div>` with "For teams" deleted shows "Pro $29", where the page before showed "Pro", "For teams" and " $29" on lines of their own, and the arbiter refuses it ("would show on one line what it showed on separate lines"). The line must be left, or changed instead of deleted. Table cells are told apart (innerText marks their edges), and flex and grid items are blocks to innerText.
- A space the person types at a changed line's edge is written there where text stands beside the line in its block, also beside whitespace already there (a space more, which shows as one). A line whose only change is a space at its edge is unchanged, so two lines a page shows glued stay glued unless one of them is changed.
- Lines a browser does not show are not offered, so they cannot be changed in VOICE, even where a script or a reader would show them later: a hidden block, a closed dialog, a closed `<details>` body, an svg or math `<title>`, svg text outside a text element, text a stylesheet does not lay out, a canvas's fallback. Nor can a line a browser shows otherwise than in one piece with exactly its words (the items of a flex row, a line with a `display: none` span inside it). Chromium drops a newline right after `<wbr>` (the CSS segment-break rules) where the deck reads a space, so the line `<p>Hello<wbr>\nworld</p>` ("Hello world" in the deck, "Helloworld" in a browser) is not placed, and not offered.
- A line that holds any text a style hides from sight is not offered, so it cannot be changed in VOICE, though its other words show: a rating with "out of 5" for screen readers, a Bootstrap button or a card's "Read more" link with a screen-reader-only suffix, a nav link with "(current)" for screen readers, `<h2>Our menu<span class="sr-only">, updated daily</span></h2>`, a line with an opacity-0 or font-size-0 word. On pages built with such classes that can be many lines, and visible words go with them: on the round-7 verifier's custom page the footer line "[Privacy] · [Terms] · [Instagram]" is no longer offered, because its icon link's label "Instagram" is for screen readers only. Offering the seen words and keeping the hidden ones would need the reader to know which of its text a style hides (backlog); it is not done, because then the person's words and a screen reader's would no longer match. With JavaScript off, a section a script would bring into sight (one that waits at opacity 0 for a scroll animation's script) reads as hidden too, so its lines are not offered. Text hidden from sight in ways the arbiter does not detect (covered by another element, coloured as its background, clipped in part) is read as shown.
- A line a style breaks over screen lines (a `display: block` span in a heading) is one line in the deck; the arbiter checks its words and that each gap the person wrote is a gap, not whether a gap is a space or the line break, so where the break falls in such a line is not checked.
- The arbiter reads with JavaScript off, so a noscript element's content and a canvas's fallback show to it (they are never offered, and stay byte for byte), and CSS text-transform is undone, so a person's capitals are compared as typed. It reads one screen size, 1440 × 900: a line a stylesheet shows only at phone widths (a `d-md-none` block) is not offered, and the prompt does not name the lines it leaves out (backlog).
- An `<a>` without an href is not a link: its words are plain and the lock does not hold them as link words, though a page whose CSS and script make one look and act like a link shows it as one.
- An emptied element browsers end elsewhere than its own end tag (misnested, left open, or one whose start tag ends another, such as a `<p>` inside an open `<p>`) is kept, empty, as is a block whose removal would run two lines together on screen; the page keeps an empty element where a person might have expected it gone.
- On a page with a link left open, that link is never removed, nor is anything holding one end of its reach and not the other. So emptying such a link is refused, and deleting the line that holds its start tag can leave an empty block. Words between two links with no place outside both are refused; a space there is written. So are words after a link the page leaves open at the end of a line, with their own reason ("words cannot be added after the link "there" on this line: the page leaves that link open, so a browser makes the words after it, up to the next link, part of it").
- In an edited line, where an empty icon in the middle of the line has a space on each side, the space after it is lost ("Hello <icon> world" becomes "Hello <icon>world"). So is the gap before an arrow at the end of a link in the middle of the line, even when only words outside the link change. Text glued to a link whose edge space sat before an arrow drops that gap too ("[Order now]!"). At a line's edge, words added outside the formatting that holds the edge space touch an icon beside them (placement above). This is layout only; the words are exact. The verifier checks edge whitespace slot by slot only where no removal merged slots; where one did, the line's words and the line as it shows are still checked.
