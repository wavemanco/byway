## Context

Anthropic's models think silently by default, so a long think can look like a dead connection. A call closed as stalled is sent once more, so it can be paid for twice.

**What held until block 2.** ADR-0111's Later notes describe the interim bound: fifteen minutes of silence for every streamed call (`STREAM_IDLE_MS`), and for a text call in an image or video step the step's own forty-five minutes, read from `SpendContext.operation.stepLimitMs`. A model step's limit was fifteen minutes, an image or video step's forty-five. Those notes also read the stall bound as what closed a silent stream, and OpenAI's SDK as what stopped an image at ten minutes. Node's own fetch came first for some calls. Its undici gives up after 300 s without headers, or 300 s between body bytes. Claude's local probe on Node 24.13.1 (a server on 127.0.0.1; [evidence/probes/node-fetch-limits-2026-10-22/](evidence/probes/node-fetch-limits-2026-10-22/)) saw both fail at 304 s, a body kept alive by a write every 30 s run to its end at 420 s, and an Agent with raised timeouts wait out headers held 330 s. So on main until block 2 (the sweep of 2026-10-22, B4; the design's list, under Consequences):

- an OpenAI or OpenRouter stream that sent nothing for five minutes was closed then, unless they send keep-alives, which is not known;
- a Google call, text or image, gave up after about five minutes a send;
- an OpenAI image gave up after five to ten minutes a send;
- each was then sent once more as "may have been billed" ([ADR-0091](0091-provider-edge-billing-fixes.md)).

**The research** the owner asked for at 09:50 is kept as [evidence/reports/answer-waits-research-2026-10-22.md](evidence/reports/answer-waits-research-2026-10-22.md) (its keeping chosen at 12:10, "Into the repo with Block 1 (Recommended)"). Its findings, in short:

- Text: no measured p95 silence at byway's effort levels is above 73 s (Opus 5.5 at medium, 72.5 s, from Artificial Analysis), so 15 minutes is 12.4 times the largest. At byway's output allowances only one worked-out case passes 15 minutes: GPT-6.1 Sol's 32k retry at the slowest speed, 15.3 minutes (Claude's arithmetic). 30 minutes covers it and the max-effort p95 on every host. 45 and 60 match no measured case at byway's settings; they stay because the owner chose them.
- Images: at byway's settings an image takes about a minute or less; the slowest p95 at any quality is 2.8 minutes. So images need less time than high-reasoning text, not more, which answered the owner's question of 09:50.
- Video: Kling 3 Pro image-to-video on fal has a p95 of 310 s, so 30 minutes is 5.8 times it. fal bills only successful outputs, and queue time is free.
- Google: a local test of @google/genai 2.27.0 failed at 306 s with undici's headers timeout, with and without the SDK's own timeout.
- Missing: no source measures silence at byway's request sizes, Anthropic's ping interval, whether a closed stream bills the reasoning done, Google's server-side deadline, or the time limit on fal's Kling app.
- Parked, outside the question: fal's fallbacks to "an equivalent endpoint" (backlog row "fal may serve a clip from another endpoint: its fallbacks are on by default"), and a second-party figure of about 367 output tokens for a GPT Image 2.5 image against the 8,000 `prices.ts` plans.

## Decision

In the owner's words: "Build selectable limits for every model/provider: 15, 30, 45, and 60 minutes" (06:40), per model, with the choice sets and defaults chosen at 09:50 and 12:10, built in block 2, and the design's four choices as the owner answered them at 18:53 (quoted under Context).

1. **Each model has its own wait, chosen in Settings** (the owner's: per model; text 15, 30, 45 or 60 minutes, default 15; images 5, 10, 15 or 20, default 15; video 30, 45, 60 or 75, default 30). The rest is Claude's:
   - A section "How long to wait for an answer", below "Model profile", one row per model, grouped by provider in the Providers section's order. Each row shows its kind ("Text", "Images", "Video clips"), its choices ("15 minutes (default)") and the one in force.
   - Rows are keyed by provider and model, so claude-opus-5-5 from Anthropic and anthropic/claude-opus-5.5 from OpenRouter are two.
   - Every model the gateway's profiles use is listed, key or no key: 14 today. A model's kind is where the profiles use it (`waits.ts`, `modelWaits`). The mock's models have none.
   - The web API checks each choice against its own model's set (`PATCH /api/waits`, `updateAnswerWait`, a strict body of provider, model and minutes). It refuses minutes the model's kind does not offer, a model no profile uses and the mock's, in plain words. The model list reaches the web through `ServiceHost.modelWaits`, not a new Gateway method.
   - The store takes only the union of the three sets (5, 10, 15, 20, 30, 45, 60, 75), checked in TypeScript, since it depends only on contracts and zod and cannot know the models; the schema checks only a whole number above 0. A new table holds one row per workspace, provider and model (`answer_waits`, migration 9).
   - A row whose model no profile uses is kept but not shown, since models are replaced (gemini-3.1-pro-preview is a preview). A model no one chose for waits its kind's default, and says "Not chosen yet, so it waits the default." A stored choice its kind does not offer is not used, and reads as the default.
   - The help reads: "How long byway waits for each model’s answer before it gives up on the call. For text that streams in, this is how long the model may send nothing. A change applies from the model’s next call; a link of an Ad Video Chain already being made keeps the waits it started with." It then names the defaults, from the data ("15 minutes for text and images, 30 for video clips"). Under the owner's answer of 18:53 it carries no note that a call may be sent twice.

2. **The gateway reads the wait on every call** (Claude's), as it reads the budgets (`CapsSource.waitMinutes`; the runner's `storeCaps` reads it by provider and model). A change applies from the next call.
   - It is read once for a call, before the call is admitted. A wait that cannot be read fails the call before anything is held or sent, with the store's own error.
   - A resend after a stall keeps the wait read for that call. The one retry after a decline ([ADR-0102](0102-one-refusal-rule-for-every-provider.md)) is a call of its own and reads it again; a read that fails there counts as a retry not made.
   - `SpendContext.operation.stepLimitMs` is gone, and `Invocation.limitMs` with it: a call in a step of any length waits its model's wait. `operation.waitMs` takes its place: the wait a relay step read before it began (item 9). The gateway uses it instead of Settings, and hands it to the decline's retry. It is checked as the step limit was (above 0, at most 2^31 − 1 ms); a stale `stepLimitMs` is ignored, not refused.
   - The mock's calls never ask; they keep a text model's default as a nominal bound. `STREAM_IDLE_MS` stays, as the bound for a request that names no wait: a text model's default, fifteen minutes.

3. **One fetch for the text and image clients** (Claude's). The Anthropic, OpenAI, OpenRouter and Google clients fetch through one undici Agent whose headers and body timeouts are 80 minutes, above the longest choice, 75 (`packages/gateway/src/providers/fetch.ts`, `PROVIDER_TIMEOUT_MS`). byway's own deadlines do the timing. It is undici's own fetch with the Agent as its dispatcher, at 7.18.2, the version Node 24.13.1 bundles, pinned exactly as a dependency of @byway/gateway; Node's internals are not reached into. Google's client takes it through `httpOptions.fetch`. apps/web keeps undici out of Next's server bundle, beside the gateway's other third-party packages. fal keeps Node's default fetch: its requests are short (a poll every 2 s), and its upload and result reads have no deadline of their own, so Node's limits bound them.

4. **A streamed answer waits its model's wait in silence.** The stall bound is the model's wait. It restarts at each chunk, so it limits silence, not the whole answer. Before the response begins, the SDKs' own ten-minute request timeout still applies (openai 7.28.0, @anthropic-ai/sdk 0.131.0). A stall is sent once more, as before, and if that send stalls too the call fails with the words of item 8.
   - **Anthropic is asked for summaries** (the owner's "Ask for summaries (Recommended)"): every Anthropic request carries `thinking: { type: "adaptive", display: "summarized" }`, in its body and in the request byway logs (Claude's: both). The model thinks the same; a summary streams while it does, so the wait measures true silence. Answers are read as before, from their text blocks only.

5. **A call answered whole waits its model's wait in all, and is not sent again once it runs out** (the owner's "Give up and end the call plainly (Recommended)"). These are Google's text calls and images and OpenAI's images (`ProviderAdapter.answersWhole`). Claude's choices in it:
   - Each send gets its own deadline at the model's wait (`packages/gateway/src/providers/deadline.ts`): Google's `config.abortSignal`; OpenAI's request signal, with the SDK's own timeout set to the wait plus a minute (`IMAGE_SDK_TIMEOUT_ABOVE_WAIT_MS`). The request byway records leaves the signal out.
   - The deadline is never joined with the run's stop, since ADR-0111 hands these calls no stop: a Cancel still leaves them running.
   - Once it runs out the call fails, not retryable, "may have been billed", and is recorded as waited. That holds only when the adapter's error is not one that billed nothing, as for the stop.
   - Other connection failures are still sent once more, and each send waits its whole wait from its own start.
   - An image step's own tries per slot (`triesPerSlot`, `asset.ts`) still apply after an image whose wait ran out.

6. **A fal clip waits its video model's wait from fal's acceptance** (Claude's, under the owner's video choices and "Give up and end the call plainly (Recommended)").
   - The time fal accepted each job is kept with the job in the spend book (`provider_jobs_at`, migration 10), so a job resumed by a later attempt keeps its clock. A job accepted before migration 10 counts its wait from the resume.
   - When the wait runs out, byway cancels the job and reads fal's answer as for a stop (ADR-0111 items 4 and 5): removed before it ran, nothing is billed and the call is released; asked to stop while running, or a cancel that failed, it may have been billed, recorded as waited with the job's id and fal's answer; already done, the clip is read and kept, since it is paid for.
   - The job is never submitted again ([ADR-0091](0091-provider-edge-billing-fixes.md) decision 2). A clip whose result fal reports done is read without the wait. A clip abandoned as waited can still be resumed by a later attempt of the same key, with its acceptance clock.
   - **fal's start deadline.** The clip job is sent with fal's start deadline under both names: `X-Fal-Request-Start-Timeout` (fal's documentation) and `x-fal-request-timeout` (@fal-ai/client 1.10.1), since which one fal's server honours is untested. It is the wait less about one clip's making: 5 minutes for a clip of up to 5 seconds (Kling 3 Pro's p95), 10 up to 10 seconds, and 15 above that, the report's scaled figure for 15 seconds, which it says overstates (`falStartTimeoutSeconds`; Claude's margins). It is in whole seconds, rounded down, and left out when that leaves a second or less. So a 5-second clip at the default 30 minutes may start up to 25 minutes after acceptance. A job that starts late still has room to finish, so byway rarely pays for a clip it then throws away. The last-frame job carries no start deadline (Claude's reading: the design names the clip's only).
   - **A clip fal dropped at that deadline counts nothing** (Claude's reading, built at W-core's last link, 6a1a1ae, for the design gap the waits builder left). Its result read fails with a 504 whose `X-Fal-Request-Timeout-Type` is "user", which @fal-ai/client 1.10.1 hands on as `status` and `timeoutType` and never retries. byway reads it as not started: not retryable, nothing billed, the call released and not recorded as waited. Nothing is cancelled or sent again, and no frame job follows. fal's word that the job never ran is taken before a stop or the clip's own wait. A 504 without that header is read as before. "Nothing billed" joins two fal pages read on 2026-10-22: the queue page, which says a start deadline that passes gets that 504, and the pricing page, which charges nothing for a request that fails with a status of 500 or more and nothing for queue time. Neither says it in one sentence, and the request-errors page says nothing about billing. The first live C5 run's fal dashboard can confirm it.

7. **The last frame is bounded** (Claude's). The frame extraction, its result read and its download may take the time left on its clip's wait plus 2 minutes (`FRAME_GRACE_MS`). The 2 minutes are a floor, which saves the frame of a clip that finished late in its wait. When that runs out, the frame job is cancelled, best effort, and the clip, made and billed, is kept and in the ledger. The step says "last-frame job {id} did not finish within the time left on the clip’s wait plus 2 minutes, so byway stopped waiting and cancelled it (…)" (the builder's words). That case is not recorded as waited: the clip is settled, and the frame's cost sits inside the clip's bound.

8. **A call that used its whole wait says so, and is recorded as "waited"** (Claude's). Without it a fal deadline would read as a Cancel, and a stall as a lost connection.
   - The spend book takes a third reason a call may have been billed, `waited`, with how long and how it waited (`WaitedFor`: in silence, for a whole answer, or for a clip, with fal's answer to the cancel in byway's words). Migration 10 rebuilds `paid_operations`, since SQLite cannot alter migration 6's CHECK. The reason stays a CHECK and is paired with a new `waited` column by another; rowids, columns and indexes are kept. A resumed call clears it.
   - The words, the design's: for a stall, "{Model} sent nothing for {N} minutes, the wait chosen in Settings, so byway stopped waiting. It may have billed the work. To wait longer, change 'How long to wait for an answer' in Settings."; for a call answered whole, "did not answer within {N} minutes"; for a clip, "did not finish clip job {id} within {N} minutes" with fal's answer to the cancel. {Model} is written "{Provider}’s model {id}", as declines are. "The wait chosen in Settings" is said even when the default applied. A clip fal removed says nothing was billed instead of "It may have billed the work."
   - For a clip fal dropped at its start deadline (item 6), the builder's words: "{Model} did not start clip job {id} in time to finish within {N} minutes, the wait chosen in Settings, so fal dropped it at the start deadline byway set ({M} minutes) and nothing was billed. To wait longer, change 'How long to wait for an answer' in Settings." The design's draft, "did not start within {N} minutes", could not be known to be true, since fal drops the job at the start deadline, before the wait ends.
   - A stall's step failure now gives these words in place of the adapter's technical message, so its count of chunks is gone from what the step says. Settings' Spending records say the same words (`apps/web/src/view/spending.ts`, a copy, since a client component cannot import the gateway), and a test pins the two together.

9. **The steps are sized so the wait governs** (the owner's "Relay from your video wait, 24 h elsewhere (Recommended)").
   - Model steps and image (ASSET) steps run under a 24-hour backstop, with the 30-second heartbeat and the 3 and 2 tries they had (`packages/runner/src/workflow/acts.ts`). Quick steps keep their minute and five tries.
   - The model proxy also carries page renders, a person's step's finish and the rerank; they share it, so they too run under 24 hours with three tries (Claude's reading of "Model and image steps" as the proxies acts.ts names; no split was chosen).
   - A relay step runs on a proxy of its own, under a limit worked out from the waits read just before it (Claude's formula, under the owner's option): 5 times the link model's wait (its two asks, as a builder's, with the decline's retry), plus the video wait, plus 15 minutes for the start frame's upload, the downloads and the frame (`relayLimitMs`, `RELAY_ALLOWANCE_MS`). That is 2 hours at the defaults and 6.5 at the longest choices.
   - A quick step (`relayWaits`) reads the waits just before each relay step. Its result is in the run's history, so every replay and every attempt of the step has the same limit and the same waits. The step hands its link call the link model's wait and its clip, and so the clip's frame, the video wait, as `operation.waitMs`. So a wait changed during a relay step does not change that step's calls (Claude's, the build order the design set).
   - Claude's choices in the build: the waits are read in the runner, through `storeCaps`, the lookup production's gateway reads them with, not by a new Gateway method. The link model is the profile's model for the step's tier (mid unless the step names one), as the gateway resolves a completion that names no model. Demo mode, a mock model and an unlisted profile wait the defaults. Each call carries its own wait on its request (`memo.ts` `withWait`), since one step needs two; the memo key is made without the request's `operation`, so every key is unchanged. `RelayInput.waits` is required. A waits read that fails after the quick proxy's five tries fails the relay step. The claims oracle's stand-in answers the read with the defaults and records no event.

10. **Cancel keeps today's behaviour** (the owner's "Keep today's behaviour (Recommended)"). The run shows Cancelled at once. Streams and fal jobs are cut off as each step hears at its next heartbeat. Google's calls and images finish, are paid, and their cost is added to the run (ADR-0111).
    - Every proxy (quick, model, image, relay) now names Temporal's `TRY_CANCEL`, from one constant (Claude's). An unset type sent the same: `@temporalio/workflow` 1.24.0 sends an unset type unset, which the protocol reads as its 0, `TRY_CANCEL`. But `@temporalio/common` 1.24.0's type docs give `WAIT_CANCELLATION_COMPLETED` as the default. So today's Cancel rested on the encoding, not on the documented default, and an SDK upgrade that brought the two together would have changed Cancel silently. ADR-0111's Context found this while building the true stop; naming the type is new.
    - Nothing changes on the wire: a proto3 zero is not encoded, so a model step's ScheduleActivity command is 102 bytes either way (measured with @temporalio/proto 1.24.0).
    - The run workflow keeps its one cancellation scope, made in `run.ts` and cancelled only there, which ADR-0111's stop rule reads.

11. **The workflow bundle changes once, with block 2's workflow batch.** The step limits, the named `TRY_CANCEL` and the relay's waits are bundle inputs, and land with P2 and VOICE-RETRY in one change. Its pinned hash moved once, from 38afef53… to b0a4e13b… (cc53dcc, `packages/runner/test/build.test.ts`). Runs waiting under the older bundle end plainly at the upgrade ([ADR-0078](0078-runs-from-older-engine-versions-end-plainly.md)). The waits builder's commits changed no bundle input beyond type-only edits, and ran `build.test.ts` unedited. ## Consequences

**What the defaults changed on day one** (the design's list, as built). Before block 2, then after:

- Streamed text calls inside image and video steps (asset briefs, placing, the relay link's call): 45 minutes, then their model's wait, 15 by default.
- Google text and images: about 5 minutes a send, sent once more (Node's fetch gave up), then 15, not sent again.
- OpenAI images: 5 to 10 minutes a send, sent once more, then 15, not sent again.
- OpenAI and OpenRouter streams that send nothing: closed by Node at 5 minutes unless they send keep-alives (not known), then 15.
- fal clips: no deadline of their own (the 45-minute media step, whose second try resumed the clip), then 30 minutes from fal's acceptance.
- A clip's frame extraction: only the media step, then the time left on its clip's wait plus 2 minutes.
- Text in model steps, compose and intake: 15 before and after.
- Step limits: model steps 15 minutes, then 24 hours; image steps 45, then 24 hours; relay steps 45, then 2 hours at the defaults.
- Anthropic's calls: thinking hidden, then summarized.

**How long a call can take at a wait W** (the design, section 3):

| Call | The wait counts | When it runs out | Longest |
|---|---|---|---|
| Streamed text | silence | sent once more | 2W of silence, plus streaming |
| Google text | the whole answer | ends plainly | W (2W after another connection failure) |
| OpenAI or Google image | the whole image | ends plainly | W (2W after another connection failure), per try |
| fal clip | from fal's acceptance | cancelled, never sent again | W, then its frame |

A declined text or image answer is asked once more, as a call of its own; a fal clip is not. A provider's own error answer is sent again, up to four sends, not counted as a stall.

- **A stalled step can take many waits.** A call that stalls twice fails its step for good. Counting the decline's retry: a builder's two asks, 3W, or 5W with declines; a GREAT critic with four shuffles, 9W, or 17W (17 hours at 60); compose, 4W, or 7W; intake, 3W, or 5W. These leave out streaming time, the time before each response and error resends, so no fixed step limit is provably above the worst case, and a step's limit is a backstop. Compose and intake run in the web app's request, with no step limit (backlog row "Recommending and composing hold their web request for as long as the waits allow").
- **A stuck step holds its run.** A step stuck in byway's own code holds its run as Running until Cancel or its limit: up to 24 hours a try, 72 for a model step's three tries and 48 for an image step's two. The heartbeat catches a dead worker, not a hung live one. That was in the option the owner chose. The sweep of 2026-10-22 (B8) found no backlog row saying when to revisit it.
- **A step that times out or loses its worker is tried again.** byway's no-retry list holds its step, budget and rejected-answer failures, and every gateway failure travels as one of them, so Temporal never retries a call that stalled twice; it does retry a step that timed out or lost its worker, and an error byway did not expect. Paid answers come back from the memo. The call still under way is not cut off and is taken over about a minute later ([ADR-0099](0099-paid-operations-keyed-to-their-caller.md)): a text or image call is sent again, so if both answer both are paid; a fal clip is only polled again by its job id, with its clock. A relay step that runs past its limit is tried again with its link answer from the memo and its clip polled by its id, so no clip is bought twice.
- **Cancel leaves the uncut calls running longer.** Google's text calls and images finish after Cancel, now for up to their wait: 60 minutes for Google text, 20 for an image. They are paid either way, and their cost is added to the run. The sweep of 2026-10-22 (B2) found no backlog row saying when to revisit what this costs.
- **Money.** A longer wait holds a call's estimate against the budget longer. Google's SDK says an aborted call is still charged (@google/genai 2.27.0, `GenerateContentConfig.abortSignal`), so a Google call or an image that uses its whole wait is likely billed; it is now not sent again, so it is paid once, not twice.
- **Anthropic's summaries** cost nothing more: Anthropic's public thinking page (read 2026-10-22 for this record) says that on Opus 5.5, Sonnet 5.5 and Fable 5.1 `display` defaults to "omitted", and that "Either way the block is billed the same". The SDK's type docs (@anthropic-ai/sdk 0.131.0, `messages.d.ts`) say the default is "summarized", which is stale. The code's comments cite the claude-api reference, which only Claude can open (backlog row "Anthropic thinking claims cite a source only Claude can open").
- **What the builders did not do.** The frame job is not read for a start-deadline 504, since it is sent with no start deadline, so a mutation removing the clip-only condition would go uncaught. No test through the engine and the real fal adapter raises a wait during a relay step; that is tested at the activity level with the real memo, and the engine tests read the scheduled limits and the inputs' waits from history. W-core's last link ran the claims oracle at its default size only. The Settings section adds 14 selects before the renderer's sandbox switch, which a browser test reaches by pressing Tab at most 40 times (the waits builder estimated about 26); the browser suite had not run when the builders finished, so the block's CI shows it.
- **The live checks the design names** (Claude's):
  - fal's start-deadline headers: the owner's own first C5 run (the option the owner chose on 2026-10-21 at 21:31 said "C5 is held out of the first live runs and only you run it."). In fal's dashboard, find each clip by the id byway records: completed, billed once, no request refused. That shows fal accepts the headers, not that it honours them. The same dashboard can confirm the reading of a dropped clip as nothing billed (item 6).
  - The lifted image caps: the first image-making run, C3 on Balanced (one Gemini image), and OpenAI images first on Best or OpenAI. An image takes about a minute, so this shows the fetch works; the local test shows the cap is gone.
  - The choice sets and defaults against byway's own call times: backlog row "Check the answer waits against live call times", after the first live runs.
- **Backlog rows.** This record builds "Selectable answer waits per model (block 2)", answers "Block 2 (P2): the activity proxies' cancellation type and the one cancellation scope" (item 10), and answers "A clip fal drops at its start deadline is counted as "may have been billed"" (item 6).
