## Context

Cancel refused new provider calls, but a call already in flight ran to completion and was billed (backlog row "Cancel stops calls already in flight", ENG-4's remainder). The audit of 2026-10-21 put it to the owner at 19:59: "D2. When someone presses Cancel, a model call already under way still finishes and is paid for, and the Cancel question doesn't say so. What should batch B do?" The owner chose "Build a true stop now", whose description read "Medium change: each provider call gets an abort; an aborted call is recorded as 'may have been billed' unless the provider reported usage; a short ADR. Only Anthropic's streamed calls are sure to stop mid-answer; for others an abort may not stop the bill and loses the result." Asked "The true stop (D2) and P2 (D3) change how calls and runs work. Before building them, should I show you a short design for each?", the owner chose "Yes, short designs first (Recommended)".

Claude's design ([evidence/designs/2026-10-21-true-stop.md](evidence/designs/2026-10-21-true-stop.md), as shown to the owner) was checked against the code at a002e60 and the providers' pages. What those pages say, as the design and then its build read them on 2026-10-21:

- Anthropic's streaming page does not say what a closed stream bills.
- OpenRouter's streaming page says that aborting a streamed request, for the providers it lists (Anthropic and OpenAI among them), "immediately stops model processing and billing", and that a request not streamed, or to a provider it does not list, is billed for the complete response. byway's OpenRouter and OpenAI chat calls were not streamed.
- Google's SDK abort is client-side only and still charged (the design's reading of the SDK).
- fal's queue page: a cancel answers 200 `{"status": "OK"}` when the job was in the queue and fal removed it ("it does not run"), 202 `{"status": "CANCELLATION_REQUESTED"}` when it is running ("The request can still complete"), 400 `{"status": "ALREADY_COMPLETED"}` when it had finished, and 404 when there is no such job. It does not say how a cancelled job is billed; its FAQ bills Model API endpoints for inference time only.
- No provider reports a cut-off answer's output tokens: Anthropic sends them in `message_delta` at the end, OpenRouter in a stream's last chunk, and OpenAI only in a last chunk when asked (`stream_options.include_usage`), which "may not" arrive when a stream is interrupted (OpenAI's chat streaming reference).

The design offered five choices, each with a recommendation. The first: "Which providers' calls does Cancel cut off in this change?", recommended "Anthropic's streams and fal's queue jobs only; OpenAI, OpenRouter and Google calls finish and are paid for as today, and a backlog row holds streaming OpenAI and OpenRouter (Recommended)", against "Also switch OpenAI and OpenRouter chat calls to streaming now, so Cancel can cut them off too". Asked at 23:04 "The true stop (design file 1): build it as designed? Its five choices, with my recommendations: cut off Anthropic's streams and fal's queue jobs only (the others are billed in full anyway); count a cut-off call as 'may have been billed' at its reservation; one fixed Cancel sentence; Settings uses the existing 'interrupted' reason; a fal job removed before it ran counts nothing.", the owner chose at 23:05 "Approve, and stream OpenAI/OpenRouter too", whose description read "As the first, but also switch the OpenAI and OpenRouter chat calls to streaming so Cancel can cut them off; this changes how their usage, cost and refusals are read just before your first live run.", over "Approve with all five recommendations (Recommended)" ("Build it in Block 1 as the design says, with an ADR that quotes your answer and names my choices.").

Found while building it (Claude's correction of its own design): the design said a run reaches Cancelled only once its steps in flight have ended, because the activity proxies use Temporal's default cancellation type. They set none, and the SDK sends an unset type as the protocol's 0, `TRY_CANCEL`, though its documentation names `WAIT_CANCELLATION_COMPLETED` as the default. So the workflow does not wait: the run shows Cancelled at once, and each step hears of the cancel at its next heartbeat. In `liveness.test.ts` every one of the 33 cut-offs (1 in the single-call test, 32 at the fan-out's peak) heard it as `NOT_FOUND`, the workflow having closed by then, never as `CANCELLED`. The stop rule's second branch (any other reason, with the store showing the run ended) covers this, so the workflow bundle does not change; making the workflow wait would change it.

## Decision

In the owner's words, the answer to the design (2026-10-21 23:05): "Approve, and stream OpenAI/OpenRouter too", described as "As the first, but also switch the OpenAI and OpenRouter chat calls to streaming so Cancel can cut them off; this changes how their usage, cost and refusals are read just before your first live run." The design's other four choices take its recommendations, quoted in items 4 to 7.

1. **When a call is cut off: only when its run is ending** (Claude's rule). Temporal's cancel of a step carries a reason. `CANCELLED` means the workflow cancelled the step's scope; the run workflow has one cancellation scope (`run.ts`) and cancels it only on Cancel, on "Stop the run" and on a failure, so the run is ending and the call is cut off. Any other reason (`NOT_FOUND` once the workflow has closed, `TIMED_OUT`, `WORKER_SHUTDOWN`, `PAUSED`, `RESET`) cuts the call off once the store shows the run ended (done, failed or cancelled). The stop asks the store when the cancel comes, and again every second while the run is going, until the step's invocation ends; a failed read is asked again. That is Claude's choice, made in block 1's fix round on 2026-10-22 (RS-2): Temporal cancels an invocation only once, so a step that heard a timeout or a lost worker with its run going kept its call, and a later Cancel never cut that call off. Until the run ends nothing changes: another attempt takes the call over ([ADR-0099](0099-paid-operations-keyed-to-their-caller.md)), or byway's clean stop hands it back. `liveness.ts` makes a `stop` signal from this rule, and the activity wrapper adds it to the step's `SpendContext.operation` beside `until` and `cancel`, after the request is hashed, so memo keys do not change. Pause cuts nothing off.

2. **What a stop does, for every provider.** Once it aborts, nothing more is sent for the call: no first send, no resend, no further queue job; a retry's wait ends at once, and the last attempt's error is the call's. The decline's one retry ([ADR-0102](0102-one-refusal-rule-for-every-provider.md)) carries the same stop, and a cut-off retry ends the call as it is, not as a final decline. The stop is looked at after the wait and before the resend's retention ([ADR-0095](0095-paid-calls-have-a-durable-spend-book.md)), which now comes just before the resend rather than before the wait (Claude's), so a call that is not sent again retains nothing.

3. **Which calls are cut off.** The gateway hands the stop only to adapters that declare it (`ProviderAdapter.cutsOff`):
   - Anthropic's streams, closed through the SDK's `signal`;
   - OpenAI's and OpenRouter's chat calls, now streamed (item 8), closed the same way;
   - fal's queue jobs: nothing more is submitted (no last-frame job), and the job under way is cancelled over fal's REST queue API, `PUT https://queue.fal.run/<app id>/requests/<request id>/cancel`, sent once with no redirect followed, because the SDK's own cancel resolves the same way for a removed job and a running one (Claude's);
   - the demo's mock, so the demo and the tests take the same path; it reserves $0, so a cut-off mock call counts nothing.
   Google's calls and every image call are handed no signal (Claude's): they finish and are settled at their true cost, as before.

4. **What a cut-off call counts.** The owner-approved recommendation: "As 'may have been billed' at its reservation, listed in Settings until you clear it (Recommended)". A call cut off after it was sent has no ledger entry, since no answer came to settle; the spend book counts it at its reservation as "may have been billed", against the workspace only, until it is cleared in Settings. Not the audit's partial-usage half: no provider reports a cut-off answer's output. Exceptions:
   - Stopped before anything billable was sent: released, counting nothing.
   - fal answers 400, already completed: the clip was made, so it is settled at its seconds and price through the made-and-billed path, without downloading it. A job fal reported done before the stop is treated the same, without a cancel.
   - fal answers 202, or the cancel fails (404, another answer, no answer): "may have been billed", listed with the job's request id (Claude's).
   - An answer that arrives as the stop comes is settled at its true cost (Claude's; the design's risks said it would be thrown away).

5. **A job fal removed before it ran.** The owner-approved recommendation: "Nothing (Recommended)". A 200 releases the call. This is Claude's reading of fal's queue page and FAQ, not a documented billing rule.

6. **How Settings names a cut-off call.** The owner-approved recommendation: "Under the existing 'interrupted' reason, with its words widened to name a cancelled run; the database does not change (Recommended)". The spend book's `abandon` takes a reason ('failed', the default, or 'interrupted'); the schema's CHECK already allowed both. A call is recorded as interrupted only when it was cut off mid-call; one whose last attempt failed and was then not sent again keeps 'failed'. The words (Claude's): "byway stopped waiting for {provider}'s answer (its run was cancelled or ended, byway stopped, or it lost its connection), so it never learned the cost."

7. **What the Cancel question says.** The owner-approved recommendation: "One fixed sentence, true for every profile: 'Cancel this run? What it made so far is kept. An AI call already under way may still be paid for: byway cuts it off where the provider allows, and otherwise the run stops when it returns.' (Recommended)". Its words are adjusted (Claude's), because with OpenAI and OpenRouter streamed "where the provider allows" claims more than byway does (OpenAI's image calls are not cut off), and because the run stops before its calls return (Context): "Cancel this run? What it made so far is kept. An AI call already under way may still be paid for: byway cuts off text and video calls, except Google’s text calls, and other calls finish after the run stops." The question describes its group (`aria-describedby`), as ConfirmPanel's does, so a screen reader reads all of it; the group has no name of its own (since block 1's fix round, B-cancel-label-repeat: its `aria-label` repeated the question). The Cancelled panel adds, and since block 1's fix round so does the Failed panel, because a failure ends the run and cuts off its other calls in flight the same way (item 1; RS-4): "If byway cut off an AI call that may have been billed, Settings lists it under Spending records; it counts at its estimate against the workspace budget, not this run’s, until you clear it." (`CUT_OFF_NOTE`, `apps/web/src/view/labels.ts`.) Those words are Claude's, made exact in that round (RS-6): until then the note read "If byway cut off an AI call, Settings lists it under Spending records until you clear it.", which also took in the calls that are not listed (one stopped before anything was sent, or a fal job removed before it ran, is released; one whose answer or clip came anyway is settled in the run's cost, item 4) and left out the workspace charge.

8. **OpenAI's and OpenRouter's chat calls are streamed** (the owner's choice), read so that the guarantees of [ADR-0091](0091-provider-edge-billing-fixes.md), [ADR-0095](0095-paid-calls-have-a-durable-spend-book.md), [ADR-0099](0099-paid-operations-keyed-to-their-caller.md), [ADR-0102](0102-one-refusal-rule-for-every-provider.md) and [ADR-0109](0109-money-path-before-the-first-live-run.md) hold:
   - OpenAI is asked for its usage (`stream_options: { include_usage: true }`), which comes in a last chunk whose `choices` is empty. OpenRouter always sends usage, with its cost, in a stream's last chunk, and calls that option deprecated with no effect, so it is not asked.
   - The chunks are joined into one answer (the first choice's text and refusal deltas, the last finish reason, the first model and OpenRouter host named, the chunk that carries usage) and parsed by the same code as before. So OpenRouter's reported cost still takes precedence over the price table, `cached_tokens` and `cache_write_tokens` are priced at their own rates, a refusal and a content-filter stop are declines asked once more on the same model, and a length stop is a cut-short answer.
   - Claude's readings where a stream does not end whole:
     - An error chunk after the 200 (OpenRouter documents them, with a choice whose finish reason is "error"), or a stream that ends with no finishing chunk, may have been billed: it is sent once more at most, with that attempt retained, as for a lost answer. This is unlike Anthropic's mid-stream error events, which [ADR-0091](0091-provider-edge-billing-fixes.md) reads as unbilled.
     - A stream that finished but whose usage chunk never came was answered and billed at a cost byway cannot read: it is settled at its planning figures, marked as an assumed price.
     - A stream that broke after its finishing chunk is settled, since its answer arrived.

9. **A stopped step ends as cancelled** (Claude's). When its stop has fired, the activity wrapper ends the step with Temporal's `CancelledFailure`, whatever the step was left with, so Temporal records a cancel and does not try the step again for a run that is ending.

10. **The workflow bundle does not change.** The work is in the gateway, the store, the runner's activities, contracts' types and apps/web. `build.test.ts`'s pinned hash, `38afef53ed613c48e1065255bdbac69c9016af95a156b0559634e67625e0b637`, passes unedited before and after.

## Alternatives considered

- **"Approve with all five recommendations (Recommended)"**: cut off Anthropic's streams and fal's queue jobs only, and let OpenAI's, OpenRouter's and Google's calls finish, with a backlog row for streaming OpenAI and OpenRouter. Not chosen: the owner chose to stream them now.
- **"Settled in the ledger from what the provider reported, with the output estimated from the text received, marked as an assumed price"**. Not chosen: no provider reports a cut-off answer's output, and an estimate would likely understate the bill and take the call off the list checked against the provider's dashboard.
- **"Words that name the calls under way for this run and their providers, read from Spending records when the question opens"**. Not chosen: the calls under way can change between opening the question and pressing Cancel run.
- **"A reason of its own ('cut off when its run was cancelled'), which needs a store migration adding a column"**. Not chosen: the person does the same thing either way.
- **"'May have been billed' at its reservation, until you clear it"**, for a fal job removed before it ran. Not chosen.
- **Making the run wait for its steps** (Claude's, not put to the owner): setting `WAIT_CANCELLATION_COMPLETED` on the activity proxies, so the run reaches Cancelled only once its calls have ended. It changes the workflow bundle, which this change must not do; block 2 carries the one bundle change, so it is reported there rather than done here.

## Consequences

- Cancel cuts off a run's Anthropic, OpenAI and OpenRouter text calls and its fal clips as each step hears of the cancel, a heartbeat after the run has stopped (about two seconds), rather than when they return. Google's calls and every image call still finish after the run stops, are paid for, and their cost is added to the run.
- A cut-off call counts at its reservation until it is cleared, and a reservation plans the whole output allowance, so it can be well above the bill. Whether a closed stream is billed for its input only, for what it generated, or in full is documented by none of Anthropic, OpenAI or OpenRouter for their own APIs; OpenRouter's page says its abort stops billing for the providers it lists. If a provider bills a cut-off answer in full, Cancel saves nothing there, and its cost is only estimated.
- A job fal is already running may still finish (its 202 answer), and is counted as "may have been billed".
- The first live run (C4 on Balanced) makes no OpenAI call: its text is Anthropic's, and C4 has no critic of another family. The second (C3 on Balanced) makes one when an OpenAI key is set: its critic is of another family (`family: 'other'`, as C6's and C7's are), and the Balanced profile's other-family model is OpenAI's `gpt-6-astra`, so that critic's calls are streamed OpenAI calls. (Until the check of the first block, this bullet said the first run's steps could ask another family; a refuter of TS-MONEY-2 found C4 has no such step, `packages/catalog/src/c4.ts`.) Streamed calls' stored requests now carry `stream: true` (and OpenAI's `stream_options`), and their stored responses are the joined answer with a note of how many chunks came and whether usage did.
- OpenAI has gated the streaming of some of its frontier models behind organisation verification: community reports of 2025 quote "Your organization must be verified to stream this model" (HTTP 400, on `stream`) for o3, gpt-5 and gpt-5-mini, which, by one report, the same organisations could call unstreamed (as the check of the first block read them; it uses no keys, so it could not try the model). Nothing found on 2026-10-22 says whether `gpt-6-astra` carries the gate; its model page lists streaming as supported with no note on verification, but so does gpt-5's. If it does and the owner's organisation is not verified, each streamed `gpt-6-astra` call is refused with that 400, which byway reads as an invalid request: not retried, counting nothing, and the step fails, where the same call unstreamed would likely have run. The money stays right, and the run fails at its first such call (on C3 on Balanced, its critic). The owner chose on 2026-10-22 at 01:54 "Record it and add a check (Recommended)", whose description read "ADR-0111 names the risk, and the first-live-run steps add: before an OpenAI run, confirm your organisation is verified (or that gpt-6-astra streams for it). No code change." ([evidence/conversation-continued.md](evidence/conversation-continued.md)). So this bullet names the risk, the backlog row "First live run with real keys and real money" has the check, and no code changed (the check of the first block, TS-MONEY-2).
- An OpenAI or OpenRouter error chunk mid-stream now costs one resend with that attempt retained, where the same failure as an HTTP error before the 200 is read as before.
- Reading `CANCELLED` as the run ending holds only while the run workflow has one cancellation scope, cancelled only in `run.ts`. A source test in `liveness.test.ts` checks that shape; block 2 (P2) rewrites the interpreter, so it must keep it or revisit this reading.
- The run shows Cancelled before its steps have ended, as it did before this change; in practice its steps hear `NOT_FOUND` and are cut off by the store's word.
- A step that heard a timeout, a lost worker or a stopping worker while its run was going reads the run's status from the store once a second for as long as it lasts (one SQLite read each), and its calls are cut off within about a second of the run's end (item 1). A text call kept that way is cut off for the rest of its stream. After a timeout the next attempt resumes an accepted fal job by its request id ([ADR-0099](0099-paid-operations-keyed-to-their-caller.md)), so when the run then ends, both attempts send fal's REST cancel for that one job. fal's queue page does not say what a second cancel of a job answers. Each answer acts on the one row by the state it finds, not by when it arrives: a clip already made settles it, whatever the other answer did; a 200 "removed" releases it, clearing a "may have been billed" mark the other attempt's answer set; and a 202 "requested", or a cancel that did not go through, marks it "may have been billed" only while it is still open, sent or accepted. So a 202 and a 200 for one job count nothing, whichever came first, and so do a 200 and a failed cancel (Claude's reading of the spend book's `settle`, `release` and `abandon`, which are keyed by the row, not the attempt; check it against fal's usage records with the readings above).
- The billing readings no provider documents (closed streams, fal's 200, OpenAI's and OpenRouter's mid-stream error chunks) join the assumptions the first live runs' ledger is to check against each provider's usage records.
- Tests (none asserts on the clock: each fake answers only when its signal aborts, or aborts the stop itself at the moment under test; the stop rule's repeated reads and the bound on a stalled stream run on fake timers; a time limit only stops a wait that hangs): `packages/gateway/test/cut-off.test.ts` (Anthropic held until cut off; a stop during the retry's wait; Google and image calls handed no signal and settled; the mock; OpenAI's and OpenRouter's streamed parse, including a stream cut off before its usage arrived, an error chunk, a missing finishing chunk and a missing usage chunk; fal's 200, 202, 404 and 400 answers and its REST cancel); the spend book's contract suite (`abandon` with a reason); `packages/runner/test/liveness.test.ts` (the stop rule, including its repeated reads after a timeout, a lost worker or a stopping worker until the run ends; the one-scope source check; through the activity wrapper: a stopped step ending as cancelled, `WORKER_SHUTDOWN`, `TIMED_OUT` and `NOT_FOUND` with the run going cutting nothing off and keeping the answer, and a step that heard `TIMED_OUT` cut off once the run ends; through the real workflow: Cancel cutting off a held call, a call byway does not cut off finishing and its cost catching up, and the review's F02 cancel at the composed limits' peak, 32 calls at once, both cut off and released, each checked against the run's Temporal history (SUB-DA-4); and the worker's shutdown, checked by the slow call still in flight rather than by elapsed time; the repeated reads, the wrapper's cases, the history checks and the shutdown check since block 1's fix round, RS-1, RS-2, RS-3 and RS-7); `packages/runner/test/memo.test.ts` (memo keys unchanged with a stop); and Settings' and the Cancel question's words in apps/web.

## What this changes in earlier records

- [ADR-0099](0099-paid-operations-keyed-to-their-caller.md): `SpendContext.operation` gains `stop`. A cancel that means the run is ending now cuts the call off; a timeout, a lost worker or a stopping worker still hands it over while the run is going, as item 3 of that record says, and if the run ends while that step's invocation lasts, its call is cut off then (item 1).
- [ADR-0095](0095-paid-calls-have-a-durable-spend-book.md): the book's `abandon` takes a reason, and a cut-off call is listed as interrupted. A resend's retention comes after the retry's wait, just before the resend, and nothing is retained when a stop ends the wait.
- [ADR-0091](0091-provider-edge-billing-fixes.md): nothing is sent again after a stop, whatever the billing reading allows. Its classification gains the streamed OpenAI and OpenRouter readings of item 8: an error chunk or a missing finishing chunk is `maybe`. Since block 1's fix round (Later notes), a stream that sends nothing for fifteen minutes (or for its step's own longer limit, an image or video step's forty-five; the Later notes of 2026-10-22) is `maybe` too, Anthropic's included, and after a stop an error that billed nothing by its own reading is released rather than counted as cut off.
- [ADR-0102](0102-one-refusal-rule-for-every-provider.md): the retry after a decline carries the stop, and a cut-off retry ends the call as it is, not as a final decline.
- [ADR-0109](0109-money-path-before-the-first-live-run.md): its item 7's assumption, a mid-stream error event treated as unbilled, now covers Anthropic's streams only; OpenAI's and OpenRouter's, which this record adds, are counted as "may have been billed".
