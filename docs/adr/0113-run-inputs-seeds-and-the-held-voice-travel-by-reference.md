## Context

Until this record, every step the engine scheduled was handed the run by value:

- the brief, with all its attachments (`RunRef.problem`, copied into each step by the interpreter);
- every SEED string handed out so far (`RunRef.seeds`);
- the fixed copy deck and every VOICE answer (`ports.voice`, `ports.held`);
- the person's own tell catalog, which went to every model step.

Start accepts 20,000 characters plus five attachments of 200,000 each: about 1 million characters, or about 3 MB of Chinese or Japanese. Temporal refuses one value over 2 MB and one scheduling batch over 4 MB. So a large brief, copied into a fan-out, could leave a run stuck in "running" with nothing spent (the external review's F02). [ADR-0098](0098-recipe-limits-disclosure-and-held-voice.md) left this to the backlog ("Run inputs are still carried by value"). On the old code, a demo C2 run on the largest brief the web accepts, in Chinese, failed at its start with Temporal's "Blob data size exceeds limit".

[ADR-0081](0081-voice-writes-the-persons-copy-exactly.md) parked VOICE-RETRY. When C5's launch gate fails, the run re-enters D2 from the ports D2 started with (`RetryStage`). So the copy the person wrote at the first late VOICE is not in the second pass, and the second late VOICE offers the AI's copy. A person who sends it back unchanged ships the AI's copy. ADR-0081 left the fix to the owner.

## Decision

In the owner's words, the answer to the design (2026-10-21 23:05): "Approve, and price long-context tiers in W". This record covers the design's P2, its VOICE-RETRY and its riders, built as the design says, with its first three open choices as recommended. The long-context tiers that answer added are in [ADR-0115](0115-the-price-table-kept-current-and-priced-by-tier.md). Each choice marked "Claude's" is Claude's, in the design or in the build, and was not put to the owner.

1. **The brief is stored once.** `Runner.start` writes the brief (its text, fields and attachments) as one JSON file in the content-addressed store, and starts the workflow with its id (`RunInput.problemId`). Every step carries the id (`RunRef.problemId`). A step that fills the problem slot reads the file once (`ArtifactReader`). `StartRunInput`, which the web app, the CLI and the tests call, does not change, and neither does the run record. Claude's, in the build (`packages/runner/src/stored-inputs.ts`):
   - The file is canonical, compact JSON in a fixed order: text, deliverable, audience, constraints, attachments, and for each attachment its name, then its text. Absent fields are left out. So a start sent twice, or the same brief with its fields in another order, is the same file and the same id, and still starts one run. JSON escapes a lone surrogate, so any brief reads back exactly.
   - The inputs are written after the recipe and engine checks and before the run record. So a refused start stores nothing, and a failed write leaves no run behind.
   - The names: `RunInput.problemId` and `RunRef.problemId`, `RunInput.inputs.{voiceId, draftId, tellsId}`, `ModelStepInput.tellsId` and `OpenCheckpointInput.initial.draftId`. The renames make every old site fail the typecheck.

2. **The fixed copy deck, the author's draft and the person's tell catalog are stored once too.** Each is a text file written at start, and the start input carries their ids beside the references, which were ids already. The deck's id is the first `ports.voice`. The model step reads the tell catalog by id, and the own-draft question reads the draft by id. That the draft and the tells move is Claude's, in the design: "the rows name the brief and the deck. The draft and the tells are the same kind of input, so they move too." Claude's, in the build: an empty deck, draft or catalog is no input and is not stored, as the interpreter treated an empty one as absent; one holding a lone surrogate is refused by the store before any run exists; and the deck is read only by a step that takes the person's words in or is held to keep them, so a lost deck file stops no other step.

3. **SEED strings stay in the store.** `RunRef` no longer carries the seeds. Each step call's seed is kept as a memo under `seed/<call key>`, and one new read-only Store method on the existing memo table reads the run's range (`memosWithPrefix`, no migration). Every PR3 check (the builder's check, the direction note's redaction, the person's own draft, the claim log, VOICE, and asset and relay writes) reads the run's seeds from there, after the step's own seed is kept. So PR3 now sees every seed handed out so far, a sibling's or an earlier attempt's included: stricter, never looser (the design).
   - **The batch bound loses its seed term** (Claude's, in the design): `ACTIVITY_BYTES` has no bytes per seed, the work bound no seed count, and ST3's batch message names "the options and their views in every one". The 2 MiB engine bound stays as it was (Claude's, in the design). A recipe refused only for its seeds is now admitted, as the design said it would be: 300 seeds then each over them, and replicate(300, seq(seed, X)). No catalog verdict changes.
   - **The base is 896 bytes**, not 1 KiB (Claude's, in the build). With the seeds gone, 1 KiB put the seed fan-out's bound at 2.02 times its heaviest batch, past [ADR-0098](0098-recipe-limits-disclosure-and-held-voice.md)'s "at least half". An input with empty ports weighs about 420 bytes beside its step, and Temporal's command about 160 (encoded with `@temporalio/proto` 1.24.0). The four measured shapes now bound at 1.06 to 1.81 times their heaviest batch. W-core's last link measured a fifth shape, twelve relay chains of two links each with the waits at their longest choices: 1.15 (Claude's; the map asked only for the four again).
   - Claude's, in the build: the method is generic (a run id and a prefix, matched exactly, not by LIKE or GLOB), so the store knows nothing of seeds; the seeds sit apart from the run's other memos, whose keys start with the run's id or `lineup/`; `ModelStepResult.seed` goes, since the workflow no longer collects seeds; and the person's write paths read the seeds outside the pure guard, so a store error is retried rather than shown to the person.

4. **The held voice travels by id.** `finishHumanStep` keeps each VOICE answer, the claim log's included, as a text file and returns its id (`FinishHumanResult.voiceId`). An empty answer is an empty file. `ports.voice` and `ports.held` hold ids. `keptVoice` reads the held answers and the latest words from their files, each text once and the latest last, as before. The voice slot reads the latest words, only for a step that takes them in. Claude's, in the build: an answer is kept with no artifact event, and a VOICE write whose answer comes back without an id stops the run, since words that cannot be held cannot be protected: "byway could not keep your words from step "{id}", so the run stopped before any step could change them."

5. **A file a run needs and cannot read fails its step plainly.** The step fails with a `StepError` that is not retried, for the store's not-found and corrupt codes; any other store error is left to Temporal's retries. The words are Claude's:
   - for a start input: "The {brief, copy deck, draft or tell catalog} this run started with cannot be read: its file ({id}) is missing or damaged in byway's data folder, perhaps from a partial restore (see "Back up and restore" in the README). Start the run again.";
   - for an answer, an id the run holds in `ports.held`: "Your words from an earlier step of this run cannot be read: their file ({id}) is missing or damaged in byway's data folder, perhaps from a partial restore (see "Back up and restore" in the README). Start the run again."
   The start-up report ([ADR-0096](0096-partial-restores-reported-at-start.md)) is unchanged (`data-check.ts`). These files are ordinary artifact rows that no event names, so a missing one is listed with no run named (Claude's).

6. **VOICE-RETRY: a gate's retry keeps the person's VOICE answers** (the owner's D9, built as the design's VOICE-RETRY part).
   - The interpreter keeps each VOICE write's answer and the deck it answered, by their files' ids, and carries them across a gate's `RetryStage`.
   - When that VOICE is asked again because the gate sent the run back, the box starts from the person's earlier lines where they still fit the work. On a deck of named fields (C5's headline, tagline and captions, or an options deck), it starts field by field (the owner's "Only the lines you wrote (Recommended)", 2026-10-23, below): a field the person changed from what they were offered comes back as they wrote it, and a field they left as offered takes the work's current value, so the second pass's CUT and swaps stay. That box is offered when it fits the work: the total reader reads it against the work's current fields and the round trip holds. On any other deck (prose, the voice-over script, a diff's "Why:", a claim log), the box starts from the whole earlier answer, and only when the deck has not changed (`sameCopy`).
   - Otherwise the box starts from the work's lines, and the question adds: "Your lines from before the final check sent the work back could not be kept, because the work's lines have changed since. You had written: "…". The box starts from the work's lines: write yours again where they still fit."
   - The design's two details (Claude's): "unchanged" is measured against the work's own deck, not against what the box started from, so sending the earlier lines back writes them; and on a web page the question names the earlier lines but never fills them in: "Before the final check sent the work back, you had written: "…". A page's lines are read again from the browser, so they are not filled in here: write them again where they still fit." No catalog recipe reaches the page case, since C5 has the only gate.
   - Claude's, in the build:
     - Answers are kept by the VOICE's place, its step id and candidate path, so each fan-out branch keeps its own. Every retry carries the latest answers. The VOICE asked again takes its own once, so a later round of it in that pass is asked as any round is.
     - An earlier answer that changed nothing it was offered, or that already equals the work's lines, is not used, and no note is added. No note is added when the lines fit either: the design names one only for lines that do not.
     - The quote is the answer's non-blank lines that were not lines of the deck it answered, at most five, each cut to 80 characters, then "; and N more". It goes after the workflow's question and before a page's rules, and re-asks do not repeat it.
     - Each VOICE write keeps the deck it answered as a text file too (`FinishHumanResult.deckId`), and the deck a box started from is passed by id. A lost deck fails the step with "The lines of the work this step offered cannot be read: their file ({id}) is missing or damaged in byway's data folder, perhaps from a partial restore (see "Back up and restore" in the README). Start the run again."
     - Re-asks keep ENG-6's quotes of what the box first offered, while the deck sets what "unchanged" means across them.
   - **Field by field, at the owner's answer of 2026-10-23.** As first built, the box started from the whole earlier answer (Claude's reading of "the box starts from your earlier lines"). So a field the person had left as offered brought back the first pass's text, and sending the box back undid the second pass's CUT and swaps without saying so. Block 2's check found it (WORKFLOW-1). Asked at 01:18 (the question is quoted under Decided by), the owner chose at 01:41 "Only the lines you wrote (Recommended)", whose description read "Field by field: a field you changed from what was offered comes back as you wrote it; a field you left as offered follows the current work, so your later CUT and swaps stay. If the result no longer fits the work, the box starts from the work's lines and quotes yours, as today." It was built in 5198a57 (fix/fx-b2f-voice, merged into block 2 at c126f43), on the activity side only, so the workflow bundle's pin did not move. Claude's readings inside the answer:
     - A field is changed when its value, as the total reader reads it, differs from its value in the deck the person answered. So a change of layout alone (a label's case, trailing spaces, blank edges, a value moved to the line after its label) is no change.
     - The box is built only while the work's deck has the fields of the deck the person answered (the same shots in the same places, the same number of options) and reads field by field. Otherwise the result is taken as no longer fitting: the box starts from the work's lines and the question quotes the person's, as before. A caption or an option's lines belong to their place in the work, so fields are not matched by label across a changed number of shots.
     - A built box is offered only while it fits the work (`applyCopy` and the round trip); otherwise it falls back the same way. A built box equal to the work's lines is treated as an answer equal to the work: the box is the work's lines, with no deck kept and no note.
     - The box is written in the deck's standard layout (as `extractCopy` lays one out), not exactly as the person typed it; the difference is layout only.
     - Prose, the voice-over script, a diff's "Why:" and claim logs keep the whole-answer rule, only while the work's deck has not changed: those decks have no fields that pair a line of the person's with a line of the work.
     - On a second retry, a field the person wrote whose text the work already held on the pass before counts as left as offered, and follows the newest work.
     - No note in the box names the fields where the person's line differs from the work's current line; the owner's answer adds none when the result fits.
   - C5's e2e assertions that recorded the old behaviour are flipped: the second late VOICE starts from the person's headline, the drive sends it back unchanged, and the delivered storyboard carries it. They hold under the field-by-field box too, since the demo writes the same on-screen copy on both passes, so they cannot tell the two rules apart; `voice-retry.test.ts` pins the field-by-field box, through the interpreter and on the real activities (backlog row "C5's end-to-end retry check cannot tell the field-by-field box from the whole-answer one").

7. **The riders the design names.**
   1. **helper.voice.apply is retired** (aa453c2): the `voice.apply` id, the five templates, the mock's responder and their tests go. A purpose `voice.apply:<medium>` is now unknown.
   2. **VOICE's prompt suffix moves as far as it can** (Claude's, in the design): only its fixed sentence, "One line per block of text; leave a line empty to remove its text.", moves into the workflow's wording (`PAGE_LINES_RULE`, `workflow/wording.ts`). The rest is read from the page and stays in the activity, since the copy code may never be bundled into the workflow ([ADR-0081](0081-voice-writes-the-persons-copy-exactly.md)). No shown text changes: a page VOICE's stored prompt is the same byte for byte. Claude's, in the build: the workflow adds the sentence only when the work is in front of the VOICE, the condition under which the activity reads a page, so a page VOICE with no work still gets no page rules; and the VOICE-RETRY note stays before the sentence, where it was before the page's rules.
   3. **C3's optional "advice" field is in the output-contract table** (5943a62): `OUTPUT_CONTRACTS['image-briefs']` gains `"advice"?:string`, with "("advice" only where the template says advice: yes: one short sentence for the person, at most 200 characters)". The line's wording is Claude's, from the template and spec §3.3. No template, parser or shown text changes.
   4. **C7's in-place prompt is keyed on the brief** (Claude's, in the design): "Answer the questions below in place…" shows only when the brief being revised came from the interview prompt. Any other brief revised in place gets the general question. The catalog's wording does not change. Claude's, in the build: a list of prompt ids in the workflow's wording (`QUESTION_BRIEF_PROMPTS`, today `product.c7.interview`), and a mark on the ports (`briefQuestions`) that every write of the brief sets or clears, a person's always clearing it. The VISION-lite variant is no longer read.
   5. **The one-shot gate's mark** (cfa059a): a gate whose body wrote a critique hands it on with the body's own empty-critique mark, if it had one, in place of the mark the gate was handed, and clears an earlier sweep's hits. A body that wrote no critique hands all three on as they were (Claude's; the build map's literal form would clear the mark there too, and the fix after it would then act on an empty CUT). No admitted recipe reaches the case.
   6. **A declined critique is cleared** (the design's open choice 1, which the owner's answer took as recommended: "row 104, clear a declined critique"). When the person declines an optional step whose body would put a critique in place (`replacesCritique`, on some path), the run goes on with an empty critique, marked, so the writer after it makes no change and its step says "Nothing to apply: you chose not to run the step that would have said what to change" (Claude's words). A declined optional that would put no critique in place leaves the ports as they were. The interpreter clears inside lenses and gate bodies too. @byway/recipe's semantics change with it: the flow walk gains `declined`, which `critiqueFlow` reads as no step's critique being the latest, and `answersReachingWork` as a critique that carries nothing (in a lens or a gate body, as a person's empty answer is there). Claude's, in the build: the cleared critique is an empty string with the mark, so the critique's scope typing does not change.
   7. **What audit, a one-shot gate and each hand on is defined once** (the order Claude's, in the design). First an execution test (9d403f8, `operator-ports.test.ts`): small admitted recipes run through the real Interpreter, and at every step the ports handed in agree with the validator's scope typing. Then a table, `HANDED_ON` in `@byway/recipe/semantics` (ec8b418): an audit and a one-shot gate hand on the critique, each the option set, and every other port goes on as handed in. `scope.ts` and the interpreter both read it. Nothing runs differently, and the test passes before and after the move. Claude's, in the build: `@byway/validator` exports `scopeTyping`, and the runner takes the validator as a test dependency only; and the audit's notes beside the work are no port, so the table leaves them out and the interpreter hands them on beside it.
   8. **The lost-run pass also runs while the engine runs** (the shape Claude's, in the design: "the pass byway runs at start also runs every few minutes while the engine runs. A run that Temporal closed on a payload, batch or history limit is then marked failed instead of staying "running". The pass skips queued runs, because a start may be under way."). It is `reconcileWhilePolling` (`dev-engine.ts`), started once the worker polls and stopped first when the engine stops. The pass at start is unchanged, and still fails queued runs. Claude's, in the build:
      - every five minutes (`RECONCILE_EVERY_MS`), for the design's "every few minutes";
      - both directions, so an orphan workflow is stopped too, as at start; runs from an older bundle are not retired again, since the worker retired them at start;
      - the message stays `LOST_RUN_MESSAGE` ("byway's engine no longer has this run, so it cannot continue. Start it again."), since a message of its own would need the reason read from Temporal's history;
      - passes never overlap (the next is timed from the end of the last); a failing pass is said and never stops the engine; and the engine's stop waits for a pass under way;
      - a pass counts only the runs it closed, which also corrects the start-up report when a run ends meanwhile;
      - what a pass does is said under "engine", in the start-up words ("ended {n} runs the engine no longer has, which cannot continue"), and a failed pass as "could not look for runs the engine no longer has ({message}); it looks again in 5 minutes".

8. **The rows Claude brought into W** (Claude's, in the build map; none was put to the owner).
   1. **An own draft byway cannot read is asked again** (7329432), at the row's trigger "at the next change to finishHumanStep", which item 4 is. `finishHumanStep` throws `AnswerRejected` for a draft `parseArtifact` cannot use, so the workflow asks again with why (ENG-6), and nothing is stored. Claude's: only such drafts; a draft holding a SEED string still fails the run (Consequences).
   2. **Runner.start and a lone surrogate** (b246a51): a test only. A recipe holding a lone surrogate is refused before a run exists and before anything is stored.
   3. **The engine refuses an ASSET slots knob that is not a whole number of at least 1** (45ccae8). `engineProblems` reports it as ST7 `slots` ("ASSET step "{id}"'s slots knob is 0.5; it must be a whole number of at least 1"), so `Runner.start` and the workflow's start refuse such a recipe, as they refuse every engine problem. Claude's: of the row's two fixes, the refusal, not skipping the step before its brief call; every value that is not such a number is refused, a non-number included. The validator already refused such a knob (ST7, 1 to 3), so this closes the path around it. The step's own handling ([ADR-0112](0112-a-placing-answer-that-misses-keeps-the-paid-images-beside-the-work.md) item 6) stays, now reached only by a direct call. No catalog verdict changes.
   4. **A failure during a fan-out** (0ef65e6): the review's reproduction runs through the real workflow (`liveness.test.ts`), with one budget refusal declined. ## Consequences

- **Large briefs no longer stop a run at Temporal's limits.** A run's start input is the recipe plus about 280 bytes (bounded at under 1 KiB), and no step input holds the brief, a seed, the deck, the draft, the tell catalog or a VOICE answer. The heaviest step input measured about 6.5 KB (`inputs-weight.test.ts` holds them under 8 KiB). A demo C2 run on the largest brief the web accepts, in Chinese (over 3 MB of UTF-8), ends done, and every prompt that shows the brief carries it exactly.
- **So very large briefs now run, and spend.** The long-context tiers the owner chose are priced ([ADR-0115](0115-the-price-table-kept-current-and-priced-by-tier.md)). A brief past a model's context window is expected to be refused by the provider with an unbilled 400, and the step fails (backlog row "A brief larger than a model's context window: no check before the provider refuses it").
- **PR3 is stricter.** A write holding a sibling's seed, or an earlier attempt's, is now refused or redacted, where before a step was checked only against the seeds handed out before it was scheduled.
- **A recipe refused before only for its seeds is admitted.** No catalog verdict changes.
- **Storage.** A run stores its brief once, and its deck, draft and tell catalog when given. Each VOICE write stores two small text files, the answer and the deck it answered, and a box that starts from earlier lines stores the work's deck. They are ordinary artifact files, inside the data folder that is the backup unit. A start that names an existing run id with a different brief leaves one file no run uses (Claude's: harmless, like references uploaded for a run that never starts). A run whose id were "seed", or began "seed/", would share the seeds' key range; product run ids are UUIDs (Claude's).
- **A run that lost one of its files cannot go on.** It fails at the first step that reads the file, with item 5's message, and must be started again.
- **What the person sees that is new:** VOICE-RETRY's box and notes (item 6); the messages for a lost file (items 4 to 6); the declined critique's note; the note on a step stopped by a failure; an own draft byway cannot read asked again, with "Your draft could not be used as the {medium}: …" leading the question; and, in the terminal, the lost-run pass's lines. A page VOICE's question is unchanged.
- **Admission changes for composed recipes only.** A person's list, then an optional critique step that does not take the list in, then the fix, is now refused (ST12 `critique-unapplied`): declined, the fix applies nothing; run, the new critique takes the list's place. `critiqueSources` withholds one claim it made before: a fix after a step and an optional holding the same step object (seq(k, optional(k), fix)) no longer "applies k's findings". The row "directionsReactedTo and critiqueSources withhold some true claims" saw its trigger: the change takes away one claim the fix made false and widens none.

A workflow that Temporal keeps running while its workflow task keeps failing (for example, a completion over gRPC's message size) reads as running, so the design's "batch" limit may not be caught. The tests stand in for a limit with a terminate carrying Temporal's history-limit reason; no real limit was hit.
