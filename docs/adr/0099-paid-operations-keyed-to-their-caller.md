## Context

[ADR-0095](0095-paid-calls-have-a-durable-spend-book.md) recorded stage 2 of the spend book for the external review's finding F03 (cluster B, recommendation C) and named what stayed open:

- **Stage 3, operation identity across Temporal's retries.** Temporal runs an activity at least once. It starts a second attempt of a step when the first timed out (the cancel reaches the first in a heartbeat reply, about two seconds later, while it may still be running) or when its worker died. The runner's memo (ADR-0079) records a call's answer only after the call, and a settled call's memo save can take tens of seconds. So an overlapping attempt was admitted as a separate call and both were bought; a dead owner's settled call whose memo was not saved was bought again; and a fal clip the provider had accepted was submitted, and paid for, again.
- **The web process did not hand its calls back when byway stopped** (ADR-0095 decision 5): nothing closed its service host, so a recommending or composing call in flight counted as under way for up to a minute, as a crashed process's would.

The work package also carried the separable P3 of F03 (a run start had no identity of its own, so a start delivered twice started two paid runs) and follow-ups found while merging and verifying earlier work: byway-side failures shared the provider's error code; a ledger line with an empty run or step id was counted under run ""; and four runner-infrastructure faults (the workflow bundle written in place, raw Playwright protocol errors, a shared next dev build folder, unbounded CDN responses in the renderer).

Decisions D1 to D4 stay with the owner and nothing here pre-decides them: Anthropic's server-side refusal fallbacks are on, as today (D1); the renderer's OS sandbox is as it was (D2).

## Decision

1. **A step's paid call has an operation key** (contracts: `SpendContext.operation { key, until, cancel, rebuy }`, `AdmitRequest.operationKey` and `rebuy`; store migration 7 adds `op_key`, unique while held, and `released_key`). The runner's memo layer adds it to each call after hashing the request, so memo keys are unchanged: the key is the run and the memo key; `cancel` is Temporal's cancellation of the attempt (a timeout included); `until` is the end of the attempt's invocation (`Invocation.done`, which the activity wrapper's `finally` aborts). Calls outside a step (the advisor's) carry none and behave as before.
2. **One rule resolves a key, in admission's transaction, before the sweep.**
   - A live row in any state but released and uncertain holds the key: the new attempt is refused `in-flight` (retryable, nothing billed).
   - A row whose provider accepted queue jobs and whose holder is gone (accepted and no longer live, or handed back as uncertain and not cleared) is **resumed**: the new caller takes its owner and lease and polls its stored job ids (`ProviderVideoRequest.resume`; the fal adapter submits only the jobs not listed, and makes no second upload). Nothing more is reserved: the row was counted already.
   - A settled row whose holder has ended answers `settledEarlier`, unless the caller asks with `rebuy`. The runner then looks for the earlier attempt's kept result (its memo) at once, after that answer, and asks with `rebuy` only when there is none: a holder keeps its result before its invocation ends, so a look that follows the answer cannot miss a kept result. (Found while testing under load: freeing the key on expiry let a waiter that looked a moment too early buy the call twice.)
   - Any other row gives the key up (an expired open row is released; an expired sent one becomes uncertain, interrupted), and the new row holds it.
3. **Holding a call.** The gateway's holder registry renews an unsettled keyed call while its caller has neither ended nor been cancelled, so a cancelled or timed-out attempt's call is taken over within one lease (60 s); a settled keyed call until its invocation ends, cancel or not, since its result is still being kept. Settlement itself holds a keyed call for a lease (`Settlement.holdMs`), so a call that answers after its caller stopped renewing it is not taken while its result is kept. The end of the invocation lets it go at once (`SpendBook.letGo`), and a gateway that closes cleanly lets its settled calls go too (`endLeases`).
4. **The runner waits instead of paying again.** A call refused `in-flight` looks for the earlier attempt's memo every 2 s and asks the gateway again every 10 s (its holder may be gone: then the call is taken over or resumed); it honours its own cancel, and after 5 minutes stops with a plain step failure rather than pay again. No workflow code changes: the workflow bundle's hash is pinned in a test, unchanged (ADR-0078).
5. **byway's own failures have their own identity** (contracts: `GatewayErrorCode` `'byway-failure'`, and `GatewayError.billed`). A call the provider answered and billed that byway could not keep or record is `byway-failure`, billed; a call byway did not start (it is stopping, or could not record it as sent) is `byway-failure`, not billed; provider failures after a clip was billed say `billed` too. The web says a billed call was paid for, is counted in the spending records, and that trying again makes and pays for a new call; a call byway did not start keeps the gateway's own words; `in-flight` has its own copy. The runner's asset step no longer tries another image after a billed failure; a call byway did not start billed nothing and is tried again, as before (every GatewayError fails a step for good, so stopping the step would end the run). Before, all of these read "The model provider did not answer. Try again in a minute."
6. **byway's stop reaches the web process** (this replaces ADR-0095 decision 5's "The web process does not close its gateways yet"). `scripts/serve.ts` starts `next start` with an IPC channel and asks it to stop before ending it; the app's instrumentation hook (`apps/web/instrumentation.ts`) then closes the service host (its gateways hand back the calls they hold, then the store closes) and exits; requests that arrive meanwhile are refused. It does the same when the channel closes and on Ctrl+C or a terminate signal, which reach the web process too: Next's own signal handler waits for requests in flight, and a model call in flight is one. `scripts/dev-web.ts` closes its guarded server first, then the services. So a recommending or composing call in flight at a clean stop counts at once as may have been billed, against the workspace only.
7. **A run start may name its run** (P3; `StartRunInput.runId`). The id stands for one Start. The Recommendation screen sends it again only while that Start got no answer (its request failed on the way, or the answer was lost, so the run may have started) and with the same inputs (budget, recipe, routes, examples, and the composed recipe shown, compared by identity); once byway answered with a refusal, or with other inputs, the next press is a new Start with a new id, as every press was before (`apps/web/src/components/startIdentity.ts`; `ApiError.status` tells an answer from none). The server accepts only a lowercase UUID (400 otherwise). Starting again with it returns the same run when it is in the same workspace, from the same intake, of the same recipe by hash, for the same problem and with the same model profile, which is what the run record holds and never changes (409 otherwise, so a recipe composed again under the same key never gets the earlier run back), and an ended run as it is. A workflow start refused as already started counts as started, whichever delivery wrote the run: one run, one workflow, and never a run marked failed under its running workflow. (The round-1 verification found both faults of a first version: the screen kept one id for its whole life, so a press after "Restart byway, then try again" got the failed run back and started nothing; and the delivery that wrote the run marked it failed when the other delivery's workflow start got to Temporal first.)
8. **Smaller corrections.**
   - A ledger line whose run or step id is present but empty is a fault, like any value the book cannot use, and the gateway refuses such a call before reserving it.
   - The renderer's allowlisted fetches read each response as it streams and stop at 20 MiB (`MAX_RENDER_FETCH_BYTES`), which real fonts and libraries are far below. To do so they use Node's fetch, hop by hop with redirects off, instead of Playwright's request API, which holds a whole response before handing it over; ADR-0096 decision 3's rule (every hop admitted, GET and HEAD followed, at most five hops) is unchanged.
   - A Playwright error while drawing a page (a protocol error such as "Unable to capture screenshot") reaches the step as one plain step failure, not retried, as the deadline already does; a cancel keeps its own reason.
   - The workflow bundle is written to a temporary file and renamed into place, so two byway starts from one checkout never read half a bundle; the real next dev test builds into `.next-dev-test`, a folder no other suite uses.

## Alternatives considered

- **Leave overlapping attempts to the memo.** Rejected: the memo records an answer only after the call, so it cannot see an attempt still running, and a lost owner's accepted clip is invisible to it.
- **Move paid-call results from the memo into the book (option A).** Not needed for a local, single-user product; the key and the hold close the window, and the memo stays the one store of results.
- **Leases per owner rather than per operation.** Rejected in the design's review: a live process would keep a timed-out attempt's call held, trapping the next attempt behind it.
- **Free a settled call's key when its lease runs out.** Rejected after a test under load bought a call twice (decision 2's `settledEarlier`).
- **A custom production server for the web process in place of `next start`.** Rejected: it would change how the app is served to reach one shutdown hook; Next's instrumentation hook runs in `next start`'s own process.
- **`REJECT_DUPLICATE` as the workflow id reuse policy.** Not needed: an ended run is returned without a start.
- **Cap the renderer's fetch on Playwright's request API by the Content-Length header.** Not enough: the API reads the whole body first, and an endless body has no length.

## Consequences

**Positive**

- An attempt that overlaps another of the same step buys nothing: it gets the first attempt's answer. A timed-out or dead attempt's call is taken over within one lease and counted once more only if it may have been billed. A relay link's clip that fal accepted is bought once, whatever happens to the worker that submitted it. ADR-0079's "Retries never buy the same thing twice" now holds across Temporal's attempts, with the residuals below.
- A clean stop hands back every process's calls at once, the web process's included.
- People are told the truth about byway's own failures, and a billed one never invites a free retry.
- A Start delivered twice starts one run.

**Negative, and residuals named**

- **A holder that dies between settlement and its memo save** (its process killed, its machine off) leaves no result: the next attempt buys the call again, counted. So does the next attempt when the holder's memo save failed four times: ENG-3's "fail rather than pay again" holds for the attempt that failed, not for another attempt waiting on it.
- **A waiting attempt gives up after 5 minutes** when the holder is alive but stuck, with a plain step failure that ends the run and says to start it again.
- **The run id is the screen's to keep, for what the record does not hold.** The runner does not compare the budget (a person can raise it during the run), the routes or the examples, which are not on the run record: a start that names a known id with another budget, other routes or other examples gets the earlier run back. The Recommendation screen never sends one (it mints a new id when any of them changes), and the id lives only while that screen is mounted: after a reload, or after choosing another recipe and coming back, a Start that got no answer is a new Start with a new id, so a second run can start.
- **Run starts, two double faults.** A Start that byway refused because its engine was down, whose refusal was lost on the way and which is pressed again, gets that failed run back (its message says the engine was not running and to start again); the next press is a new Start. And when two deliveries of one Start reach a stopping engine, the one that wrote the run marks it failed if its own workflow start fails for a reason other than "already started", even if the other delivery's start went through; that workflow cannot spend (the gateway refuses an ended run's calls) and ends.
- **An attempt cancelled while its call hangs** is taken over one lease (up to 60 s) later; if the hung call then answers, both calls are counted at their true cost.
- **No background reconciliation with fal.** An accepted job is resumed only when the same step is retried; a run that ends first leaves the call listed as may have been billed, with its request ids to look up.
- **The workflow bundle's hash is pinned** in `packages/runner/test/build.test.ts`: a change that alters workflow code on purpose updates it in the same change.
- **`next start` now runs with an IPC channel.** Run by hand without one, it keeps Next's own signal handling and does not close the services.
- **The renderer's allowlisted fetches go through Node's network stack**, as Playwright's request API's did, with the request's own headers; a response over 20 MiB is blocked rather than shown cut.
- **Contracts and schema.** Migration 7 is new (older builds refuse the newer database, as for every migration). `SpendBook.letGo`, `AdmitOutcome` `inFlight`, `resume` and `settledEarlier`, `GatewayErrorCode` `byway-failure` and `in-flight`, `GatewayError.billed` and `settledEarlier`, `Settlement.holdMs`, `SpendContext.operation`, `StartRunInput.runId` and `ProviderVideoRequest.resume` are new; all optional except the book method.
