## Context

ADR-0074's guard refuses a request not addressed to 127.0.0.1 and a change sent from another site, so neither a web page the person visits nor another machine can drive byway. It rejected "A token in the URL for every request" as heavier than a local tool needs once Host and Origin are checked, and said it can be revisited. A map of the code the owner asked for (Floorplan, 2026-11-16) reported that no endpoint checks who is calling. What the guard leaves open is another program on the same computer, under any Windows account: it can call 127.0.0.1 with the headers it chooses and start runs that spend.

Before building, Claude found a second door. The engine's Temporal server listens on 127.0.0.1:7233 with no password (only its HTTP interface is off, ADR-0074), so another program can start a byway workflow through it, read a run's inputs from its history and start it again, reset a running workflow so that it does paid steps again, answer a run's checkpoint, or pause and cancel runs. The owner chose to close both doors: the option read "The web secret as you chose it, plus: the engine pays for a run only if this byway started it. The app marks each run start with a check value made from the per-start secret (kept in byway's processes, never on disk), and the run's first step verifies it, and that the run is new in byway's own data, before any paid call; a run started or replayed through Temporal's port fails before it spends. Pausing or cancelling through the port stays possible (no money moves) and is written down. The workflow's input changes, so its merge waits for no run in flight. One adversarial check over both."

## Decision

1. **A secret and a host name made at each start.** `pnpm start` and `pnpm dev` (scripts/serve.ts) make a random access key of 32 bytes and a random host name, `byway-<24 hex digits>.localhost`, each time they start, before the engine starts, and hand the key to the web server and the engine's worker, and the name to the web server, in their environment only: never on disk or in Temporal; the key is printed only in the start link on the terminal, and the browser suite's log of that output masks it. `BYWAY_ACCESS_KEY` may name a key of 32 characters or more, and `BYWAY_ACCESS_HOST` a name of that form, which the browser suite uses (scripts/e2e.ts); byway takes them only in demo mode, which spends nothing, so a key or name kept in a file never guards a byway that spends. byway prints the link `http://<host name>:<port>/open?key=<key>` with the line "open this link in Chrome, Edge or Firefox: byway answers only the browser that opened it, until it stops". Those browsers send any name under .localhost to this computer themselves.
2. **The web door.** Opening that link with this start's key, at this start's host name, sets the cookie `byway_access` (HttpOnly, SameSite=Strict, Path=/, for that host name alone) and answers with a small page that goes on to the start screen by itself, sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`: a browser sends a Strict cookie on a navigation only when byway's own page started it, and the link is often opened from another site's page, which a redirect would carry over. A browser sends a cookie to every port of its host, so a cookie for 127.0.0.1 would reach any program listening on another 127.0.0.1 port; the host name is new at each start, so another program has no name to have the browser visit. Chrome and Edge try a name under .localhost on IPv6 loopback ([::1]) first, so byway holds its web port there for as long as it runs, passing each connection on to 127.0.0.1, and does not start when another program holds it (apps/web/src/server/ipv6-hold.ts). A generated page whose scripts the person turns on can read the name from its own address, which the scripts switch says. At 127.0.0.1, localhost or any other name the link is refused (403), even with the key; a tab or bookmark at an earlier start's name gets a page saying byway has started again, at a new address, and to open the new link. ADR-0074's Host check answers this start's host name beside the loopback names; scripts and tests reach byway at 127.0.0.1 with the cookie in their request. Every other request, pages, endpoints, files, Next's own development endpoints and WebSocket upgrades included, needs that cookie: without it byway answers 401 ("byway answers only the browser that opened the link it printed when it started."), as a small page for a browser and as JSON otherwise; the link with another key gets 403; a server started with no key refuses everything with 503, and one with no host name refuses the link with 503, and says to start byway with `pnpm start`. Keys are compared in constant time. The production server checks it in proxy.ts after ADR-0074's guard; contributor mode's guarded server checks it in dev-server.ts before Next sees the request (apps/web/src/server/guard.ts, `checkAccess`).
3. **The engine door: each run is claimed once, with its own input.** Each run's record holds the digest of the workflow input Runner.start gives it (`runs.start_digest`, schema 12; packages/runner/src/start-digest.ts): its recipe, profile, budget, medium, routes, the references to its brief and inputs, and its id. The workflow's first step, `claimRun`, digests the input it was started with and claims the run for its own Temporal execution (`runs.claimed_by`) only when that digest is the run's, and only once; every other step that names its run first checks that it runs in the execution that claimed the run (packages/runner/src/activities/claim.ts; storyboardShots, which only reads a storyboard file, names none). So a workflow started through the port for a run byway never made, or for a run byway made with any other input, a finished run started again from its history, and a reset (which Temporal runs as a new execution) all stop at their first step, before any paid call, with the failure "RunNotStartedHere". The input is in Temporal's history for any program to read, so the claim rests on the input itself and on the run being claimed once, not on a secret: a program that stops a new run's workflow before its first step and starts it again with any other input only stops the run. byway's own workflow for a run, refused at its claim before anything claimed the run, fails the run at once with "byway stopped this run before it spent anything: the engine started it with other settings than byway kept for it. Start it again."; a refused replay, reset, or workflow under another id leaves the run as it was. Runs made before schema 12 are marked claimed by `before-schema-12`, so none of them runs under any execution again.
4. **Signed answers.** An answer to a checkpoint can move money (the "use more of the budget?" question is a checkpoint), and the update that carries it can be sent through the port. byway's app signs each answer with the access key (HMAC-SHA256 over the run, the checkpoint and what the answer says: its choice, text and approval), and the worker records an answer only with a valid signature for that run and checkpoint, and only when what it writes is what was signed (packages/runner/src/answer-check.ts; recordResolution). A worker does not start without this start's key (32 characters or more; packages/runner/src/worker.ts). An answer that an earlier start's worker recorded before byway stopped hard, before Temporal heard of it, counts as recorded when Temporal tries it again under the new key, so the run goes on with what the person said. A refused answer reaches the person in byway's own words, not as Temporal's "Activity task failed". A signature cannot be moved to another checkpoint or another answer, and once its checkpoint is answered a copy read from Temporal's history answers nothing.
5. **What stays open, written down.** Through Temporal's port, which has no password, until the port itself is closed (backlog row B-195):
   - **A second worker.** The claim binds a step to an execution, not to the code that scheduled it. A program that polls byway's task queue (`byway-runs`) as a workflow worker of its own wins about half of new runs' first workflow tasks; it then claims the run with its true input and chooses its steps, and byway's worker runs each one: it can raise the run's and the workspace's budgets with no answer, choose the models, and spend through byway's provider keys up to the caps it set. The check reproduced it on the mock gateway (4 of 8 runs taken, a run's budget from $50 to $1,050).
   - **Pausing, resuming and cancelling.** A program can pause or cancel a run, and resume one the person paused, after which the run goes on spending within its budget.
   - **Reading what Temporal's history holds** (run inputs travel by reference, ADR-0113, but the history holds each step's arguments and results).
   - **Resetting a run**, which stops it: the reset's execution is refused at its next step, and byway's pass every few minutes (lost-runs.ts) closes the run as failed.

   Temporal's dev server cannot require a client certificate (the research of 2026-11-17, in B-195): closing the port means byway runs Temporal's full server itself, with certificates made at each start. A program under the person's own Windows account can read byway's data folder and `.env.agents` already, and can read another process's environment and memory; the secret and the host name add most against another account.

Where this departs from the option's words (Claude's, while building): the option said "a check value made from the per-start secret (kept in byway's processes, never on disk)". The check value is the digest of the run's input, kept in byway's data folder; it is not a secret and needs none. A value made from the per-start secret would change at the next start, so a run waiting on a question across a restart could not go on, and a replay carries the same value as the run it copies. The first build held a random token per run, which its workflow input carried; an automated security review of the commit (2026-11-17) found that a program reading that token from Temporal's history could, before the run's first step, stop its workflow and start it again with another recipe, profile or routes, and spend up to the run's budget on them (the caps read the budget from byway's own record, so not past it). Binding the claim to the whole input closed that, before the adversarial check. Signed answers (item 4) were not in the option; Claude added them on reading that a checkpoint's answer is one of the "paid" doors.

**The adversarial check (2026-11-17)** ran four lenses in clones of the branch, each finding put to a refuter, and a critic: 12 agents. Every finding put to a refuter held. Its two high findings were that the cookie for 127.0.0.1 went to every 127.0.0.1 port, so a program under another account that got the person's browser to load one page from its port had the key, the web API and the signing key (three lenses; reproduced in Chromium 153, by a link, a redirect with no click, or a typed address), and the second worker of item 5 (two lenses). Its medium findings were that images and clips in generated pages stopped loading (a page's frame is sandboxed, so its own requests count as another site's and carry no cookie), and that the README said no other program could use byway. Its low findings: a refused claim showed "queued" until the lost-run pass; the e2e log held the suite's key; the link opened from another site's page landed on the 401 page; a cookie of the same name set from another port could lock the person out; and no unit test caught removing proxy.ts's refusal. The critic added that recordResolution checked the signature on the answer but wrote the resolution beside it, and that the resume signal takes no check. Asked how to handle the first, the owner chose "Per-start host name (Recommended)" ("The start link becomes http://b-<random>.localhost:<port>/open?key=… (Chrome, Edge and Firefox send *.localhost to this computer themselves). The cookie then belongs only to that name, which no other program can guess, and byway's Host check accepts only it. This also stops another port overwriting the cookie. Scripts and tests reach byway at 127.0.0.1 with that Host header."); the second, "Look at Temporal's TLS now (Recommended)" ("Find out, with no code, whether the Temporal dev server byway starts can require a client certificate made at each start. That would close the port to every other program: takeover, resume, pause and cancel. Then come back with a design. B-188 merges after this fix round, with the takeover named as open until then."); and the rest, "All of them, one round (Recommended)" ("One fix round with the answers above, then the gate. The size of any re-check comes to you before it runs."). The fix round built items 1 to 5 as written above, a unit test of proxy.ts (apps/web/test/proxy.test.ts) and a browser test of the link (apps/web/e2e/start-link.spec.ts); generated pages shown in byway's frame carry their images inline, as downloads already did (apps/web/src/server/api.ts, selfContained). **The re-check (2026-11-17)** ran three lenses, a refuter for each of its first 8 findings, and a critic: 12 agents, all of whose refuters held, two in part. Its high finding came from the fix round: Chrome and Edge open the start link's .localhost name on [::1] first, and byway listened only on 127.0.0.1, so a program listening on [::1] at byway's port received the start link, key included, and could pass everything on to byway unseen (reproduced twice with byway's own guard). Its medium findings: a run stuck after a hard stop while an answer was being recorded (the next start's worker, with a new key, refused the retry of its own earlier answer; this came from the first build); the README and guard.ts still saying no other program could use byway; and the records saying the name is shown only on the terminal, when a page with scripts on can read it. Its low findings: a refused answer read "Activity task failed"; an old tab got JSON saying byway answers only 127.0.0.1; a link between generated pages shows the 401 page in the frame; no test caught removing two of the name checks or the e2e log's masking; and the worker started without a key, though the owner's chosen words said it refuses to. The critic added that `pnpm start` took the browser suite's fixed key and name, even from `.env.agents`; that Firefox and system proxies were never tried; that whether other accounts can write the data folder was not looked at; that with images inline a page with scripts on can read them; and that no test answered a question at the name. Asked whether a second fix round should run, the owner chose "All of it, one round (Recommended)" ("byway holds [::1] at its port itself (refusing to start when it is taken, and passing those connections on to 127.0.0.1), with a test. Answers already recorded before a restart count as done. You see the real refusal text. An old tab gets a page saying byway restarted. The worker refuses to start without a key. Fixed keys and names are honoured only in demo mode. Tests for the unchecked lines, and a browser test that answers a question at the host name. The README, guard.ts, the scripts warning and ADR-0117 say exactly what holds; Firefox, proxies and the data-folder question are recorded or get a row."), and for its re-check "Two lenses and a critic". The round built items 1, 2 and 4 as written above, the tests the option names (apps/web/test/ipv6-hold.test.ts, apps/web/test/access.test.ts, apps/web/test/proxy.test.ts, scripts/test/serve.test.ts, packages/runner/test/start-claim.test.ts, and apps/web/e2e/start-link.spec.ts, which now also checks [::1] and answers a run's questions at the name), and the records; the data folder is backlog row B-197.

Where it departs from the host-name option's words (Claude's): the name is `byway-<24 hex digits>`, not `b-<random>`; byway's Host check answers it beside the loopback names, not alone, and scripts and tests reach byway at 127.0.0.1 with their own Host and the cookie, since Node on Windows does not resolve names under .localhost; the start link alone is refused at any name but this start's, so a browser never holds a cookie for 127.0.0.1.

## Alternatives considered

- **"Record it, row for later (Recommended)"** (the first question): no code now; a row for a per-start secret before byway runs on a shared computer or for others. Not chosen: it would leave the other-account path open until a trigger no one may notice firing.
- **"Record it only"**: accept the residual for a single-user local app. Not chosen: it accepts it for good.
- **"Web secret only, Temporal row"**: the web secret, with the Temporal port recorded and a row to close it. Not chosen: it leaves the paid door open.
- **"Look at Temporal's own TLS first"**: find out whether the Temporal dev server can require a client certificate made at each start, which would close the port itself, pausing and cancelling included. Not chosen by the owner on 2026-11-16; chosen on 2026-11-17, after the check, as "Look at Temporal's TLS now (Recommended)". The answer: it cannot; the design to close the port is B-195's.
- **"Record it as open"** (the cookie, 2026-11-17): no code change, the path named in item 5, guard.ts and the README. Not chosen: a protection the person relies on would have stayed bypassed by one page load.
- **"Check the money paths in steps"** (the engine port, 2026-11-17): a budget raise only from a signed, recorded approval, the profile from byway's record, resume only after the person's. Not chosen: each check closes one step, a takeover would still choose the run's steps within its budget, and closing the port closes them all.
- **"Record it, with a row"** (the engine port, 2026-11-17): name it and file a row. Not chosen: the owner chose to look at closing it now.
- **"Regression and records only"** (the fix round, 2026-11-17): fix the images and the wording, file the low findings. Not chosen.
- **"High and mediums only"** (the second fix round, 2026-11-17): the [::1] fix, the stuck run and the wording, with the rest as rows. Not chosen: the low findings were each small enough to land in the same round.
- **"Back out the host name"** (the second fix round): the 127.0.0.1 link again, with the cross-port leak recorded as open. Not chosen: holding [::1] closes the new path, and the old one needed only a page load from another port.
- **"One lens, capped (Recommended)"** and **"No re-check"** (the second round's re-check): not chosen; the owner chose two lenses and a critic.
- **What the check's refuters showed does not stop the cookie leak:** the `__Host-` prefix with Secure (Chromium sends and replaces it on another port too), a value derived from the key in the cookie (the cookie still drives the web API, which signs answers itself), and one fixed name such as `byway.localhost` (a cookie for it goes to that name's other ports).
- **A token in the URL of every request** (ADR-0074's alternative): a cookie set once from the start link keeps the key out of every later URL, history entry and Referer.
- **A check value made from the per-start secret** (the option's words): see Decision, above.

## Consequences

- The person opens the link byway prints, each time it starts, in Chrome, Edge or Firefox; a tab from an earlier start is at an earlier host name and gets nothing until the new link is opened. A bookmark of `http://127.0.0.1:3000` no longer opens byway.
- A generated page shown in byway carries its images and clips inline, up to selfContained's 40 MB in all; past that, the rest do not load in byway's frame. A page whose scripts the person turns on can read those images, and the address byway runs at; a link from one generated page to another shows byway's 401 page in the frame, since a navigation the sandboxed page starts carries no cookie.
- byway does not start when another program holds its web port on [::1].
- Not tried: Firefox (the check's Playwright build for it was missing) and a browser behind a system proxy, PAC file or WPAD. A browser that sent names under .localhost to the network's DNS or a proxy, rather than to this computer, would send the start link there. Windows' own resolver does not answer such names (Node gets EAI_AGAIN), so a script reaches byway at 127.0.0.1.
- The workflow's input and its first step changed, so the workflow bundle's hash changed (packages/runner/test/build.test.ts), and a run in flight when this lands would be refused; the merge waits for no run in flight.
- The browser suite and the dev-server tests carry the cookie (apps/web/e2e/access.ts, apps/web/test/fixtures/http.ts).
- Floorplan's check still reports no endpoint checking the caller: it looks for a sign-in check in each route, and this one sits in front of them all.
- If it breaks: a 401 or 503 on every page means the web server has no key or the browser has an older cookie (open the printed link); runs that fail at once with "RunNotStartedHere" mean the input the workflow received does not digest to the one Runner.start kept (a change between Runner.start's `args` and the workflow's first line, or in how start-digest.ts reads them), or the store's claim refused it (packages/store/src/store.ts, `claimRun`); an answer refused with "AnswerNotSigned" means the app and the worker hold different keys, or the worker has none; a run that fails with "byway stopped this run before it spent anything" had its own workflow refused at its claim, as above; a start link that does not load (a name not found) means the browser does not send names under .localhost to this computer; "Port … on [::1] (IPv6 loopback) is already in use by another program" at start means another program holds byway's port there; a page saying byway has started again means a tab or bookmark from an earlier start; a refused start link at 127.0.0.1 means the link was not opened as printed; images missing from a page shown in byway mean the artifact route did not inline them (apps/web/src/server/api.ts).
