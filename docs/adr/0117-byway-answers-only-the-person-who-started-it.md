## Context

ADR-0074's guard refuses a request not addressed to 127.0.0.1 and a change sent from another site, so neither a web page the person visits nor another machine can drive byway. It rejected "A token in the URL for every request" as heavier than a local tool needs once Host and Origin are checked, and said it can be revisited. A map of the code the owner asked for (Floorplan, 2026-11-16) reported that no endpoint checks who is calling. What the guard leaves open is another program on the same computer, under any Windows account: it can call 127.0.0.1 with the headers it chooses and start runs that spend.

Before building, Claude found a second door. The engine's Temporal server listens on 127.0.0.1:7233 with no password (only its HTTP interface is off, ADR-0074), so another program can start a byway workflow through it, read a run's inputs from its history and start it again, reset a running workflow so that it does paid steps again, answer a run's checkpoint, or pause and cancel runs. The owner chose to close both doors: the option read "The web secret as you chose it, plus: the engine pays for a run only if this byway started it. The app marks each run start with a check value made from the per-start secret (kept in byway's processes, never on disk), and the run's first step verifies it, and that the run is new in byway's own data, before any paid call; a run started or replayed through Temporal's port fails before it spends. Pausing or cancelling through the port stays possible (no money moves) and is written down. The workflow's input changes, so its merge waits for no run in flight. One adversarial check over both."

## Decision

1. **A secret made at each start.** `pnpm start` and `pnpm dev` (scripts/serve.ts) make a random access key of 32 bytes each time they start, before the engine starts, and hand it to the web server and the engine's worker in their environment only: never on disk, in Temporal or in a log. `BYWAY_ACCESS_KEY` may name one of 32 characters or more, which the browser suite uses (scripts/e2e.ts). byway prints the link `http://127.0.0.1:<port>/open?key=<key>` with the line "open this link: byway answers only the browser that opened it, until it stops".
2. **The web door.** Opening that link with this start's key sets the cookie `byway_access` (HttpOnly, SameSite=Strict, Path=/) and goes on to the start screen with a 303, sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Every other request, pages, endpoints, files, Next's own development endpoints and WebSocket upgrades included, needs that cookie: without it byway answers 401 ("byway answers only the browser that opened the link it printed when it started."), as a small page for a browser and as JSON otherwise; the link with another key gets 403; a server started with no key refuses everything with 503 and says to start byway with `pnpm start`. Keys are compared in constant time. The production server checks it in proxy.ts after ADR-0074's guard; contributor mode's guarded server checks it in dev-server.ts before Next sees the request (apps/web/src/server/guard.ts, `checkAccess`).
3. **The engine door: each run is claimed once.** Each run's record holds a random start token (`runs.start_token`, schema 12), which its workflow input carries. The workflow's first step, `claimRun`, claims the run for its own Temporal execution (`runs.claimed_by`), only with that token and only once; every other step first checks that it runs in the execution that claimed the run (packages/runner/src/activities/claim.ts). So a workflow started through the port for a run byway never made, a finished run started again from its history, and a reset (which Temporal runs as a new execution) all stop at their first step, before any paid call, with the failure "RunNotStartedHere". Runs made before schema 12 are marked claimed by `before-schema-12`, so none of them runs under any execution again.
4. **Signed answers.** An answer to a checkpoint can move money (the "use more of the budget?" question is a checkpoint), and the update that carries it can be sent through the port. byway's app signs each answer with the access key (HMAC-SHA256 over the run, the checkpoint and what the answer says: its choice, text and approval), and the worker records an answer only with a valid signature for that run and checkpoint (packages/runner/src/answer-check.ts; recordResolution). A signature cannot be moved to another checkpoint or another answer, and once its checkpoint is answered a copy read from Temporal's history answers nothing.
5. **What stays open, written down.** Pausing and cancelling a run through the port (no money moves). Reading what Temporal's history holds (run inputs travel by reference, ADR-0113, but the history holds each step's arguments and results). Resetting a run through the port, which stops it: the reset's execution is refused at its first step, and byway's pass every few minutes (lost-runs.ts) closes the run as failed. A program under the person's own Windows account can read byway's data folder and `.env.agents` already, and can read another process's environment; the secret adds most against another account.

Where this departs from the option's words (Claude's, while building): the option said "a check value made from the per-start secret (kept in byway's processes, never on disk)". The start token is random per run and is stored in byway's data folder and carried in Temporal's history; it protects by being claimed once, not by being secret. A value made from the per-start secret would change at the next start, so a run waiting on a question across a restart could not go on, and a replay carries the same value as the run it copies. Signed answers (item 4) were not in the option; Claude added them on reading that a checkpoint's answer is one of the "paid" doors.

## Alternatives considered

- **"Record it, row for later (Recommended)"** (the first question): no code now; a row for a per-start secret before byway runs on a shared computer or for others. Not chosen: it would leave the other-account path open until a trigger no one may notice firing.
- **"Record it only"**: accept the residual for a single-user local app. Not chosen: it accepts it for good.
- **"Web secret only, Temporal row"**: the web secret, with the Temporal port recorded and a row to close it. Not chosen: it leaves the paid door open.
- **"Look at Temporal's own TLS first"**: find out whether the Temporal dev server can require a client certificate made at each start, which would close the port itself, pausing and cancelling included. Not chosen by the owner; it remains the way to close what item 5 leaves open, if that is wanted later.
- **A token in the URL of every request** (ADR-0074's alternative): a cookie set once from the start link keeps the key out of every later URL, history entry and Referer.
- **A check value made from the per-start secret** (the option's words): see Decision, above.

## Consequences

- The person opens the link byway prints, each time it starts; a tab from an earlier start gets the 401 page until the new link is opened. A bookmark of `http://127.0.0.1:3000` alone no longer opens byway.
- The workflow's input and its first step changed, so the workflow bundle's hash changed (packages/runner/test/build.test.ts), and a run in flight when this lands would be refused; the merge waits for no run in flight.
- The browser suite and the dev-server tests carry the cookie (apps/web/e2e/access.ts, apps/web/test/fixtures/http.ts).
- Floorplan's check still reports no endpoint checking the caller: it looks for a sign-in check in each route, and this one sits in front of them all.
- If it breaks: a 401 or 503 on every page means the web server has no key or the browser has an older cookie (open the printed link); runs that fail at once with "RunNotStartedHere" mean the workflow input lost its start token, or the store's claim refused it (packages/store/src/store.ts, `claimRun`); an answer refused with "AnswerNotSigned" means the app and the worker hold different keys.
