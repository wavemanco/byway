## Context

ADR-0074's guard refuses a request not addressed to 127.0.0.1 and a change sent from another site, so neither a web page the person visits nor another machine can drive byway. It rejected "A token in the URL for every request" as heavier than a local tool needs once Host and Origin are checked, and said it can be revisited. A map of the code the owner asked for (Floorplan, 2026-11-16) reported that no endpoint checks who is calling. What the guard leaves open is another program on the same computer, under any Windows account: it can call 127.0.0.1 with the headers it chooses and start runs that spend.

Before building, Claude found a second door. The engine's Temporal server listens on 127.0.0.1:7233 with no password (only its HTTP interface is off, ADR-0074), so another program can start a byway workflow through it, read a run's inputs from its history and start it again, reset a running workflow so that it does paid steps again, answer a run's checkpoint, or pause and cancel runs. The owner chose to close both doors: the option read "The web secret as you chose it, plus: the engine pays for a run only if this byway started it. The app marks each run start with a check value made from the per-start secret (kept in byway's processes, never on disk), and the run's first step verifies it, and that the run is new in byway's own data, before any paid call; a run started or replayed through Temporal's port fails before it spends. Pausing or cancelling through the port stays possible (no money moves) and is written down. The workflow's input changes, so its merge waits for no run in flight. One adversarial check over both."

## Decision

1. **A secret and a host name made at each start.** `pnpm start` and `pnpm dev` (scripts/serve.ts) make a random access key of 32 bytes and a random host name, `byway-<24 hex digits>.localhost`, each time they start, before the engine starts, and hand the key to the web server and the engine's worker, and the name to the web server, in their environment only: never on disk or in Temporal; the key is printed only in the start link on the terminal, and the browser suite's log of that output masks it. `BYWAY_ACCESS_KEY` may name a key of 32 characters or more, and `BYWAY_ACCESS_HOST` a name of that form, which the browser suite uses (scripts/e2e.ts); byway takes them only in demo mode, which spends nothing, from the shell (never from `.env.agents`), and with a data folder other than the default one (by the file system's own identity once the folder exists, so a junction or link to the default folder, a network path to it on this computer, or its `\\?\` or `\\?\`Volume form is the default folder; and byway does not start with a data folder whose path holds a #, % or ?, which the engine's Temporal server reads as part of its database's address (the long-path form `\\?\` included, under which the server cannot open a database at all), nor, on Windows, with one whose path has a part ending in a dot or a space, which Node keeps and Windows drops for most programs, SQLite a single trailing dot), so a key or name kept in a file never guards byway, and a known one never guards the person's own runs and Settings. byway prints the link `http://<host name>:<port>/open?key=<key>` with the line "open this link in Chrome, Edge or Firefox: byway answers only the browser that opened it, until it stops", only once its web server says it listens (`next start`'s "Ready in" line, which scripts/serve.ts reads from its output, or the contributor web server's message), and it does not start when anything already answers a connection at its port on 127.0.0.1 or [::1]: on Windows a bind check misses a program listening on 0.0.0.0 or [::], which would otherwise answer at 127.0.0.1 until the web server listens. Those browsers send any name under .localhost to this computer themselves.
2. **The web door.** Opening that link with this start's key, at this start's host name, sets the cookie `byway_access` (HttpOnly, SameSite=Strict, Path=/, for that host name alone) and answers with a small page that goes on to the start screen by itself, sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`: a browser sends a Strict cookie on a navigation only when byway's own page started it, and the link is often opened from another site's page, which a redirect would carry over. A browser sends a cookie to every port of its host, so a cookie for 127.0.0.1 would reach any program listening on another 127.0.0.1 port; the host name is new at each start, so another program has no name to have the browser visit. Chrome and Edge try a name under .localhost on IPv6 loopback ([::1]) first, so byway holds its web port there for as long as it runs, passing each connection on to 127.0.0.1, and does not start when another program holds it (apps/web/src/server/ipv6-hold.ts). A generated page whose scripts the person turns on can read the name from its own address, which the scripts switch says. At 127.0.0.1, localhost or any other name the link is refused (403), even with the key; a tab or bookmark at an earlier start's name gets a page saying byway has started again, at a new address, and to open the new link. ADR-0074's Host check answers this start's host name beside the loopback names; scripts and tests reach byway at 127.0.0.1 with the cookie in their request. Every other request, pages, endpoints, files, Next's own development endpoints and WebSocket upgrades included, needs that cookie: without it byway answers 401 ("byway answers only the browser that opened the link it printed when it started."), as a small page for a browser and as JSON otherwise; the link with another key gets 403; a server started with no key refuses everything with 503, and one with no host name refuses the link with 503, and says to start byway with `pnpm start`. Keys are compared in constant time. The production server checks it in proxy.ts after ADR-0074's guard; contributor mode's guarded server checks it in dev-server.ts before Next sees the request (apps/web/src/server/guard.ts, `checkAccess`).
3. **The engine door: each run is claimed once, with its own input.** Each run's record holds the digest of the workflow input Runner.start gives it (`runs.start_digest`, schema 12; packages/runner/src/start-digest.ts): its recipe, profile, budget, medium, routes, the references to its brief and inputs, and its id. The workflow's first step, `claimRun`, digests the input it was started with and claims the run for its own Temporal execution (`runs.claimed_by`) only when it runs under the run's own workflow id and that digest is the run's, and only once; every other step that names its run first checks that it runs in the execution that claimed the run (packages/runner/src/activities/claim.ts; storyboardShots, which only reads a storyboard file, names none). So a workflow started through the port for a run byway never made, or for a run byway made with any other input or under another workflow id than the run's own (which, with the run's true input, would spend where byway's cancel, pause and answers never reach), a finished run started again from its history, and a reset (which Temporal runs as a new execution) all stop at their first step, before any paid call, with the failure "RunNotStartedHere". The input is in Temporal's history for any program to read, so the claim rests on the input itself and on the run being claimed once, not on a secret: a program that stops a new run's workflow before its first step and starts it again with any other input only stops the run. byway's own workflow for a run, refused at its claim before anything claimed the run, fails the run at once with "byway stopped this run before it spent anything: the engine started it with other settings than byway kept for it. Start it again."; a refused replay, reset, or workflow under another id leaves the run as it was. Runs made before schema 12 are marked claimed by `before-schema-12`, so none of them runs under any execution again.
4. **Signed answers.** An answer to a checkpoint can move money (the "use more of the budget?" question is a checkpoint), and the update that carries it can be sent through the port. byway's app signs each answer with the access key (HMAC-SHA256 over the run, the checkpoint and what the answer says: its choice, text and approval), and the worker records an answer only with a valid signature for that run and checkpoint, and only when what it writes is what was signed (packages/runner/src/answer-check.ts; recordResolution). A worker does not start without this start's key (32 characters or more; packages/runner/src/worker.ts). An answer that an earlier start's worker recorded before byway stopped hard, before Temporal heard of it, counts as recorded when Temporal tries it again under the new key, so the run goes on with what the person said. A refused answer reaches the person in byway's own words, not as Temporal's "Activity task failed", and its refusal names the restart case too: an answer an earlier start's worker took and had not yet written when byway stopped hard is refused under the next start's key, which cannot check the earlier one. Nobody waits for that answer any more, so those words reach only the terminal's warning; in the app the question shows open again once Temporal's one-minute limit for the first try has passed, and the person answers again (within that minute an answer is refused as answered already, as before B-188). A signature cannot be moved to another checkpoint or another answer, and once its checkpoint is answered a copy read from Temporal's history answers nothing.
5. **What stays open, written down.** Through Temporal's port, which has no password, until the port itself is closed (backlog row B-195):
   - **A second worker.** The claim binds a step to an execution, not to the code that scheduled it. A program that polls byway's task queue (`byway-runs`) as a workflow worker of its own wins about half of new runs' first workflow tasks; it then claims the run with its true input and chooses its steps, and byway's worker runs each one: it can raise the run's and the workspace's budgets with no answer, choose the models, and spend through byway's provider keys up to the caps it set. The check reproduced it on the mock gateway (4 of 8 runs taken, a run's budget from $50 to $1,050).
   - **Pausing, resuming and cancelling.** A program can pause or cancel a run, and resume one the person paused, after which the run goes on spending within its budget.
   - **Reading what Temporal's history holds** (run inputs travel by reference, ADR-0113, but the history holds each step's arguments and results).
   - **Resetting a run**, which stops it: the reset's execution is refused at its next step, and byway's pass every few minutes (lost-runs.ts) closes the run as failed.

   Temporal's dev server cannot require a client certificate (the research of 2026-11-17, in B-195): closing the port means byway runs Temporal's full server itself, with certificates made at each start. A program under the person's own Windows account can read byway's data folder and `.env.agents` already, and can read another process's environment and memory; the secret and the host name add most against another account.

Where this departs from the option's words (Claude's, while building): the option said "a check value made from the per-start secret (kept in byway's processes, never on disk)". The check value is the digest of the run's input, kept in byway's data folder; it is not a secret and needs none. A value made from the per-start secret would change at the next start, so a run waiting on a question across a restart could not go on, and a replay carries the same value as the run it copies. The first build held a random token per run, which its workflow input carried; an automated security review of the commit (2026-11-17) found that a program reading that token from Temporal's history could, before the run's first step, stop its workflow and start it again with another recipe, profile or routes, and spend up to the run's budget on them (the caps read the budget from byway's own record, so not past it). Binding the claim to the whole input closed that, before the adversarial check. Signed answers (item 4) were not in the option; Claude added them on reading that a checkpoint's answer is one of the "paid" doors.

## Consequences

- The person opens the link byway prints, each time it starts, in Chrome, Edge or Firefox; a tab from an earlier start is at an earlier host name and gets nothing until the new link is opened. A bookmark of `http://127.0.0.1:3000` no longer opens byway.
- A generated page shown in byway carries its images and clips inline, up to selfContained's 40 MB in all; past that, the rest do not load in byway's frame. A page whose scripts the person turns on can read those images, and the address byway runs at; a link from one generated page to another shows byway's 401 page in the frame, since a navigation the sandboxed page starts carries no cookie.
- byway does not start when another program holds its web port on [::1], or when anything already answers a connection at that port on 127.0.0.1 or [::1]. The start link appears a moment later than before, once the web server listens.
- What the person typed in a tab and has not sent belongs to that start's address, since the browser keeps it per address: it does not follow byway to its next one. Once any request from such a tab is answered "started again", every screen of it says so (a tab from before B-188, at 127.0.0.1, is answered so too: a browser's own request there can never carry the cookie), keeps the text on screen and asks the person to copy it before reloading. Settings' single-key shortcuts switch, kept in the browser until the third round, is a Store preference (schema 13), so it stays as set across restarts, byway's other open tabs in the same browser follow a change at once, and every tab reads it again once loaded, whenever it comes back into view and whenever its window gets focus, one in another browser profile or a private window included; a read answered after a change the tab heard since it was sent, or after a read sent later, is not applied; switches of the browser's own, such as a page's "Run its scripts", were never remembered (SEC-4). A switch turned off before B-188 was kept in the browser for 127.0.0.1:3000, which this byway cannot read: after the upgrade it is on again, once, until it is turned off in Settings.
- While byway is stopped, or still building at its next start, whatever program then answers at its port can answer a tab from an earlier start, and so read what that tab kept for its address; that was as true before B-188, for 127.0.0.1:3000. Next.js itself answers TRACE (an error) and its URL-normalising redirects before `proxy.ts` runs; neither reaches anything (the third re-check's probe), and a Next.js update that changes either is worth probing again.
- Not tried by a check: macOS; another Windows account's listener at byway's port (no second account; by Microsoft's bind rules it makes the web server's own bind fail, and byway stops before it prints the link). The [::1] hold and the bind and connection checks were probed on Windows 11; Linux runs the browser suite in CI, apps/web/e2e/start-link.spec.ts included.
- Not tried: Firefox (the check's Playwright build for it was missing) and a browser behind a system proxy, PAC file or WPAD. A browser that sent names under .localhost to the network's DNS or a proxy, rather than to this computer, would send the start link there. Windows' own resolver does not answer such names (Node gets EAI_AGAIN), so a script reaches byway at 127.0.0.1.
- The workflow's input and its first step changed, so the workflow bundle's hash changed (packages/runner/test/build.test.ts), and a run in flight when this lands would be refused; the merge waits for no run in flight.
- The browser suite and the dev-server tests carry the cookie (apps/web/e2e/access.ts, apps/web/test/fixtures/http.ts).
- Floorplan's check still reports no endpoint checking the caller: it looks for a sign-in check in each route, and this one sits in front of them all.
- If it breaks: a 401 or 503 on every page means the web server has no key or the browser has an older cookie (open the printed link); runs that fail at once with "RunNotStartedHere" mean the input the workflow received does not digest to the one Runner.start kept (a change between Runner.start's `args` and the workflow's first line, or in how start-digest.ts reads them), or the store's claim refused it (packages/store/src/store.ts, `claimRun`); an answer refused with "AnswerNotSigned" means the app and the worker hold different keys: byway stopped hard while an answer of its earlier start was being written (the person answers again), or the app runs with another start's key; a start link that never appears means the web server never said it listens (`next start`'s "Ready in" line, which scripts/serve.ts reads; a Next.js update may change that line); "Something on this computer already answers at port …" at start means a program listens there, perhaps on 0.0.0.0 or [::]; a notice on every screen saying byway has started again means a tab from an earlier start; a shortcuts switch that another open tab does not follow means the tabs' channel did not carry the change (apps/web/src/components/useShortcuts.ts, `announceSingleKeys`), or that a tab in another browser profile has not come back into view since (its read of GET /api/settings); "Refusing to keep byway data in …: its part "…" ends in a dot or a space" at start means BYWAY_DATA_DIR names such a folder, and "its path holds "#"" (or "%", or "?") one whose path the engine's server would read as an address (the `\\?\` form included), whose contents are to be moved to the folder BYWAY_DATA_DIR then names; "The Temporal server on port … has not opened byway's engine database" means another program answered on that port, or the server kept its database elsewhere; a run that fails with "byway stopped this run before it spent anything" had its own workflow refused at its claim, as above; a start link that does not load (a name not found) means the browser does not send names under .localhost to this computer; "Port … on [::1] (IPv6 loopback) is already in use by another program" at start means another program holds byway's port there; a page saying byway has started again means a tab or bookmark from an earlier start; a refused start link at 127.0.0.1 means the link was not opened as printed; images missing from a page shown in byway mean the artifact route did not inline them (apps/web/src/server/api.ts).
