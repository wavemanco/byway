## Context

The renderer is the one place byway runs content it did not write: pages a model writes, with their scripts, web-page examples given as HTML, and the cards a reviewing model sees, which decode images people upload and images providers return. Since F07 it also reads the text a page shows a visitor, with the page's scripts running ([ADR-0081](0081-voice-writes-the-persons-copy-exactly.md)). [ADR-0084](0084-renderer-launch-without-secrets.md) took the keys out of Chromium's environment and stated one launch, but left Chromium's own OS sandbox off, as it always had been: Playwright adds `--no-sandbox` to every Chromium process unless asked otherwise. Whether to switch it on was decision D2 of the [external-review verification](../reviews/2026-10-08-external-review-verification.md) (§4 item 2), the open part of finding F18.

**The brief and its skeptic** (2026-10-16; `owner-decisions.json`, entries "analyse:D2" and "challenge:D2", under Evidence):

- **Off**, one Chromium, V8 or image-decoder bug lets that content run as the person: it can read `.env.agents` (keys spendable at the providers outside byway's budgets), change the spend book, the ledger and its head together without detection (the ledger's head is not anchored outside the data directory, `packages/gateway/src/ledger.ts`), and read the rest of the account. **On**, the page renderer runs at Untrusted integrity on Windows, and the same content needs a second bug to get out. The skeptic put the threat as unlikely but serious, with protection that costs almost nothing.
- **Measured on Windows 11** with Playwright 1.63.0: with the sandbox on, tiles and visitor reads were byte-identical, a launch took as long, and page scripts and image decoding worked. With the constant flipped, 188 of 189 real-Chromium tests passed; the one that failed was the test that pins the value.
- **Where it cannot start:** Ubuntu 24.04 and later, which restrict unprivileged user namespaces unless an AppArmor profile allows them for the program (23.10 brought the restriction in without turning it on; [ADR-0084](0084-renderer-launch-without-secrets.md) says "the default on Ubuntu 23.10 and later", which is wrong); byway run as root; inside Docker or another container; rarely, locked-down machines whose security software blocks it.
- **Readiness did not reach the sandboxed process.** `ready()` and `checkRenderer()` only launched the browser, which starts the GPU and network-service processes but not the page renderer, the process the sandbox exists for. A failure only the sandboxed page renderer hits would have passed the start-up line and the readiness check before money was spent, then failed at the first draw with a message that never named the sandbox.
- **Playwright's words.** With its pipe transport, the error's first line only says "Target page, context or browser has been closed"; further down it says "Chromium sandboxing failed!", which Playwright writes in place of Chromium's own log when that log holds "No usable sandbox!", "crbug.com/357670" or "crbug.com/638180" (the last when Chromium runs as root). byway's message for a launch failure would have blamed a missing install.

**The owner's decision** (2026-10-16). The coordinator proposed: "1. On by default on every OS. 2. If it can't start, byway says so in the app, not only the terminal. It explains why for that OS and gives the fix, for example the exact AppArmor command on Ubuntu 24.04 or 'don't run byway as root'. 3. An explicit off switch in Settings, not a hidden setting. Turning it off asks you to confirm and explains the risk plainly: a malicious page or image plus a browser bug could then run as you, next to your API keys and spending records. 4. While it's off, you can't forget it: a persistent banner on every screen; a note on each run whose pages were drawn without it; the start-up line. At each start, byway also checks whether the sandbox could now start (for example after you've applied the fix) and offers to turn it back on. 5. Never automatic: byway never turns the sandbox off by itself." The owner answered: "go with revised design but only Windows and Linux for now. MacOS later (so you might want to make certain accommodations now for that)."

[ADR-0106](0106-a-late-close-retires-the-renderers-browser.md), built first in the same wave, gives the renderer a way to replace its browser without failing the renders still on the old one, which a change of this setting needs.

## Decision

**Who decided what.**

- **The owner** decided the design on 2026-10-16 (quoted under Context). On 2026-10-18 the owner answered three more questions (the session's transcript, under Evidence):
  - CI's Ubuntu 24.04 machine, where the kernel restricts user namespaces, is enough to ship the sandbox on for Linux for now. The owner's chosen answer read: "Ship it on for Linux; the README says the steps are proven on CI's Ubuntu 24.04 and not yet on a desktop install; trying them on the first real Linux machine stays in the backlog." The closed D2 backlog row had asked for a desktop trial before the sandbox was switched on for Linux. (The README may not say "proven", which byway's claims rule forbids there, so it says the steps have run on CI's machine and not yet on a desktop install.)
  - The start-up probe without the sandbox (item 5) stays, recorded as Claude's choice.
  - Linux (item 8): asked "since any AppArmor exception for Chromium weakens Ubuntu's restriction for programs running as you, which approach?", the owner chose "Simple home-folder profile, honest wording": the one-step script on Playwright's own folder, with the README and the script saying plainly that it lets programs running as the person use user namespaces, as Ubuntu's own profile for Chrome does, and that the alternative is to switch byway's sandbox off, so the person chooses per machine. The reason put to the owner: round 2's security check had shown that any such exception is open to `LD_PRELOAD` and `aa-exec`, so the folder only root can change that round 2 had built added friction for little protection (Alternatives).
- **Claude chose**, within the D2 wave the owner started, each reversible:
  - one setting for the data directory, where the brief had named the workspace's preferences (item 1);
  - reading the setting before each load (item 2);
  - the probe itself, which draws byway's own test page without the sandbox (item 5).

1. **On by default, a setting the person owns.** Chromium runs inside its OS sandbox unless the person switched it off in Settings.
   - The setting lives in the store, one for the data directory, since the engine's one renderer serves every workspace: `RendererSettings` (contracts), the `renderer_settings` table (migration 8). Never set means on.
   - The only writer of the setting is `Store.setRendererSandbox`, which only Settings' route calls (`PATCH /api/renderer`, body `{ osSandbox }` and nothing else; the route's `GET`, which the banner calls, only reads). Recording the start-up check never changes it.
   - `apps/web/test/guard-sandbox.test.ts` holds the product sources to that: every code file under `packages/<name>/src`, apps/web's `src` and `app` and its own root code files (not its browser tests' config or a type declaration), and `scripts` other than `scripts/test`, with lines that are only a comment left out. It pins as exact lists every line that mentions a way to:
     - switch the setting: `setRendererSandbox`, Settings' `updateRenderer`, `/api/renderer` (Settings' switch and the banner's read), and the setting's table and column (`renderer_settings`, `os_sandbox`), which only the store's migration, its queries and the reader of its row name;
     - set Chromium's `chromiumSandbox` option: only in `chromiumLaunchOptions`, from the setting;
     - build a renderer: `playwrightPages`, `renderBrowsers`, `checkRenderer` and `storeOsSandbox`, so renderers are built only by the worker (the store's setting) and by the start-up check (below), which only `scripts/serve.ts` runs;
     - launch Chromium: `launchChromium`, `chromiumLaunchOptions`, the test-only `launch` seam, Playwright's launch calls (`launch`, `launchPersistentContext`, `launchServer`, `connectOverCDP`), and any line that names Playwright's packages (`playwright`, `playwright-core`, `playwright-chromium`, `@playwright/…`), Puppeteer's or `chromium-bidi` in quotes, as an import does, which only `packages/runner/src/pages.ts` has.
   - A line counts whatever its arguments look like, so a setting in a named function or a shorthand property moves a list as an inline one does. A line that opens an import or re-export list (`import {`, `import * as`, `export {`, `export *`) is pinned by its file alone, so naming one more thing in a list already pinned is not a change, but a new importer is. The guard also checks itself against each way round it that reviews have found (the launch seam with a launch of its own, a setting in a named function, `chromiumLaunchOptions` handed to Playwright, Playwright's own launch, whose default is no sandbox, and more): each must change one of its lists.
   - It does not see a use that names none of these (a namespace import called by a computed name, SQL that builds the table's or the column's name from pieces), a browser driver it does not list, a browser started as a program of its own, a file outside those it reads, or a change inside the lines it pins, such as a retry without the sandbox in `pages.ts`; `launch.test.ts`, `pages.test.ts` and `renderer-check.test.ts` check that behaviour. `launchChromium` and `chromiumLaunchOptions` are not exported from the runner package.
   - `RENDERER_OS_SANDBOX` becomes `RENDERER_OS_SANDBOX_DEFAULT`, true. A setting that cannot be read counts as on.
2. **Read before each load; a change applies from the next one.** The renderer reads the setting before every load (a render's screen, a visitor read, the readiness check's test page) and launches its browser with the setting read for the load that launches it (`launchChromium({ osSandbox })`, the only production launch, which takes nothing else). A browser launched with the other setting is retired, as for a late close ([ADR-0106](0106-a-late-close-retires-the-renderers-browser.md)): new loads launch another, the loads still on it finish there, and it is closed when the last of them ends, with the reason "byway closed the page renderer after its OS sandbox setting changed" (the backstop applies as for any retired browser). Nothing under way is cut short.
3. **Readiness draws a page.** `ready()` finds or launches the browser under the setting in force and, the first time it is asked on that browser, draws byway's own test page there, whose script must run. A browser that has drawn any page has nothing left to prove. `beginRun` (web-page runs) and the model step's readiness (runs whose examples form cards) call it before anything is spent, so a run whose page renderer cannot start is refused then. The test page is never counted as a page drawn for a run.
4. **A plain message, per system.** A failure whose text holds Playwright's "Chromium sandboxing failed!" or one of Chromium's three markers, anywhere in the error including its log and cause, is the sandbox's: one plain step failure, not retried, that says the page renderer could not start inside its OS sandbox on this computer, so pages and cards cannot be drawn, then why and the fix (`packages/runner/src/sandbox.ts`):
   - **Windows:** the sandbox is Chromium's normal mode, so something blocks it, most often security software or a company policy; allow Playwright's Chromium or ask whoever manages the computer. The message names the file byway runs: byway launches Chromium headless, which Playwright runs as its headless shell (`chromium_headless_shell-<revision>\chrome-headless-shell-win64\chrome-headless-shell.exe`), not the full Chromium that Playwright's `chromium.executablePath()` names. byway finds the shell from that path, beside full Chromium in Playwright's browsers folder and of the same revision (so `PLAYWRIGHT_BROWSERS_PATH` is followed), and names the folder instead when the file is not there (`sandbox.ts` `headlessShell`). `pages.test.ts` compares the named file with the program a real launch runs.
   - **Linux**, in this order: as root (Chromium's own marker, or user id 0): start byway as an ordinary user. In a container (`/.dockerenv`, `/run/.containerenv`, the `container` variable, or a container's cgroup): run byway outside it. AppArmor restricting user namespaces (`kernel.apparmor_restrict_unprivileged_userns` = 1; Ubuntu's default from 24.04): run `sh scripts/linux/allow-chromium-sandbox.sh`, then start byway again; Renderer in the README says what else its profile allows (item 8). User namespaces switched off (`kernel.unprivileged_userns_clone` or `user.max_user_namespaces` = 0): someone with admin rights has to switch them on. Otherwise: byway could not tell, and the README lists the usual causes.
   - **macOS, and any other system:** byway does not support it yet; byway runs on Windows and Linux. This is the slot macOS will fill.
   - A test page that fails with the sandbox on and no marker names the sandbox as one possible cause, with the same why and fix, and memory as another. Two failures of the test page are said as they are, with no word of the sandbox: one past its own 30 s ("The page renderer did not draw byway's test page within 30 s."; item 5 and Consequences say where that is seen), unless the start-up check found the sandbox cannot start (below), and one byway's own close stopped ("byway's test page could not be drawn: byway closed the page renderer …", with byway's reason).
   - A launch that fails with the sandbox on and no marker, other than a Chromium that is not there (Playwright's "Executable doesn't exist"), names the sandbox as one possible cause too, with the same why and fix, and keeps the install command. On Windows a sandbox that cannot start ends Chromium at launch with none of the markers, so without this a run would be refused with the install command while the banner and Settings blamed the sandbox.
   - Once byway's last start-up check found the sandbox cannot start on this computer (item 5), the readiness check that refuses a run (item 3) reads that from the store, and a sandboxed start that fails again, other than a Chromium that is not there or a renderer byway closed, is refused with the sandbox's message, as the start-up line and Settings say it.
   - No message advises switching the sandbox off. `packages/runner/test/sandbox.test.ts` launches the installed Playwright against a stand-in for Chromium that prints each marker and exits, and checks Playwright's words and the first line (the drift test).
5. **The start-up check, and its record.** `scripts/serve.ts` reads the setting from the store and runs `checkRenderer({ osSandbox })`, which draws the test page in a renderer of its own and closes it.
   - **On:** if the test page cannot be drawn and Chromium did not tie the failure to the sandbox, the test page is drawn once more without the sandbox; if that works, the sandbox is the cause, and the check says why and the fix. If it fails too, the sandbox is not shown to be the cause, and the check gives the message of the attempt without it.
   - **Off:** the test page is also drawn with the sandbox on, to say whether the sandbox could start now.
   - Neither probe changes the setting, and neither draws anything but byway's own test page (the owner kept the probe on 2026-10-18, after round 1's checks).
   - **On, what the check answers when the sandboxed test page could not be drawn for no reason Chromium gave:** the probe draws the page, so the sandbox's why and fix; the probe fails too, so the probe's own message, which does not blame the sandbox; or the probe is late (next bullet), so the sandboxed attempt's message. That message is, for a launch that died, or a test page that failed, with no reason given, the sandbox as one possible cause, with why and the fix (item 4); for a sandboxed test page that ran past its own 30 s, only that it was not drawn in time ("The page renderer did not draw byway's test page within 30 s."), with no word of the sandbox.
   - **Each probe has its own limit, 15 s**, less than the test page's own 30 s, so a probe that hangs is not read as a sandbox that fails. A probe that has not answered by then is closed: its renderer is closed and launches nothing more ([ADR-0106](0106-a-late-close-retires-the-renderers-browser.md) item 1). A launch still on its way cannot be cut short (Playwright's own launch timeout bounds it); its browser is closed as it arrives, before any page, and the probe's readiness check then fails with "byway closed the page renderer as it shut down", which nothing reads. So a probe draws only within its 15 s. The check answers with what it had found: off, ready with the sandbox unknown; on, not ready with the sandboxed attempt's message, as above.
   - **The start-up line's own limit** (30 s, counted once the app is built and the engine is up; [ADR-0084](0084-renderer-launch-without-secrets.md)'s later note) says what the check had found by then (`scripts/serve.ts` passes the check a `progress` that `rendererCheckWithin` reads): while a probe runs, that is the answer the check would give if the probe were late, with the messages above. If the check had found nothing yet, the line says "not checked in time" and that byway could not tell whether it can draw pages, and nothing about Chromium; the record then has no `ready`.
   - The `renderer` line says "Playwright's Chromium, ready, inside its OS sandbox"; or "…, ready, with its OS sandbox off (switched off in Settings)" and then whether the sandbox can start on this computer now (Settings offers to turn it back on), still cannot, and why, or that byway could not tell; or "not available" with the message; or "not checked in time". The result is recorded in the store (`Store.recordRendererCheck`), where Settings reads it. `pnpm e2e` fails unless the line says "Playwright's Chromium, ready, inside its OS sandbox". Under it, byway names Playwright's browsers folder, as Playwright resolves it (`browsersFolder()`; `PLAYWRIGHT_BROWSERS_PATH` moves it, and on Linux `XDG_CACHE_HOME`), so a person on Linux can check that byway takes Chromium from the folder item 8's profile covers.
6. **In the app.**
   - **Settings, "Page renderer's OS sandbox":** the switch. Turning it off asks first and explains the risk plainly, as item 3 of the design the owner approved says it does (quoted under Context), in words Claude wrote: "With the sandbox off, a malicious page or image, together with a bug in Chromium, could run as you on this computer, next to your API keys and spending records. byway shows a banner on every screen while it is off." Turning it on asks nothing. Under the switch, what the last start-up check found: why the sandbox could not start and the fix; while it is off and the sandbox could start, a "Turn the sandbox back on" button; that byway could not tell whether it can start; or that the page renderer was not ready, or not checked in time, with the message. Keyboard and screen reader: a `role="switch"` button that keeps focus while it saves; the confirmation is a named group whose "Keep it on" takes focus, and both its answers are described by the risk (`aria-describedby`), so a screen reader reads it with the one that has focus (the group is not, or the risk would be read twice); when the confirmation or the offer goes, focus returns to the switch; a status line announces the change.
   - **A banner on every screen** (the demo banner's pattern, `role="note"`) while the sandbox is off, and while it is on but the last start-up check found it could not start ("byway cannot draw pages: …"). Each links to Settings' section. A client component in the root layout draws it (`SandboxBanner`): it starts from the server's state and, as the header's waiting count does, reads the renderer's state again (`GET /api/renderer`) on every navigation, every 5 s while the tab is visible and when it is shown again, and at once when that tab's own switch changed it. So every open tab shows the banner, and loses it, without a reload, the ones opened before the change included (round 2's check WEB-R2-1: the root layout outlives page changes, and a banner drawn only by its server render stayed as it was in every other tab).
   - **A note on each step whose pages were drawn with the sandbox off:** the renderer tells each load's caller the setting it was drawn under, and the step's first page drawn without the sandbox writes one `renderer-sandbox-off` event for that step call, which the Run screen's timeline and the Result's "How this was made" show with the step's notes (a step that failed shows its notes under its failure): "Pages in this step were drawn with the page renderer's OS sandbox off (it was switched off in Settings)."
7. **Never automatic.** byway never switches the sandbox off, or on, by itself. The offer to turn it back on is a button the person presses.
8. **Linux: one script for the README and CI, on Playwright's own folder, saying plainly what it allows.** `scripts/linux/allow-chromium-sandbox.sh` runs as the person, not as root, and asks for `sudo` for its two commands that need it: writing the profile and loading it. It:
   - adds one AppArmor profile, `playwright-chromium`, attached to Playwright's own browsers folder as Playwright finds it on Linux, `${XDG_CACHE_HOME:-$HOME/.cache}/ms-playwright/chromium*/chrome-*/chrome{,-headless-shell}` (the headless shell and full Chromium, in the folder layout Playwright 1.63 uses; named as the folder it really is when a symbolic link leads to it, since AppArmor matches the file actually run), with `flags=(unconfined)` and `userns`: those programs may create user namespaces and are confined in no other way, as with Ubuntu's own profile for Google Chrome. A Playwright upgrade that keeps that layout needs nothing more, and CI's Linux tests with the sandbox on show when one does not;
   - refuses when `PLAYWRIGHT_BROWSERS_PATH` is set (byway would take Chromium from a folder the profile does not cover), when that folder is not a full path or does not exist yet, and when its path, or the path a link leads to, has a space or a character AppArmor reads as a pattern;
   - says plainly, at its top and in what it prints at the end, what else the profile allows, as the README does: any program running as the person can then create user namespaces through it, which is what the restriction exists to stop. It can start one of those Chromium programs with a library of its own (`LD_PRELOAD`); while `kernel.apparmor_restrict_unprivileged_unconfined` is 0, Ubuntu 24.04's default, it can enter the profile by name with `aa-exec`; and it can put a program of its own in that folder, which is the person's to write. Ubuntu's own profile for Google Chrome can be used in the first two ways too. The alternative it names is to add no profile and switch byway's sandbox off in Settings, which has its own risk, and it says that the restriction is then as Ubuntu set it, which on Ubuntu 24.04, while `kernel.apparmor_restrict_unprivileged_unconfined` is 0, Ubuntu's own profiles (loaded whether or not their programs are installed) already open to `aa-exec`; the person chooses for each machine. It ends with how to remove the profile;
   - prints `kernel.apparmor_restrict_unprivileged_userns` and, where the kernel has it, `kernel.apparmor_restrict_unprivileged_unconfined`, and says no profile is needed where the kernel has no restriction setting.

   byway's AppArmor message names the script and says that Renderer in the README says what else its profile allows; a Chromium that is missing gives Playwright's own install, which puts it in the folder the profile covers unless `PLAYWRIGHT_BROWSERS_PATH` moves it. The README's Renderer section gives the script, what else it allows and the alternative, and says the steps have run on CI's Ubuntu 24.04 machine and not yet on a desktop install. CI's Linux job runs Playwright's own install with its system libraries, then the script, so every CI run tries the README's steps on a fresh Ubuntu 24.04 machine. `scripts/test/ci.test.ts` holds the script, the workflow and the README to this: one profile on that folder, the two commands as root and no other, the refusals of a moved folder, of a folder that is not a full path and of a path with a space, which it runs (no test runs the refusals of root, of a folder that does not exist yet or of the path a link leads to; the last two the script reaches only where the kernel has the restriction setting), and the plain statement at the top and at the end; and the script, the workflow, both READMEs, the renderer's code, `scripts/serve.ts` and the backlog to no claim that the profile gives the namespaces to Chromium alone, that the rest of the machine stays restricted, that switching byway's sandbox off keeps the restriction whole, or that the profile covers any or every version.
9. **Correction.** Ubuntu 23.10 brought in the restriction on unprivileged user namespaces without turning it on; 24.04 is the first release that restricts them by default. [ADR-0084](0084-renderer-launch-without-secrets.md)'s "the default on Ubuntu 23.10 and later" is wrong.

## Alternatives considered

- **Keep it off** (the brief's option 1). No work and no new failure, but a hostile page or image plus one Chromium bug runs with the person's full rights, and the protection is free where byway runs today.
- **On, fail closed, no off switch** (option 2, the brief's and the skeptic's recommendation). Simplest, and no switch to forget. The owner chose an explicit switch instead, so a teammate whose machine cannot start the sandbox is not stuck, and asked for "a pop-up or a message of some kind" so that the switch is not forgotten, and to "tell them of the risks too (if any)" (2026-10-16); the revised design the owner approved made that the banner, the run notes, the start-up line and the offer.
- **A switch in the environment or in `.env.agents`** (option 3 as first written), or a flag typed at each start (the skeptic's variant). The revised design the owner approved puts the switch in Settings, where it is seen and asked about; a value in a file is copied and forgotten.
- **Fall back to no sandbox where it cannot start** (option 4). The machines that lose the protection would be exactly the ones where nobody chose to. The design the owner approved rules it out (its item 5, "Never automatic").
- **A preference per workspace.** The renderer is one per engine and serves every workspace, so a per-workspace setting could disagree with the browser in use. One setting for the data directory, in the store the web app and the engine share.
- **Read the setting once at start-up, and restart byway to change it.** Simpler, but a change would need a restart and would apply to no run in between; reading before each load costs one SQLite read, and ADR-0106's retirement keeps the loads under way.
- **Keep `ready()` a launch only.** It would not start the page renderer, the process the sandbox is for, so a machine whose page renderer cannot start in the sandbox would pass every readiness check and fail after paid steps.
- **Recognise a sandbox failure from Playwright's first line.** That line is the same as a crash's. The whole error is read, and the drift test holds the words to the installed Playwright.
- **No probe without the sandbox: say only that the cause is unknown.** Closest to the approved design's "Never automatic", since Chromium would never start without the sandbox unless the person switched it off. Not chosen: on Windows a sandbox that cannot start ends Chromium with no word of why, so byway could never tell the person that the sandbox is the cause, nor give its fix with any confidence, and a person whose sandbox cannot start would be left to guess, with the off switch the nearest thing to hand. The probe draws only byway's own test page, which holds nothing from a run, and changes no setting, so nothing byway did not write is ever drawn without the sandbox by byway's choice; it runs only when Chromium gave no reason (with one of its markers, the cause is known). Claude chose the probe; round 1's checks asked whether to keep it, and the owner kept it on 2026-10-18.
- **Name the full Chromium that `chromium.executablePath()` names** (as first built). Rejected: byway does not run it, so allowing it does not unblock the renderer, and after `playwright install --only-shell` it is not there (round 1's check S1).
- **Name the program from the launch error's `<launching>` line.** Exact for a failed launch, but a test page that fails after the launch has no such line, and neither has what the start-up check found. Finding the shell beside full Chromium covers every message, and the drift test holds it to a real launch.
- **Name only Playwright's browsers folder.** It would survive a Playwright update, which changes the file's path, but security software is more often told about a file than a folder. byway names the file, and the folder only when the file is not there.
- **Keep the install command alone for a launch that dies with no reason given** (as first built). On Windows a run would then be refused for a missing install while the banner and Settings blamed the sandbox (round 1's check S2).
- **A Chromium in a folder only root can change** (round 2's build, the owner's option "Keep the root folder, fix the wording"). After the automated security review of 2026-10-18 found that a profile on the person's own folder covers any file a program running as them puts there, round 2's script installed Playwright's Chromium as root in `/opt/byway/ms-playwright`, attached the profile there, and had the person export `PLAYWRIGHT_BROWSERS_PATH`; CI ran it (run 39149469179). Round 2's security check then showed that any such exception is open to `LD_PRELOAD` on every release and to `aa-exec` on Ubuntu 24.04, whatever folder it is attached to, so the root folder removed only the route of putting a file in the folder, while the docs said the profile let "nothing else" create user namespaces and "the rest of the machine stays restricted", which was false. Against that small gain it had real costs: `sudo` ran the person's Node and byway's Playwright as root, at install and after every Playwright upgrade; a variable had to be exported; and after each upgrade the renderer could not start until the script ran again. The owner chose the home folder, with the trade-off said plainly (Who decided what).
- **No script: explain both choices in the app** (the owner's option "No script; explain both choices"). On Ubuntu 24.04 the in-app message would explain adding an AppArmor exception yourself or switching byway's sandbox off, and their risks. Claude recommended the script instead, and the owner chose it: without one, a person who wants the sandbox would write a profile by hand, which CI could not try for them, and with the script and the trade-off said plainly the choice per machine is still the person's.
- **Give the start-up check's test page a shorter limit**, so both attempts fit in the line's 30 s. A first draw slowed by the build would then fail and, with a quick probe without the sandbox, be read as the sandbox's failure. Instead the probe has its own limit, and the line says what the check had found.

## Consequences

**Positive**

- Content byway did not write runs inside Chromium's sandbox by default, on Windows at Untrusted integrity, with nothing else changed where it was measured.
- A machine whose sandbox cannot start is told why and how to fix it, at start-up, in Settings, on every screen and in a run's failure, before anything is spent. Where Chromium gives no reason, as on Windows, a run's failure names the sandbox as one possible cause until the start-up check has told the causes apart, and then says it as the start-up line does.
- The off switch exists and cannot be forgotten: the banner, the run notes, the start-up line and the offer to turn it back on.
- CI tries the README's Linux steps on every run.

**Negative and residual**

- **Linux machines that restrict user namespaces cannot draw pages with the sandbox on until someone runs the script**, which needs admin rights once; until then the renderer's message names it. The steps have run only on CI's Ubuntu 24.04 machine, not on a desktop install, as the README says: the owner decided on 2026-10-18 that this is enough to ship for now, and trying them on the first real Linux machine stays in the backlog.
- **The script's profile weakens Ubuntu's restriction for that person.** Any program running as them can create user namespaces through it: by starting one of Playwright's Chromium programs with a library of its own (`LD_PRELOAD`), on every release; by entering the profile with `aa-exec` while `kernel.apparmor_restrict_unprivileged_unconfined` is 0, Ubuntu 24.04's default; and by putting a program in Playwright's folder, which is theirs to write. Ubuntu's own profile for Google Chrome can be used in the first two ways too; the third is this profile's own, since Chrome's folder is root's. On a machine with no such program that sets `kernel.apparmor_restrict_unprivileged_unconfined` to 1, this profile can be the only way round the restriction. The README and the script say so, with the alternative (the sandbox off, with its own risk), and the person chooses.
- **Root and containers** cannot draw pages with the sandbox on. Playwright's seccomp profile for containers is not tested here.
- **macOS** is not supported: the messages say so, and nothing claims it works there.
- **The probes launch Chromium a second time at start-up** when the sandbox is off, or when it is on and failing for no reason Chromium gave. Each draws only byway's own test page, and only within its 15 s: one that has not answered by then is closed, launches nothing more, and leaves the sandbox unknown. A launch still on its way then is not cut short: Playwright's own launch timeout bounds it, and its browser is closed as it arrives.
- **On Windows, the file the fix names changes with each Playwright update**, so an allow rule for one version stops covering the next; the next failure names the new file.
- **A sandboxed test page slower than 30 s** is said as "The page renderer did not draw byway's test page within 30 s.", with no word of the sandbox: in a run's refusal, unless the start-up check found the sandbox cannot start; and in the start-up check when the probe without the sandbox does not answer within its 15 s either, or when the start-up line's 30 s come while that probe runs. When the probe draws the page in time, the check finds the sandbox the cause, with why and the fix.
- **The start-up check is a snapshot.** The banner, Settings' findings and the offer reflect the last start; after applying a fix, starting byway again updates them. Runs do not wait for a restart: a failed launch is tried again on the next load.
- **On Windows, the broker and the network service still run at Medium integrity**, as ADR-0084 recorded; the sandbox holds the page renderer.
- **The Playwright driver still runs in the engine process**, which holds the keys.
- **A sandbox escape still needs only a second bug.** Playwright is pinned, so known bugs collect over time; the Playwright bump policy stays a backlog row.
- **The research harness's own renderer** (`protocol/06-runbook.md`, `chromium.launch()`) is not changed by this record.
